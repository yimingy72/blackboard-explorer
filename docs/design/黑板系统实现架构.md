# 黑板式探索系统 · 实现架构

> 本文是《黑板式探索架构设计.md》的实现层设计。前者定义"黑板是什么、Agent 怎么协作、调度规则是什么"；本文定义"用什么容器、什么数据结构、什么框架接口把它做出来"。
>
> 技术选型：后端 Python 3.12（FastAPI + Microsoft Agent Framework），存储 PostgreSQL 16 + pgvector，对象存储 MinIO（S3 API），前端 React + @xyflow/react（React Flow v12）。
>
> 变更记录见附录 A。开发计划见《黑板系统开发方案.md》。

---

## 0. 框架层面的四个判断

### 0.1 调度器不用 MAF Workflow

MAF Workflow 采用超步（superstep）模型：同一超步内所有 executor 并行执行，**全部完成后**才进入下一超步。若把"调度器 → 扇出 N 个 explore → 扇入 → 调度器"做成 Workflow，5 个 explore 里有一个 2 分钟结束、其余跑 20 分钟时，空出的槽位要等 20 分钟后才能复用。这与"存在 open 意图且有空槽位就创建 explore"直接冲突。

| 方案 | 结论 | 理由 |
|---|---|---|
| MAF Workflow | 不用 | 超步屏障 |
| Temporal | v1 不用 | 持久化与重试能力和黑板重复；多一套 server + worker；Agent 运行需包成带心跳的 activity |
| Celery / Prefect / Dagster | 不合适 | 面向批任务与 DAG，不是"读状态 → 决策 → 派发"的连续循环 |
| **自建 asyncio 循环** | **采用** | 规则少；状态全在黑板，调度器无状态，重启即恢复；单实例用 Postgres advisory lock 防重复 |

MAF 的使用范围：Agent 本体（模型调用、工具循环、中间件、上下文提供者、会话、消息注入、OTel）和 MCP 客户端。

### 0.2 v1 不部署模型网关

MAF 没有网关/路由类，只有 provider 客户端（`agent_framework.openai`、`anthropic`、`ollama`、`azure`、`foundry` 等）。"按任务类型选模型"由代码构造不同 client 解决，"记账"由 `ChatMiddleware` 读 `usage` 解决。需要统一多家提供商、跨服务限流或审计时，加一个 LiteLLM，MAF 侧只改客户端的 `base_url`。

**v1 模型**：统一使用 DeepSeek `deepseek-flash`（DeepSeek-V4.1-Flash，上下文 1M，默认开启思考模式）。DeepSeek 提供 OpenAI 兼容的 Chat Completions 接口，因此用 MAF 的 `OpenAIChatCompletionClient`（`base_url=https://api.deepseek.com`）。注意 MAF 的 `OpenAIChatClient` 对应的是 OpenAI Responses 接口，DeepSeek 不适用。已实测：工具调用正常；多轮工具调用时不回传 `reasoning_content` 也不报错；`reasoning_effort`（low / high / max）可用；用量中含 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 与推理 token 数。

### 0.3 框架行为核对结论（本版新增，已对照 MAF main 分支源码）

| 事项 | 核对结果 | 设计处理 |
|---|---|---|
| 函数调用循环上限 | `FunctionInvocationConfiguration.max_iterations` 默认 **40**（模型往返次数），小于 `explore_max_steps=60` | 构造 client 时设 `max_iterations = explore_max_steps + conclude_grace_calls + 5`；另设 `max_duration_seconds` 作兜底 |
| 函数中间件的"终止" | 设置 `context.result` 且不调用 `call_next` = **替换工具结果，模型继续**；抛 `MiddlewareTermination` / terminate = **结束整个运行** | 宽限管控必须用前者（旧版用了 terminate，会直接中断 Agent） |
| 运行中同步消息 | M2a 在 MAF 1.19 实测：enqueue 的增量只在当轮可见，下一轮工具调用丢失；追加公开 Content.text/result 则跨轮保留 | BoardSync 把增量追加到最近工具结果，首轮无工具结果时附到已有 user 文本；每段仅追加一次，显式使用 Agent session |
| MCP 工具 | MCP 工具被转换为 `FunctionTool`，**经过函数中间件**；HTTP 头参数为 `static_headers`（另有按调用生成的 `header_provider`） | call_id 统一由记录中间件生成，envd 不再单独生成 |

### 0.4 重复判断归 Agent

Agent 已通过启动快照与增量同步获得黑板信息，由 Agent 自行判断事实和意图是否重复；必要时通过 get 或关键词 search 查看已有原文。黑板不生成向量、不部署本地 embedding 模型，也不做相似度预检、top-3 提示或二次确认拦截。

黑板继续执行证据存在性、引用、权限、意图认领与状态迁移等确定性规则；提交通过这些校验后直接追加事件。关键词查询只帮助定位原文，不替 Agent 判断语义重复。

## 1. 总体架构

### 1.1 容器拓扑

```
                       ┌────────────────────────────────────────────────────┐
  浏览器 ──REST/SSE──▶ │ blackboard                                          │
                       │  FastAPI：黑板 API · 事件流 · 验收评估 · Agent 配置管理 │
                       │  关键词查询与黑板信息同步                        │
                       │  托管前端静态文件（React Flow 工作台）                  │
                       └───────┬───────────────────────────┬────────────────┘
                               │                           │
                     ┌─────────▼─────────┐       ┌─────────▼─────────┐
                     │ postgres (pgvector)│       │ minio (S3 API)     │
                     │ 事件日志 · 折叠表   │       │ 证据 · 工具日志     │
                     │ Agent 配置 · 原文   │       │ 报告 · workspace 归档│
                     └───────────────────┘       └─────────▲─────────┘
                                                           │ 上传
  ┌────────────────────────────────────────────────────────┴───────────────┐
  │ agent-runtime（全局一个）                                                │
  │  · 调度循环（asyncio，每任务一个） · MAF Agent 池 · 执行环境生命周期管理      │
  │  · 黑板工具（Python 原生）        · 中间件        · 模型 provider 客户端    │
  └──────┬─────────────────────────────────────────────┬────────────────────┘
         │ Docker API：创建/销毁                        │ MCP (streamable HTTP) + 内部文件接口
  ┌──────▼──────────────┐  ┌──────────────────────┐  ┌─▼────────────────────┐
  │ exec-env-{task A}    │  │ exec-env-{task B}     │  │ …                     │
  │ ubuntu + envd        │  │ ubuntu + envd         │  │ 一个任务一个容器        │
  │ /workspace           │  │ /workspace            │  │ N 个 Agent 共用        │
  └──────┬──────────────┘  └──────┬───────────────┘  └──────────────────────┘
         └────────────┬───────────┘
              ┌───────▼────────┐
              │ egress-proxy    │  仅显式代理隔离模式使用；默认执行环境直接出网
              └────────────────┘

  横切：otel-collector（可选）
  后续可选：model-gateway（LiteLLM）
```

| 容器 | 数量 | 有无状态 | 职责 |
|---|---|---|---|
| `blackboard` | 1 | 无（状态在 postgres/minio） | REST + SSE + 前端静态；写入校验、关键词查询、快照、验收评估、Agent 配置 |
| `postgres` | 1 | 有 | 事件日志、折叠表、agent_runs、tool_calls、Agent 配置 |
| `minio` | 1 | 有 | 证据、工具调用全文、报告、workspace 归档 |
| `agent-runtime` | 1（v1） | 无（重启后重读黑板） | 调度循环、MAF Agent、执行环境管理 |
| `exec-env-{task}` | 每任务 1 | 有，任务结束归档后销毁 | Agent 的唯一副作用发生地 |
| `egress-proxy` | 可选1 | 无 | 代理隔离模式下的出网代理与部署级域名白名单 |

### 1.2 三条原则

1. **黑板是唯一事实来源。** agent-runtime 内存里不保存黑板状态，每次决策都读 blackboard。
2. **副作用只发生在 exec-env。** agent-runtime 不碰业务文件系统、不发业务请求；一切通过 `execute_command` 在 exec-env 里做。
3. **Agent 拉，UI 推。** Agent 在每次模型调用前拉 `delta(since)`；UI 通过 SSE 收事件。

## 2. 执行环境（exec-env）

### 2.1 镜像

`ubuntu:24.04` + 常用工具链（git、curl、python3、jq、build-essential，按问题域追加）+ `envd`（Python 进程，端口 8080）。镜像名由 `agent_profiles.exec_image` 指定，不同问题域可以准备不同镜像。

### 2.2 envd 接口

agent-runtime 独占 `ENVD_TOKEN_SECRET`，以任务 UUID 的标准小写连字符字符串为消息、secret 的 UTF-8 字节为密钥，计算 HMAC-SHA256 的十六进制摘要作为每任务 `ENVD_TOKEN`，创建容器时注入。envd 只读取 `ENVD_TOKEN`，不接收派生密钥；MCP 与内部接口均校验 `Authorization: Bearer <ENVD_TOKEN>`。执行 Agent 命令时不向子进程传递控制面 token；默认不注入代理变量，显式代理隔离模式才注入egress-proxy地址。

**MCP 端点 `/mcp`**（给模型用，streamable HTTP）。只暴露一个工具：

```
execute_command(command: str, cwd: str | None = None, timeout_sec: int = 120, privileged: bool = False)
  -> {exit_code, stdout, stderr, truncated, full_output_path}
```

- 请求头 `X-Agent-Id`（连接时由 `static_headers` 设置）决定以哪个 Linux 用户执行（见 2.3），默认 `cwd=/workspace/agents/{agent_id}/`。
- `timeout_sec` 上限 `command_timeout_max`（默认 1200 秒）；超时杀整个进程组。并发调用各自独立子进程。
- stdout/stderr 合计超过 64KB 时保留头尾各 32KB，`truncated=true`，全文写入 `/workspace/agents/{agent_id}/.outputs/{seq}.txt`，路径在 `full_output_path` 返回。
- `privileged=true` 时以 root 执行，但只放行白名单命令前缀（`apt-get install`、`pip install`、`npm install -g` 等，按镜像配置），其余拒绝。
- 返回值作为数据包裹：`<command_output>…</command_output>`，提示词说明其中内容是数据不是指令。

**内部接口**（只给 agent-runtime 用，模型不可见，每任务 token 鉴权）：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 健康检查 |
| GET | `/files?path=` | 读文件字节（post_fact 取证据）；超过 `evidence_max_bytes` 返回 413 |
| GET | `/stat?path=` | 存在性、大小、类型 |
| POST | `/users` | 为新 Agent 预建 Linux 用户与工作目录（spawn 时调用） |
| POST | `/archive` | 按排除规则打包 `/workspace` 为 tar.zst，流式返回 |

### 2.3 目录与权限

envd 以 root 运行；**每个 Agent 对应一个 Linux 用户**，由 agent-runtime 在 spawn 时通过 `/users` 创建（用户名即 agent id，家目录即工作目录）。之后该 Agent 的命令一律 `runuser -u {agent_id} -- bash -lc "..."` 执行。

```
/workspace/                        root, 755
  shared/                          root, 1777（sticky）  任务级共享：仓库、数据集、别人要用的复现脚本
  agents/{agent_id}/               {agent_id}, 755       各 Agent 的工作目录：脚本、输出、证据文件
  agents/{agent_id}/.outputs/      {agent_id}, 755       被截断命令的全文输出
```

| 目录 | 任何 Agent | 目录所有者 |
|---|---|---|
| 自己的 `agents/{id}/` | — | 读写删 |
| 别人的 `agents/{id}/` | 只读 | — |
| `shared/` | 新增文件；读所有文件；**只能删改自己创建的文件** | — |

证据文件放在 Agent 自己的目录即可，`post_fact` 时由系统取走上传 MinIO；MinIO 中的副本才是不可篡改的最终证据。

### 2.4 隔离

| 项 | 设置 | 说明 |
|---|---|---|
| 特权 | 非 privileged；`cap_drop: ALL`，`cap_add: CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, KILL` | envd 需要创建及切换用户，并在超时时向不同 UID 的 Agent 进程组发送终止信号；其余能力全部去掉 |
| 提权 | `security_opt: no-new-privileges` | Agent 进程无法通过 setuid 程序提权 |
| 根文件系统 | **可写** | useradd、apt-get 需要写 /etc、/usr；容器按任务销毁，不需要只读（旧版"只读根文件系统"与此冲突，已删除） |
| 资源 | `cpus`、`mem_limit`、`pids_limit` 按 profile 配置 | |
| 网络 | 默认只接入带网关的`exec`网络，不注入代理变量；容器可直接访问公网。显式代理隔离模式要求`exec`为internal网络，`HTTP(S)_PROXY`指向egress-proxy，由部署级`EGRESS_ALLOWLIST`控制 | 两种模式都不向宿主发布envd端口，控制面token不进入Agent命令 |

生产 runtime 与 envd 同处exec网络，按容器名访问。宿主机开发时使用显式relay模式：每任务增加一个独立的固定目标TCP中转容器，连接默认网络与exec网络，仅把宿主机`127.0.0.1`的随机端口转发到该任务envd:8080。envd不发布端口；中转不支持任意目标、去掉全部capability并启用no-new-privileges。中转随任务一起恢复或销毁，不改变所选出网模式。

### 2.5 生命周期

```
provisioning  agent-runtime 通过 Docker API 创建 exec-env-{task}
              → /health 通过 → 状态 running，调度循环开始（任务相关的环境准备由种子 explore 完成）
closing       所有 Agent 结束 → 终结模式的 close 结束
finished      POST /archive → 上传 minio: workspace/{task}.tar.zst → 销毁容器
failed        conclude 所有 Agent → 同上归档销毁
```

归档排除规则（`archive_exclude`，默认）：`**/.git/objects/`、`**/node_modules/`、`**/__pycache__/`、`**/target/`、`**/*.o`。归档超过 `archive_max_bytes`（默认 2GB）时退化为只归档 `agents/`，并在任务上记录。

ExecEnvManager 接收任务 UUID 和该任务固定版本的 AgentProfile，返回包含容器标识、访问地址与任务 token 的内部 handle。provision 幂等，find/destroy 按完整 task UUID 标签识别资源；短容器名冲突时拒绝复用。启动失败只清理本次创建的资源。归档按块读入临时文件后上传对象存储，避免把整个归档放进内存。

**读时计算**

- `facts.status`：争议图按创建顺序无环。从最新事实往回算：`disputed ⇔ ∃ d ∈ disputers(f): status(d) = proposed`。单次快照 O(n)。
- `facts.relied_by`：`count(g) where g.author <> f.author and f.id = any(g.derived_from)`。
- `dispute_depth`：沿 disputes 链到"根事实"的距离，用于点名深度判断。

### 3.2 对象存储布局（MinIO，bucket `blackboard`）

```
evidence/{task}/{agent}/{sha256[:12]}-{basename}    post_fact 时上传；单文件上限 evidence_max_bytes（默认 50MB）
toolcalls/{task}/{call_id}.txt                        工具调用全文（参数 + 结果）
reports/{task}.md                                     close 报告
workspace/{task}.tar.zst                              任务结束归档
```

`facts.evidence[].path` 保留 exec-env 内的原路径（同任务 Agent 可直接读），`uri` 是对象 key（黑板、UI、后续任务使用）。

### 3.3 事件类型

| type | payload | 触发者 |
|---|---|---|
| `task.created / provisioning / running / closing / finished / failed / stopped` | 状态与原因 | user / scheduler |
| `fact.posted` | fact 全文 | agent |
| `intent.posted` | intent 全文（含是否同时 claim） | agent |
| `intent.claimed` / `intent.released` | {intent_id, holder, note?, counted} | agent / scheduler / system |
| `intent.closed` | {intent_id, result, by: fact_id \| system, reason?} | 派生 / system（attempts 上限） |
| `agent.spawned` / `agent.progress` / `agent.finished` | agent 状态、end_reason | scheduler / runtime |
| `agent.conclude_requested` | {agent_id, reason} · addressed_to=[agent_id] | scheduler |
| `fact.disputed` / `fact.undisputed` | {fact_id, by, depth} · addressed_to=[author]（depth ≤ dispute_notify_depth 时） | 派生 |
| `derive.result` | {posted, excluded} | runtime（据回执） |
| `acceptance.judged` | {verdicts: [{id, verdict, reason, missing, evidence_facts}], mode} | close（submit_close） |
| `acceptance.reverted` | {id, fact_id}：met 项的支撑事实被争议 | 派生 |
| `task.report` | {uri} | close |
| `budget.updated` | usage 快照、是否用尽 | blackboard |
| `tool_call.recorded` | 工具调用记录（含 call_id、agent_id、结果摘要与全文 uri）；参与 fact provenance 判定，重放时恢复 tool_calls | runtime |

派生事件与主事件在同一事务内追加。

### 3.4 验收条件

验收条件是文字，由人在创建任务时给出：

```json
[{"id": "A1", "desc": "给出 502 的直接触发条件，并有可复现的证据"},
 {"id": "A2", "desc": "解释为什么只在高峰期出现"}]
```

每一项的状态保存在 `tasks.acceptance_state`：

```json
{"A1": {"status": "unmet", "reason": "…", "missing": "缺少可复现的触发步骤", "evidence_facts": [], "judged_version": 1830},
 "A2": {"status": "met",   "reason": "…", "missing": null, "evidence_facts": ["F44", "F31"], "judged_version": 1830}}
```

状态只有两种，改变它的途径只有两条：

```
unmet ──close 裁定为 met──▶ met
met   ──close 裁定为 unmet──▶ unmet
met   ──evidence_facts 中任一事实变为 disputed──▶ unmet（missing = "支撑事实 Fxx 被争议"，写 acceptance.reverted）
```

"何时请 close 裁定"由调度器决定（5.2），blackboard 提供判断所需的数据：

| 数据 | 来源 |
|---|---|
| 待裁定的声明 | `facts.satisfies` 非空、version > `last_judgment_version`、且指向的项中有 unmet |
| 黑板是否有变化 | `last_change_version > last_judgment_version` |
| 裁定是否在进行 | `agent_runs` 中存在 running 的 close（mode=judge） |

`submit_close` 写入时：记录 `acceptance.judged`；按 verdict 更新各项状态；`last_judgment_version` 置为该次裁定开始时的 version（`agent_runs.judge_from_version`）。

### 3.5 Agent 配置管理

`agent_profiles` 承载"后端 Agent 编辑"：提示词模板、各任务类型的模型与价格、默认参数、执行环境镜像与资源、privileged 白名单。任务创建时固定 profile 名与版本，运行中不变；UI 可新建版本、对比、回滚。

M1b 的“设为某任务默认”指创建任务时选择 profile 名与版本；未指定版本时使用该名称的最新版本。已有任务不随新版本改变，亦不直接改写其 profile 投影。

加载本地 profile 时读取 `prompts` 指向的三个文件，把正文写入 `prompt_templates`；内容哈希覆盖参数、模型、路径和模板正文。新 profile 版本必须保存完整的三个正文，runtime 按任务固定版本的正文渲染，不能再按路径读取后来修改的文件。这样修改模板正文会产生新版本，已有任务仍保留原模板。

### 4.3 事实写入流水线


## 5. agent-runtime

### 5.1 进程结构

```
agent-runtime
├─ TaskSupervisor        订阅 blackboard 全局事件；task.provisioning → ExecEnvManager.provision → 启动 SchedulerLoop
├─ SchedulerLoop[task]   事件唤醒（去抖 500ms）或每 2s 执行一次 tick；每任务一把 asyncio.Lock，tick 串行
├─ AgentRunner           asyncio task 池：构造 MAF Agent → run() → 回执 → finish
├─ Sweeper               每 30s：心跳超时、宽限超时、收尾等待超时
├─ ExecEnvManager        Docker API：create / health / users / archive / destroy
└─ Recovery              启动时执行一次（5.6）
```

单实例保障：启动时以独立 asyncpg 会话获取固定键的 Postgres advisory lock，拿不到则退出。runtime 从 POSTGRES_HOST/PORT/USER/PASSWORD/DB 获取该连接；此连接只用于锁，不直接写黑板表。会话断开时停止监管与本进程 Agent，避免失锁后继续派发。

### 5.2 决策

```python
async def tick(task_id):
    st = await bb.state(task_id)
    P = st.params

    if st.status == "closing":
        return await drive_closing(st)
    if st.status != "running":
        return

    running  = [a for a in st.agents if a.status in ("running", "concluding")]
    workers  = [a for a in running if a.task_type in ("explore", "derive")]    # 占并发名额的
    judging  = any(a.task_type == "close" for a in running)

    # 1. 失败判定（设计 5.3）
    if st.failure_streak >= P.max_consecutive_failures:
        return await fail(st, "连续运行错误")
    if st.seed_empty_count >= 2:
        return await fail(st, "无法起步")

    # 2. 上限类 conclude
    for a in running:
        if a.status == "running" and a.task_type == "explore":
            limit = P.seed_max_steps if (a.is_seed and not ever_claimed(st, a)) else P.explore_max_steps
            if a.steps >= limit or a.context_tokens >= P.context_threshold:
                await bb.conclude(task_id, a.id, reason="limit")

    # 3. 意图重试上限
    for i in st.intents:
        if i.status == "open" and i.attempts >= P.intent_max_attempts:
            await bb.system_close(task_id, i.id, reason="attempts")

    # 4. 收尾（设计 5.6）
    if all(s.status == "met" for s in st.acceptance_state.values()):
        return await enter_closing(st, reason="accepted")
    if st.explore_budget_exhausted or st.derive_empty_streak >= P.derive_empty_limit:
        return await enter_closing(st, reason="terminated")

    # 5. 裁定（设计 5.5）：与探索并行，不占名额
    quiescent = not any(i.status in ("open", "claimed") for i in st.intents) and not workers
    if not judging:
        if st.pending_claims or (quiescent and st.last_change_version > st.last_judgment_version):
            await spawn(st, "close", mode="judge")
            judging = True

    slots = st.budget.max_concurrent_agents - len(workers)
    if slots <= 0:
        return

    # 6. 种子（设计 5.1）
    if st.board_empty and not workers:
        return await spawn(st, "explore", seed=True)

    # 7. derive（设计 5.4）：探索停下来，且最近一次裁定晚于最后一次黑板变化
    if quiescent and not judging and st.last_judgment_version >= st.last_change_version:
        return await spawn(st, "derive")

    # 8. 为 open 意图创建 explore（设计 5.1）
    for intent in sorted([i for i in st.intents if i.status == "open"], key=priority(st.acceptance_state))[:slots]:
        aid = await bb.register_agent(task_id, "explore", intent_id=intent.id)
        if await bb.claim_for(task_id, intent.id, aid):
            await start_agent(st, aid, "explore", intent.id)
        else:
            await bb.finish_agent(task_id, aid, receipt={"accepted": False, "reason": "claim_lost"}, end_reason="normal")

async def enter_closing(st, reason):
    await bb.set_status(st.id, "closing", reason=reason)
    for a in running_agents(st):
        await bb.conclude(st.id, a.id, reason="closing")

async def drive_closing(st):
    running = running_agents(st)
    if any(a.task_type == "close" and a.close_mode == "final" for a in running):
        return                                                         # 终结 close 进行中
    if running:
        return                                                         # 等其余 Agent 结束（含进行中的裁定；Sweeper 负责超时）
    if not st.final_close_done:
        return await spawn(st, "close", mode="final")
    # 终结 close 已提交：blackboard 已把任务置为 finished
```

终结重试保护：closing 且无活动 Agent 时，若历史 final close 已完成但任务仍未 finished，视为该次终结未完成；按既有 Agent 历史计数（不计 runtime_restart），最多尝试 `max_consecutive_failures` 次，之后任务 failed，原因“终结报告连续未完成”。normal/refused 但未 submit_close 也占一次，避免无效回执导致无限付费重试；不新增计数字段。

`st.pending_claims`：存在 `satisfies` 非空、version 大于 `last_judgment_version`、且指向至少一项 unmet 的事实。

`ever_claimed(st, a)`：有当前 intent_id，或已有意图交接 notes.by 等于该 Agent，或该 Agent 已提交带 resolves 的事实。三者覆盖仍持有、释放、正常关闭的路径；种子首次认领后永久按 explore_max_steps，不会在释放/关闭后重新退回 seed_max_steps，不新增持久化字段。

`priority(acc)`：`relates_to` 含 unmet 项的排前，再按 version。

人工停止由 `/stop` 直接进入上述 closing 流程；不另设尚未定义的 `stop_requested` 数据库字段。HTTP 层发出 closing conclude 后，调度器继续执行 `drive_closing`。

`submit_close` 的后续由 blackboard 处理：裁定模式只更新验收状态（全部 met 时下一个 tick 进入收尾）；终结模式写报告并把任务置为 `finished`。任务到达 `finished` / `failed` 后 TaskSupervisor 负责归档与销毁执行环境。

### 5.3 spawn 与运行

```python
async def spawn(st, task_type, seed=False, mode=None):
    aid = await bb.register_agent(st.id, task_type, is_seed=seed)
    await start_agent(st, aid, task_type, None, mode=mode)

async def start_agent(st, aid, task_type, intent_id, mode=None):
    if task_type == "explore":
        await envd.create_user(st.id, aid)
    agent = make_agent(st, task_type, aid, intent_id, mode)          # 第 6 节
    runner.create_task(run_agent(st.id, agent, aid), name=f"{st.id}/{aid}")

async def run_agent(task_id, agent, aid):
    session = agent.create_session()
    end_reason = "normal"
    try:
        resp = await agent.run("开始。", session=session)
        receipt = parse_receipt(resp.text)                            # 解析失败 → {"accepted": true, "data": {"note": "回执格式错误"}}
        if receipt.get("accepted") is False: end_reason = "refused"
    except asyncio.CancelledError:
        receipt, end_reason = {"accepted": False, "reason": "cancelled"}, "grace_timeout"
    except Exception as e:
        receipt, end_reason = {"accepted": False, "reason": f"runtime_error: {e}"}, "runtime_error"
    await bb.finish_agent(task_id, aid, receipt, end_reason)
```

`finish_agent` 在 blackboard 侧完成：释放仍持有的意图（写 note；`end_reason ∈ {refused, grace_timeout, heartbeat, runtime_error}`，或因上限被 conclude 后仍持有，attempts+1；因收尾被 conclude 或 runtime_restart 不计）；更新 `failure_streak`（runtime_error +1，runtime_restart 保留，其他清零）；种子结束且黑板仍为空、且不是 runtime_restart 时 `seed_empty_count+1`；derive 结束时据回执写 `derive.result` 并更新 `derive_empty_streak`。

### 5.4 Sweeper

| 检查 | 动作 |
|---|---|
| running 且 `now - last_heartbeat_at > heartbeat_timeout` | 取消其 asyncio task；finish（end_reason=heartbeat） |
| concluding 且 `now - conclude_requested_at > grace_timeout` | 取消其 asyncio task；finish（end_reason=grace_timeout，note="系统强制释放，持有者未完成交接"） |
| 任务 running 且超过 `max_minutes` | 标记探索预算用尽（下个 tick 进入终结收尾） |

### 5.5 任务结束

`finished` / `failed` / `stopped`：先为剩余 running Agent 补 conclude（失败任务 reason=failed），独立清理协程等待交接至原始宽限截止时间，超时取消并等待 finish，再归档上传，调用服务身份 `POST /api/tasks/{id}/archive` 写入 `task.archived` 事件（`uri=workspace/{id}.tar.zst`、`size`、`fallback`），投影更新 `workspace_uri`，最后销毁容器。接口验证终态、没有活动 Agent、对象存在与任务 key；相同 URI 重复登记幂等。归档/登记失败保留容器，后续 tick 重试；已持久化 URI 后可直接重试销毁。尚未创建容器的 stopped 排队任务跳过归档。清理和等待销毁的容器仍占任务容量；清理独立运行，不阻塞其他任务的监管轮询。终态任务禁止再次登记 Agent；同终态迁移幂等，不能从一种终态改写为另一种终态。这样归档完成后不会因迟到派发产生新写入。黑板仍是唯一领域写入口。

### 5.6 重启恢复

agent-runtime 启动时：

1. 对所有 `running` / `concluding` 的 agent_runs：finish（end_reason=`runtime_restart`，**不计 attempts**）。重启中断也不记种子空产、不清零既有 failure_streak；即使旧 Agent 已因 limit 进入 concluding，runtime_restart 仍不计 attempts。Agent 的 MAF 会话在内存中，无法恢复；未提交的工作丢失，已提交到黑板的全部保留。
2. 对 `provisioning`：没有容器表示仍在排队或尚未成功创建，保留 provisioning 等待可用槽位；有容器则检查健康并接管。对 `running` / `closing`：检查任务容器是否存在且健康，存在则接管，不存在或不健康则 failed（工作区已丢失或不可用，已持久化证据仍在）。provision 本身负责清理失败的新资源。
3. 恢复 SchedulerLoop。任务列表必须读取所有分页；运行中和 closing 的任务占用任务并发槽位，排队按创建时间先后处理。

## 6. Agent 构造（MAF）

### 6.1 组装

```python
from agent_framework import Agent, MCPStreamableHTTPTool

def make_agent(st, task_type, aid, intent_id, mode=None):
    m = st.profile.models[task_type]
    P = st.params
    client = make_client(m)
    client.function_invocation_configuration["max_iterations"] = P.explore_max_steps + P.conclude_grace_calls + 5
    client.function_invocation_configuration["max_duration_seconds"] = (st.budget.max_minutes + P.grace_timeout + 1) * 60

    tools = make_board_tools(st, aid, task_type)                  # 6.2
    if task_type == "explore":
        tools.append(MCPStreamableHTTPTool(
            name="exec",
            url=f"http://exec-env-{st.id}:8080/mcp",
            static_headers={"X-Agent-Id": aid, "Authorization": f"Bearer {st.exec_token}"},
        ))

    return Agent(
        client=client,
        name=aid,
        tools=tools,
        context_providers=[OpeningContextProvider(st, task_type, aid, intent_id, mode)],   # 7.1
        middleware=[
            ToolLogMiddleware(st.id, aid),        # function，最外层
            GraceGateMiddleware(st.id, aid),      # function
            BoardSyncMiddleware(st.id, aid),      # chat：持久追加增量、心跳、记账
        ],
    )
```

同类中间件的执行顺序由 M2a 验证。运行期不再依赖 MessageInjectionMiddleware 队列，避免增量跨轮丢失以及最终回执后因排队消息而额外调用模型。

`post_fact` 的执行顺序（Agent 自行判断重复后直接提交，工具负责证据持久化）：

```python
@tool(approval_mode="never_require")
async def post_fact(kind: str, statement: str, evidence: list[EvidenceIn],
                    derived_from: list[str] = [], disputes: list[str] = [],
                    resolves: str | None = None, result: str | None = None) -> str:
    """提交一条事实。Agent 已自行判断重复；evidence[].path 是执行环境内的文件路径。"""
    for ev in evidence:
        st_ = await envd.stat(ev.path)                         # 不存在 → 返回错误说明，不写黑板
        if st_.size > P.evidence_max_bytes: return "证据文件过大，请截取相关部分另存后再提交"
        data = await envd.read_file(ev.path)
        ev.uri = await store.put(f"evidence/{task_id}/{aid}/{sha12(data)}-{basename(ev.path)}", data)
        if ev.call_id:                                         # 自动附上系统记录的命令与输出
            evidence.append(auto_evidence_from_toolcall(ev.call_id))
    return render_result(await bb.post_fact(task_id, ..., token=agent_token))
```

终结报告保护：同一 close Agent 的 submit_close 工具调用串行执行；final 每次上传固定报告 key 前重新读取任务状态，只有 closing 才允许写入，已 finished 时不改写报告。黑板在任务行锁下拒绝同时登记多个活动 close Agent（包括 judge/final），使固定 key 的报告只有一个活动提交者。失败的尚未发布报告允许后续有效终结重试覆盖；已发布的报告不会因重复模型工具调用被覆盖。

所有工具的返回都是给模型读的简短文本（成功：对象 id + 一句说明；失败：原因 + 怎么改）。

`reasoning_effort` 按任务类型在 profile 中配置（默认 explore / derive / close 均为 high），通过每次运行的 options 传入。v1 所有任务都用 `deepseek-flash`；如果 M5 发现裁定准确率不足，可以只把 close 换成 `deepseek-v4-pro`，改 profile 即可。

**DeepSeek 用量适配**：MAF 1.19 的默认解析丢弃 DeepSeek 顶层缓存命中/未命中字段，且非流式响应不保留原始响应。使用 OpenAIChatCompletionClient 的最小子类 DeepSeekChatClient，在 `_parse_usage_from_openai` 中保留父类标准字段并补齐 DeepSeek 的缓存命中/未命中计数；该兼容点由锁定版本与传输回归测试守护，不保存整份原始响应。

**请求有界**：MAF 的函数循环 `max_duration_seconds` 只在模型请求之间检查，不能中断正在等待的请求。客户端另设每次 HTTP 请求超时为 `min(120, max_duration_seconds)` 秒，保留 SDK 默认两次重试；运行器与 MAF 循环的总硬时限均为 `(任务 max_minutes + grace_timeout + 1) * 60` 秒：为探索预算后的交接保留完整宽限，另留一分钟覆盖清扫/调度间隔。该时限只是故障兜底，超时按 runtime_error 收尾；调度器仍在任务 max_minutes 时立即进入 closing，Sweeper 按 conclude 时间决定交接截止。单请求超时仍不超过 120 秒。

**记账**：`BoardSyncMiddleware` 从每次调用的 `usage_details` 取 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`（含推理），按 profile 价格表换算金额，累加到 agent_runs 与 tasks。预算按金额判断（设计文档 3.1）。

### 7.2 增量同步：`BoardSyncMiddleware`（ChatMiddleware）

```python
class BoardSyncMiddleware(ChatMiddleware):
    def __init__(self):
        self.conclude_injected = False  # 每个 Agent 独立实例；重启后旧 run 会结束

    async def process(self, context: ChatContext, call_next):
        run = await bb.agent(task_id, aid)
        if run.task_type == "explore":
            events = await bb.events(task_id, since=run.last_seen_version, for_agent=aid)
            lines = [render_full(e) for e in events if e.addressed_to]
            digest = [e for e in events if not e.addressed_to and e.type in DIGEST_TYPES and e.actor != aid]
            lines += [render_counts(digest)] if len(digest) > P.delta_max_lines else [render_line(e) for e in digest]
            if run.conclude_requested_at and not self.conclude_injected:
                lines.insert(0, render_conclude(run.conclude_reason, P.conclude_grace_calls))
                self.conclude_injected = True
            if lines:
                append_board_update(context.messages, "[黑板更新]\n" + "\n".join(lines))
            last_seen = max_version(events, default=run.last_seen_version)
        else:
            last_seen = run.last_seen_version
        await call_next()
        usage = context.result.usage_details if context.result else None
        await bb.heartbeat(task_id, aid, steps_inc=1, usage=usage,
                           context_tokens=usage.get("input_token_count", 0) if usage else 0, last_seen_version=last_seen)
```

`append_board_update` 修改最近一条工具结果的公开 Content.result；没有工具结果时修改已有起始 user 消息的 Content.text，保留原文本并追加有边界的黑板增量。M2a 的三轮真实 MAF（脚本模型）工具循环验证增量持续可见、各出现一次；不操作 SDK 私有历史，也不重复追加已见版本。

`DIGEST_TYPES = {fact.posted, intent.posted, intent.closed, fact.disputed, fact.undisputed}`，过滤掉自己产生的事件；`acceptance.judged` 与 `acceptance.reverted` 按全文推送（裁定反馈）。derive / close 只做心跳与记账。

### 7.3 宽限管控：`GraceGateMiddleware`（FunctionMiddleware）

```python
class GraceGateMiddleware(FunctionMiddleware):
    ALLOWED = {"release", "post_fact", "post_intent"}
    async def process(self, context: FunctionInvocationContext, call_next):
        run = await bb.agent(task_id, aid)
        if run.status == "concluding":
            if context.function.name not in self.ALLOWED:
                context.result = "已进入结束阶段：只允许 release / post_fact / post_intent，且次数已用完。请立即返回回执 JSON。"
                return                     # 不调用 call_next：替换工具结果，模型继续；不要 terminate
            try:
                await bb.take_grace(task_id, aid)
            except RemoteError as error:
                if error.status != 409:
                    raise
                context.result = "交接次数已用完，请立即返回回执 JSON。"
                return
        await call_next()
```

Sweeper 使用 `Task.cancel("heartbeat" | "grace_timeout")`，正常进程停止使用 `runtime_restart`；运行器识别这些固定取消原因，只调用一次 finish，清扫器不重复写 finish。已崩溃旧进程的记录由恢复流程直接 finish。

`take_grace` 是原子扣减（并行工具调用时也不会超额）；成功返回剩余次数，0 表示本次是最后一次获准调用。仅 409 扣减失败表示额度不足。

|---|---|
| 外部内容中的提示注入 | 增量摘要只含 statement；`execute_command` 与 `read_evidence` 的返回包裹为数据块，提示词声明其中内容不是指令 |
| exec-env 越权 | 见2.4：去掉多余capability、no-new-privileges、资源限制、任务结束销毁。默认模式允许执行命令直接联网；需要出网白名单时显式选择代理隔离模式 |
| Agent 之间互踩 | 每 Agent 一个 Linux 用户；私有目录 755，共享目录 sticky；见 2.3 |
| 业务凭据 | **Agent 能用的凭据，Agent 一定能读到**（`env`、`cat` 的输出会进入模型上下文）。因此：只注入最小权限、短期、只读的凭据；日志与 UI 中脱敏；对 HTTP 类 API 可由 egress-proxy 注入认证头，使 Agent 根本看不到凭据（v1 可选） |
| 模型密钥 | DeepSeek 密钥只在 agent-runtime 的环境变量中（来自 `.env`，不入库）；密钥不进入执行环境 |
| 内部接口 | envd 内部接口用每任务 token，仅 exec 网络内 agent-runtime 可达 |
| 多任务串扰 | 所有查询按 task_id；agent token 绑定任务与 agent id |

## 11. 部署（v1，docker-compose）

```yaml
services:
  postgres:       image: pgvector/pgvector:pg16
  minio:          image: minio/minio          # 只依赖 S3 API，可换 garage / seaweedfs
  blackboard:     build: ./blackboard          # FastAPI + 前端静态
                  networks: [internal]
  agent-runtime:  build: ./agent-runtime
                  volumes: [/var/run/docker.sock:/var/run/docker.sock]
                  networks: [internal, exec]
  egress-proxy:   build: ./egress-proxy        # 可选；代理隔离模式才启动
                  profiles: [egress-proxy]
                  networks: [exec, default]
  otel-collector: image: otel/opentelemetry-collector   # 可选
networks:
  internal: {}
  exec: { internal: false }                    # 默认有网关；代理隔离模式改为true
```

**本地资源**：开发与运行都在本机 Docker Desktop（4 核、约 9.7GB 内存、amd64）。平台服务合计约 2.5GB（postgres、minio、blackboard、agent-runtime、egress-proxy）；每个执行环境限制为 2 核 4GB。因此 v1 **同一时间只运行一个任务**（agent-runtime 配置 `max_running_tasks=1`），任务内最多 5 个 Agent 并发——Agent 大部分时间在等模型返回，占用的是执行环境里的命令，不是模型本身。

`exec-env-{task}` 由 agent-runtime 运行时创建并接入 `exec` 网络。不接受挂 docker.sock 的话，用 Docker socket proxy 限制到 create/start/stop/remove/exec，或改用 gVisor / 远程执行服务。

默认模式下exec-env直接出网，`egress_allowlist`只记录任务期望访问的域名，不提供访问控制。若部署者显式选择代理隔离模式，则必须同时将exec网络设为internal，并启动egress-proxy；原有全局`EGRESS_ALLOWLIST`继续控制代理可访问域名，任务字段不会动态改变该列表。可信runtime同时接控制网络与exec网络，可直接访问模型服务；需要宿主代理时用独立RUNTIME_HTTP_PROXY/RUNTIME_HTTPS_PROXY注入其进程，内部黑板/envd HTTP客户端不读取这些代理变量。

## 12. 演进路径

| 阶段 | 内容 |
|---|---|
| **M1 黑板** | blackboard + postgres + minio：对象、事件、校验、快照、增量、搜索、验收状态机；脚本模拟写入；画布可见 |
| **M2 执行环境 + 单 Agent** | exec-env 镜像与 envd；agent-runtime 跑一个种子 explore；打通 MCP、中间件、消息注入、证据上传、回执 |
| **M3 调度** | 完整调度循环、预认领、conclude、宽限、Sweeper、失败与重试保护、derive、close（裁定 / 终结）与裁定触发、归档销毁、重启恢复 |
| **M4 工作台** | 详情、证据查看器、时间轴、Agent 面板、验收与报告、Agent 配置页 |
| **M5 评估** | 已知答案任务回归：命中率、耗时、token、争议率、裁定通过率；调参数 |
| **后续** | agent-runtime 按任务拆分；exec-env 迁到独立主机或 k8s（envd 接口不变）；模型网关；Temporal 替换派发；人工在黑板上直接提交意图 |

## 13. 待验证与风险

1. **中间件顺序**：同类中间件在列表中的先后与执行内外层的对应关系；BoardSync 必须先于 MessageInjection。M2 验证。
2. **消息注入对上下文长度的影响**：注入的增量是否计入后续每次调用（应当计入），`context_threshold` 是否据此及时触发。M2 验证。
3. **单工具是否够用**：只有 `execute_command` 时，二进制与大文件处理都靠 shell；观察 M2 的实际使用。
4. **close 裁定的可靠性**：LLM 裁定可能过宽或过严；M5 用已知答案任务统计裁定准确率，必要时对 close 使用不同于 explore 的模型。
5. **验收规则表达力、快照裁剪、Agent 自主判断重复**：M5 验证。
6. **MinIO 版本**：社区版功能收缩，只用 S3 API；备选 Garage。
