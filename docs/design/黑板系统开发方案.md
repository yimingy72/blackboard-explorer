# 黑板式探索系统 · 开发方案

> 依据：《黑板式探索架构设计.md》（概念与规则）、《黑板系统实现架构.md》（容器、数据、接口）。本文回答：代码怎么组织、按什么顺序做、每一步做到什么程度算完成、怎么测试、有哪些风险要先排除。

---

## 0. 范围与开发条件

**产品定位**：通用问题求解引擎。核心协作、调度和裁定不绑定代码审查或任何单一领域；领域资料与完成条件由任务输入提供。

**v1 目标**：在本机 Docker 上跑通完整闭环，并能衡量效果。软件诊断与非代码数据核对均作为回归场景；现有mini-shop评分器是一个特定任务的评测适配，不定义平台能力边界。固定Profile不得预置该任务的答案或类别检查清单。

```
创建任务 → 种子 explore → 多个 explore 并发 → satisfies 触发裁定 / 探索停下来触发裁定
       → 不通过：反馈推给探索者、derive 补意图 → 通过：收尾报告 → 归档
全过程在工作台画布上实时可见；用一个带标准答案的评估任务衡量召回率、精确率、耗时与成本
```

**v1 不做**：多机 / k8s 部署、模型网关、Temporal、多租户与细粒度权限、按任务的出网白名单（默认直接出网；显式代理隔离模式使用全局白名单）、人工在黑板上直接提交事实或意图（接口预留，UI 不做）。

**已确定的开发条件**

| 项 | 决定 | 影响 |
|---|---|---|
| 模型 | DeepSeek `deepseek-flash`（V4.1-Flash，1M 上下文），explore / derive / close 统一使用 | 用 MAF 的 `OpenAIChatCompletionClient` 接 DeepSeek 的 OpenAI 兼容接口；已实测工具调用可用 |
| 重复判断 | Agent 根据启动快照与增量黑板信息自行判断 | 无本地 embedding 模型、向量列或相似度确认流程；关键词查询辅助定位原文 |
| 部署 | 本机 Docker Desktop（4 核、约 9.7GB 内存、amd64） | 同一时间只运行一个任务，任务内最多 5 个 Agent 并发 |
| 仓库 | `/Users/yym/blackboard-explorer`（M0 第一步创建） | — |
| 评估 | 自建评估任务"mini-shop 变更审查"（7.2） | M5 前需要先把评估目标系统做出来 |
| 开发方式 | 一人 + AI 协作开发 | 按检查点推进，不按人日排期（第 5 节） |
| 预算单位 | 金额（按 DeepSeek 价格表，区分缓存命中、未命中、输出） | 长驻 Agent 的输入大部分命中前缀缓存，按 token 计会严重高估成本 |

## 2. 开发原则

1. **契约先行。** 所有跨服务的数据结构只在 `contracts` 中定义一次；blackboard 导出 OpenAPI，前端从中生成类型；`openapi.json` 做快照比对，接口变化必须显式更新快照。
2. **规则集中在纯函数里。** 黑板的写入规则、争议状态、验收状态、快照裁剪，以及调度器的决策，都写成"输入状态 → 输出结果"的纯函数，用表驱动测试覆盖。数据库、网络、Docker 只出现在外层。
3. **调度器拆成 `decide(state) → actions` 与执行器。** 实现架构 5.2 的伪代码在代码里是一个纯函数，返回"创建 explore(I4)""conclude(agent-3)""进入收尾"之类的动作列表；执行器负责调用接口。每条调度规则都能在不启动任何服务的情况下测试。
4. **不依赖真实模型也能测试整个系统。** `ScriptedChatClient` 按脚本返回工具调用和文本，并能对注入的消息做出反应（例如看到 conclude 就 release 并返回回执）。真实模型只用于端到端与评估，控制花费。
5. **每个里程碑都有可演示的结果。** 不做"最后才集成"的开发。
6. **文档与实现一致。** 实现中发现设计需要改，先改设计文档，再改代码。
7. **评估任务与开发隔离。** 开发和调试只用玩具任务（7.1）；评估任务（7.2）只在 M5 使用，避免把提示词调成"只会做这一道题"。

## 3. 测试策略

| 层 | 覆盖范围 | 工具 | 运行时机 |
|---|---|---|---|
| 单元 | 黑板写入规则、争议递归、验收状态机、快照裁剪、调度 `decide()`、回执解析、模板渲染、金额换算 | pytest | 每次提交 |
| 集成 | blackboard API + Postgres + MinIO；envd 在真实容器中（用户隔离、超时、截断） | pytest + testcontainers | 每次提交 |
| 场景 | agent-runtime + 真实 blackboard + FakeEnvd + ScriptedChatClient，跑完整任务生命周期（M3 场景表） | pytest | 每次提交 |
| 端到端 | docker-compose 全栈 + DeepSeek + 玩具任务 | `make e2e` | 里程碑检查点、改动提示词或中间件后 |
| 评估 | 评估任务，统计召回率、精确率、耗时、成本 | `make eval` | M5 起；每次改提示词或参数后 |

**两个测试替身**

- `ScriptedChatClient`：实现 MAF 的 chat client 接口。脚本由若干步组成，每步是"返回这些工具调用"或"返回这段文本"，可以带条件（"如果收到的消息里包含 conclude 指令，则跳到交接步骤"）。它记录每次被调用时收到的完整消息列表，用于断言注入是否生效；可以返回与 DeepSeek 相同结构的用量字段，用于测试记账。
- `FakeEnvd`：实现 envd 的 MCP 与内部接口，命令执行用预设的输出表，文件读写落在临时目录。场景测试用它避免启动 Docker。

**场景测试**（ScriptedChatClient 驱动，全部必须通过）

| 场景 | 验证点 |
|---|---|
| 顺利完成 | 种子 → 3 个并发 explore → satisfies 触发裁定 → 全部 met → conclude 其余 Agent → 终结 close 写报告 → finished → 归档 |
| 裁定不通过 | 裁定 unmet → 反馈推到运行中的 explore → 探索停下来 → 再次裁定 → derive（输入含反馈）→ 新意图 → met |
| derive 两次为空 | 第二次 derive 收到第一次的排除理由 → 终结收尾，报告列出未满足项 |
| 有毒意图 | 同一意图 3 次未关闭就释放 → 系统关闭为 inconclusive，不再派发 |
| 模型不可用 | 连续 3 个 Agent 以运行时错误结束 → failed，归档完成，不创建 close |
| 种子空产 | 两个种子结束时黑板都为空 → failed |
| 认领竞争 | 种子 `claim=true` 与调度器预认领同时发生 → 无重复持有，失败方正确处理 |
| 宽限超时 | conclude 后 Agent 不返回 → grace_timeout 后强制结束、释放、写入系统 note、attempts+1 |
| 预算用尽 | 探索预算（金额）耗尽 → 终结收尾，终结 close 用预留预算仍能运行 |
| 支撑事实被争议 | met 项回到 unmet → 后续重新裁定 |
| 裁定期间有新声明 | 裁定运行时出现新的 satisfies → 合并到下一次裁定，不并发两个裁定 |
| 重启恢复 | 运行中重启 agent-runtime → 进行中的 Agent 记为 runtime_restart，意图重新派发，attempts 不变 |
| 人工停止 | 停止 → 终结收尾 → 报告 |

**检查点**：场景全部通过；你在工作台创建玩具任务并启动，DeepSeek 跑通完整闭环，产出报告与归档，画布上能看到全过程。

### 7.1 开发用玩具任务：order-service 偶发测试失败

**评分**

| 指标 | 计算方式 |
|---|---|
| 召回率 | 找到的植入问题数 ÷ 6。"找到"= 定位（文件与函数）、机制、可复现证据三项齐全；只有定位和机制计 0.5 |
| 精确率 | 有效发现 ÷ 报告的全部问题。报告了 D1–D3 必算误报；植入列表之外的发现由你人工复核，确有问题算有效 |
| 证据可复现率 | 在全新执行环境中重跑报告里的复现脚本，结果与报告一致的比例 |
| 接口覆盖 | A2 列出的接口是否覆盖分支改动的全部接口 |
| 耗时、花费 | 从启动到 finished 的时间；金额与缓存命中率 |
| 过程指标 | 争议数、satisfies 声明命中率、裁定次数、各 Agent 结束原因分布 |

评分脚本先按文件与函数名、关键词把报告中的发现与 P1–P6 自动匹配，再由你复核匹配结果与植入列表之外的发现。

**运行方式**：多 Agent 与单 Agent 基线各跑 5 次（模型输出有随机性，单次结果不可靠），报告平均值与最差一次。

**判断标准**：多 Agent 的平均召回率比单 Agent 至少多找到 1 个问题，或召回率持平但耗时明显更短，才算达到设计目的。否则先分析原因再迭代。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| MAF 行为与预期不符 | M2 实现方式需要调整 | 第 6 节前置验证，每项都有退路 |
| 同一个模型既探索又裁定，可能倾向于认可自己的结论 | 过早结束 | M5 统计裁定准确率；不足时只把 close 换成 `deepseek-v4-pro`（改 profile） |
| 模型不遵守提示词（工具用法、回执格式、质量门槛） | 探索质量下降、回执解析失败 | 回执解析容错；工具返回的错误说明写清"怎么改"；M2 用玩具任务观察 |
| 思考模式的推理 token 按输出计费 | 成本高于预期 | 按任务类型调 `reasoning_effort`；M5 统计每任务花费；预算按金额兜底 |
| DeepSeek 限流或响应慢 | Agent 卡住、心跳超时 | 客户端重试与退避；`heartbeat_timeout` 留足余量 |
| 本机资源（4 核、约 9.7GB） | 执行环境内跑测试或服务时资源紧张 | 同一时间一个任务；执行环境限制 2 核 4GB；必要时调大 Docker Desktop 内存 |
| 执行环境的安全边界 | 越权、外泄 | 非root Agent、去掉多余capability、控制面密钥不下发；默认直接出网，需白名单时选择代理隔离模式 |
| agent-runtime 挂载 docker.sock | 权限过大 | 使用 Docker socket proxy，只开放容器的创建、启动、停止、删除 |
| API 密钥已出现在对话记录中 | 泄露风险 | 只写入 `.env`；如有顾虑，项目开始后在 DeepSeek 控制台重新生成一个 |
| 多 Agent 相对单 Agent 没有收益 | 方向需要调整 | M5 基线对比；优先分析原因再加功能 |
