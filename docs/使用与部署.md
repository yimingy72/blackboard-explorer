# 使用与部署

本页描述当前 `main` 的本地运行方式。项目是通用问题求解引擎，黑板式多 Agent 是协作机制。设计规则以 [`docs/design/`](design/黑板式探索架构设计.md) 为准；历史测试结果和阶段性限制见 [HANDOFF](HANDOFF.md) 与对应任务报告。

## 准备与启动

在仓库根目录执行。复制 `.env.example` 为 `.env`，自行设置数据库、对象存储、服务令牌、`ADMIN_USERS` ；模型凭据在平台页面保存；不要提交或分享 `.env`。如果 runtime 访问模型需要宿主机代理，在 `.env` 配置 `RUNTIME_HTTP_PROXY` 与 `RUNTIME_HTTPS_PROXY`。下面的构建需要 Docker 和已安装的 uv、pnpm。镜像下载或构建需要宿主机代理时，按本机网络情况为命令单独设置代理；这些变量不会自动赋予执行容器代理出网。

```sh
UV_CACHE_DIR=/private/tmp/bbx-uv-cache uv sync --locked
make web-install web-build
make image-exec-env image-agent-runtime image-blackboard
docker compose --project-name blackboard-explorer up -d --wait
```

工作台地址是 <http://127.0.0.1:58000/login>，登录凭据来自你配置的 `ADMIN_USERS`。以上为基础服务，使用自建目标的公网地址时无需启动仓库内的评测目标。`make up` 只执行基础 `docker compose up -d`，不构建镜像，也不启动开发叠加文件。

### CTF 团队模式专用部署

`bbx-ctf-team-mode` 使用独立的执行网络，不能只依赖主 `.env` 中的 `EXEC_NETWORK`。构建后通过仓库内的运维入口启动；入口会固定项目名、主工作树 `.env` 路径和 `docker-compose.ctf-team-mode.yml`，不会修改或打印 `.env`：

```sh
make web-build image-exec-env image-agent-runtime image-blackboard
docker tag bbx-blackboard:latest bbx-ctf-blackboard:latest
sh scripts/deploy_ctf_team_mode.sh up -d --wait
```

该入口固定 `EXEC_NETWORK=bbx-ctf-team-mode_exec`，并同步固定 Compose 顶层 `exec` 网络名；后续重建 agent-runtime 仍使用相同配置。不要使用不带该 override 的同项目 Compose 命令替换 runtime。

任务创建页可选黑板探索或CTF团队，创建后模式固定。CTF由Lead协调具名队友、复用各自Session；题目记录用于交接证据和增援，定向消息可直接送给任何成员。画布默认占满工作区，点击Agent进入连续会话，点击题目查看概览/记录/文件；详情可以拉伸和关闭。验证记录只读展示，不提供人工确认或调整要求的入口。系统重启仅初始化缺失的默认配置，已经保存的平台设置保持；修改模板需通过配置页显式保存。

CTF 的队友数是成员上限，实际同时获准的模型调用还受预算预留限制。暂时占额时成员保留同一回合等待，结算后继续，不会反复生成中断回执；等待仍计任务活动时间，停止任务可以中断等待。永久不足以容纳下一次调用时预算收尾。模型响应丢失且费用尚未确认时，平台不会复用同一预留再次发起调用，未知费用保留为占额，后续恢复沿用原流程。调度、会话与隔离验证详见 [CTF 协作优化报告](tasks/CTF-cooperation-report.md)。

CTF 模板在 Agent 配置的 CTF 配置页编辑，用于之后创建的任务。Lead 根据依赖拆分工作并登记 owner/协作者后派工；成员按已有 Session 和信息缺口读取记录，及时共享关键发现。已接受派工的最终结果由系统通知，普通成员提问需要显式回信，纯通知无需确认。内建工具的版本冲突会提供当前 revision 和刷新建议，仍需读取最新题目后决定如何更新；不会自动覆盖。记录工具和 HTTP 查询支持可选 after_version，分页期间保持该值不变并沿 next_offset 读取；下一组增量使用已完整读过的最高 created_version、offset 归零。详细边界见 [系统提示与工具报告](tasks/CTF-prompts-tools-report.md)。

长 CTF 任务中，已保存的大工具输出可能在模型视图中显示头尾预览，原始会话与工具配对不删除；无法缩减的用户输入会给出上下文阻塞。控制链短暂断开先重试，同一已提交派工不会重复建立回合。全队静默时以五秒巡检、六十秒冷却提醒 Lead，三次无题目/记录进展后部分完成收尾；不自动确认旧 deferred 消息或恢复停止成员。显式续跑开始新的提醒周期。

CTF 创建请求中的 `ctf_options.max_steps/context_threshold` 会写入有效任务快照并实际生效；省略步数时继承所选配置，省略阈值且模型窗口已知时使用该窗口，显式超窗报错。阈值以 token 为单位，实际输入另外预留输出空间和一次安全余量。长工具结果的模型预览第一次生成后固定，新增结果不改写旧预览；历史超限时一次批量裁剪，MAF 原生分组保护工具与推理配对，完整 Session 仍保留。上下文封锁后新回合依据目标和黑板恢复，每成员每轮最多一次自动恢复；步数到限最多自动续跑三次，金额、时长和停止边界继续有效。新用户消息会返回恢复请求或封锁状态，显式续跑开启新一轮恢复额度。见 [缓存与长任务恢复报告](tasks/CTF-context-recovery-report.md)。

已明确识别的瞬时模型故障只结算受影响成员的回合，再以2/4/8秒退避最多自动恢复三次；其他成员继续工作。次数和退避跨服务重启保留，显式续跑才重置；耗尽后通知Lead，不自动重复未知工具或清零未知费用。封锁恢复兼容旧空消息ID，旧未确认输入保留为deferred，取消/移除的成员与消息不复活。发送前新增批次跨窗口时，只能裁已提交且准确映射的完整旧历史，当前输入及未知工具保持；无法安全裁剪仍明确阻挡。owner/Lead可以在`record_candidate`显式传`work_status`原子保存交付，已有可信验证不会被Agent候选覆盖。见 [Run3独立审查与修复](tasks/CTF-run3-hardening-report.md)。

“预算不足”可能表示已入账估算加未确认占额后，不足下一次最坏预留，并不等于供应商已经扣完预算。平台先依据已确认 Session 的用量幂等对账；缺少可信用量的未知结果仍保留。报告分别列估算与占额，并给逐题记录、卡点和证据索引；平台 accepted、候选和外部答案字符串匹配需分开理解。详见 [批量评测复核报告](tasks/CTF-batch-hardening-report.md)。

需要使用仓库内置目标时，先构建素材并叠加开发 Compose：

```sh
make eval-targets
docker compose --project-name blackboard-explorer -f docker-compose.yml -f docker-compose.dev.yml up -d --wait
```

`eval-targets` 在执行网络中提供内置目标素材。当前目标和选择方法见 [评测目标](../eval/targets/README.md)及[评测任务](../eval/tasks/README.md)。

## 从任务到报告

1. 登录后在“新建任务”填写简短任务名、完整目标、领域资料和可检查的完成条件，可添加初始附件，再选择任务模型、推理强度与人民币预算。任务名可省略，旧任务以目标摘要展示；完整目标在工作台顶部“目标”中就地展开。强度默认沿用模型配置，也可仅为这个任务选择；三Worker共用该任务的固定选择，不改平台模型默认或旧任务。DeepSeek及其兼容/Responses连接可选择low/high/max；“模型默认（不传参数）”沿用接口默认行为。自建目标的地址、访问约束和操作边界应写入任务资料；不要假设 Agent 能从其他任务继承这些信息。
2. 启动任务后，在工作台查看 Agent、Fact、Intent、关系和事件。Fact 是 Agent 提交的发现，仍需结合证据核对；它不会因文字相似而被代码自动丢弃。各 Agent 根据同步的黑板信息自行判断是否重复。
3. Explore 可以声明目标已满足，调度器据此安排 Close；只有 Close 的裁定会改变任务的完成状态并生成报告。若证据不足，报告应说明缺口。任务结束后可以查看报告和任务归档；归档完成后可通过“续跑任务”追加预算和时长，保留原黑板与会话；目标和验收范围变化时建议新建任务。

初始附件每个最多50 MiB，最多20个、总计200 MiB。同名文件按不同文件ID保存，启动前恢复到 `/workspace/shared/inputs/<file-id>/<filename>`；工作台顶部“目标”的附件入口可查看路径并下载原件。上传不自动解压、执行或生成Fact。需修改时先复制到自己的工作目录或其他共享路径；原件即使未被Fact引用，也保留在必要文件归档和续跑恢复中。创建任务仍需手动点击启动，上传和创建不会调用模型。

上传失败可重试或移除，创建结果未确认时重试同一冻结请求，避免重复建任务。附件组24小时未绑定即过期，点击“重新上传附件”可保留当前草稿并重传；离开创建页会取消未绑定组，清理失败及遗留对象由后台每5分钟分批重试。已绑定文件不可从上传接口改写；删除任务才会清理对应输入与存档。

任务页标题下方显示已持续时间。状态行下方设分割线，下一行同时显示结束原因与运行统计；验收理由和缺口可从目标节点详情或裁定历史查看。图谱展示当前版本的全部对象，不提供筛选或自动折叠；右下角保留紧凑缩略图。事实和意图的详情正文使用 Markdown 排版，路径、命令和代码块可清晰阅读。常驻 Agent 条显示该任务的所有 Agent，从 1 独立编号，已结束者也保留；点击条目或拓扑中的 Agent 可打开右侧对话记录。新运行会保存初始上下文、黑板注入、模型返回内容与工具调用；长内容按需展开并可下载。模型未返回推理文本时不生成替代内容。旧任务只展示已保存的工具调用和回执，并标明上下文未记录。

## 网络模式与排障

### 模型连接短暂中断

真实模型connection/timeout错误在SDK重试之外可从同一Agent检查点有界恢复。恢复期暂停新探索/推导/普通裁定派发，使用现有Agent请求作为单一恢复探针；每Agent本次run累计最多两次额外恢复，固定120秒窗口内2/4秒退避。Agent对话记录显示连接恢复，工具不会由框架自动重放；完整成功可解除暂停，持续故障仍会终止。清扫、人工停止和收尾继续，等待仍计活动时长。永久请求、认证、余额、内容审核以及会话/控制HTTP错误不走该恢复路径；恢复不保证长时间断网下无限运行。

### 任务内 sudo 与共享环境

每任务一个 Ubuntu，普通命令按 Agent 用户运行。新建容器中的所有 Agent 均可免密 `sudo -n`；`execute_command(..., privileged=true)` 兼容为该 Agent 经 sudo 执行整条 shell 命令。旧 `privileged_allowlist` 字段保留数据兼容，不再是权限控制开关。执行容器移除 `no-new-privileges`，保留 Docker 默认 capabilities 并增加 NET_ADMIN、挂载 `/dev/net/tun`，支持任务内安装工具及 VPN/TUN 等操作；relay 仍保留其原有限制。没有增加高权限辅助容器，不开放宿主网络或 Docker socket。

`/workspace/agents/agent-N/` 放工作文件，`/workspace/shared/` 放共同使用的资料；不增设 private 目录。共享文件需要修改时先复制到自己的工作目录，验证后另存成果并发布 Fact。普通用户权限用于防止互相误改，sudo 能越过这一限制。软件、进程和网络共享，变更前应核对已有工作，完成后及时同步黑板；不要覆盖他人文件或重复修改公共路由。

envd 保存命令开始、结束、超时及取消记录，sudo 原生记录保存调用用户、目标用户、目录、命令和退出状态。命令与返回值仍通过平台工具记录持久化；结束归档前将本轮原始审计保存到 `toolcalls/<task-id>/runtime-audit-run-<N>.txt`，任务归档 `.bbx/task.json` 的 `runtime_audit` 及清单引用该对象，删除任务时一并清理。sudo shell/脚本记录的是该次提权及退出，并非其中每条子命令；容器日志不保证抵抗 root 主动篡改。

更新镜像和 agent-runtime 后，新任务或显式续跑创建的新容器使用新能力。已有容器不会就地提权；旧容器没有审计接口时归档明确标记 `legacy_runtime`，容器已丢失且没有已保存审计时标记 `runtime_missing`。审计读取或上传失败会保留容器以供重试，不假装归档成功。

### 出网模式

默认配置是 `EXEC_EGRESS_MODE=direct`、`EXEC_NETWORK_INTERNAL=false`：新建的 Ubuntu 执行容器经 Docker 网关直接访问外部地址，不注入 `HTTP_PROXY`/`HTTPS_PROXY`。任务表单里的 `egress_allowlist` 在此模式只记录需求，不限制连接。执行容器仍保留独立用户、文件权限和内部控制接口鉴权。宿主机用于拉镜像/下载依赖的 `127.0.0.1:7897`，以及 Agent runtime 访问 DeepSeek 时可设置的 `RUNTIME_HTTP_PROXY`/`RUNTIME_HTTPS_PROXY`，都不决定执行容器的出网方式。Docker Desktop 上，runtime 的宿主机代理地址通常写为 `http://host.docker.internal:7897`。

只有确实需要部署级白名单时，才切换到 `EXEC_EGRESS_MODE=proxy`、`EXEC_NETWORK_INTERNAL=true`，在 `.env` 中设置 `EGRESS_ALLOWLIST`，构建可选代理镜像并启用其 Compose profile：

```sh
make image-egress-proxy
docker compose --project-name blackboard-explorer --profile egress-proxy -f docker-compose.yml -f docker-compose.dev.yml down --remove-orphans
docker compose --project-name blackboard-explorer --profile egress-proxy -f docker-compose.yml -f docker-compose.dev.yml up -d --wait
```

先结束仍在运行的任务，再切换模式并重建网络；不要在已有任务的执行容器上期待设置即时生效。上述 `down` 不带 `-v`，保留 PostgreSQL/MinIO 数据卷。没有使用内置目标时，可去掉两处 `-f docker-compose.dev.yml`。从代理模式切回直连也需要带 `--profile egress-proxy` 执行 `down --remove-orphans` 清理旧代理容器，再把 `.env` 改回直连设置并按基础模式 `up`。白名单由部署级 `EGRESS_ALLOWLIST` 决定，任务字段不会动态更新它；代理细节见 [egress-proxy](../services/egress-proxy/README.md)。

可用 `docker network inspect blackboard-explorer_exec --format '{{.Internal}}'` 核对执行网络：默认直连为 `false`，代理隔离为 `true`。若看到代理返回的 `403 Filtered`，检查是否启用了代理模式和部署级白名单；直连模式下的 HTTP 403 也可能是目标服务自身响应。`Network is unreachable` 先检查执行网络是否为 internal、容器是否在预期网络和目标路由是否可达。已有终态任务的报告不会因改配置而变化；可显式续跑原任务或新建任务重试。

## 检查与评测

```sh
make check              # 静态检查与普通测试；假模型，无 DeepSeek 费用
make test-integration   # Docker 集成测试；不调用真实模型
```

`make test-integration` 会按 Makefile 构建测试需要的镜像，包括可选代理镜像；这不表示日常运行必须启用代理。`make e2e`、`make eval-run`、`make test-live` 和工作台真实任务会请求 DeepSeek，产生费用。显式端到端命令、任务参数及保留复盘工作台的方法见 [Agent runtime](../services/agent-runtime/README.md)；批量评分见 [评测运行器](../eval/runner/README.md)。`single` 是单 Explore 并发的调度配置，仍使用黑板与 Close，不能当作完全没有黑板的单 Agent 架构。历史 E1/E2 样本使用旧网络与旧 Profile，不能与当前默认直连配置直接比较。

## 按 Agent 查看贡献与复盘

Agent 标签上显示其创建的 Fact、Intent 数量，并用相同颜色标识这些对象的节点背景和作者。认领他人的意图不会改变该意图的创建者颜色。点击 Agent 后，可展开“产出”定位对象，从会话“更多操作 → 运行信息”查看耗时、调用数与 token；数量只表示已提交记录。需要事件、裁定历史、时间轴或工作区时，点击顶部“更多任务操作 → 复盘记录”。Fact/Intent 的阅读排版会整理旧正文的编号条目和长段落，点击“原文”查看或复制存储的原始文字。


## 与 Agent 对话和删除任务

点击 Agent 标签或节点，在右侧输入框发送消息；Ctrl/⌘+Enter 可发送。运行中消息将在下一模型轮次送达，长命令或当前模型请求不会被输入立即中断。任务结束后仍可在同一处继续只读问答，复盘模型费用单独记录。历史回放视图不可发送，返回实时后即可继续。

新版本启动的 Agent 自动持久化原生 Session；旧任务可基于已有记录建立 legacy 复盘会话，界面会说明原会话未保存。仅查看页面不会调用模型，发送消息才会请求模型。会话一直保留到删除任务。

在任务列表点击“删除”，确认后清理该任务的黑板、全部会话、消息、证据、报告与归档；运行中需先结束任务。删除中的任务会显示“删除中”，清理异常由后台重试，不应手工删数据库行或清空所有数据卷。


## 直接配置 Worker 与任务模型

配置页不展示历史版本、default/single名称、内部连接标识或浏览器默认。进入Agent配置后直接选择explore、derive、close，编辑完整系统提示词和工具，点击“保存并应用”。保存会检查模板语法和变量，409表示其他操作已更新配置，当前草稿保留，应重新读取后合并修改。

系统提示词在运行Agent下一次模型调用前生效，不打断在途模型请求或命令，不清空聊天历史，不重跑工具；更新正文及内部revision记入Session和trace。全局调度、模型与执行环境快照保持固定；续跑时可选择把当前 Worker 工具设置固定到新执行轮次。结束后的复盘仍受只读指令约束，不自动继续探索。

“模型配置”中只需填写显示名称、Provider、厂商模型ID、相应连接参数和人民币价格，内部标识自动生成。Provider表单由MAF Python支持目录驱动，云服务按需填写AWS凭据、Azure服务主体或Google服务账号JSON，所有敏感内容仅写入平台加密存储，不回显；编辑时留空保留。服务不需要认证时可不填。已有DeepSeek环境密钥由runtime启动时一次性导入，导入不会覆盖用户已保存的凭据，不需要在聊天或前端重新暴露密钥。

模型“上下文大小（token）”可留空，留空沿用全局交接阈值（默认128000）。填写后，新任务以该容量80%作为Explore交接和Derive下一轮分段阈值，留20%给输出及黑板增量，例如500000对应400000。请按服务商真实容量填写，此设置不能扩大模型容量，也不保证任意长度的工具结果都不会超限。原生Profile使用不同角色模型时取最小显式容量。已有任务与续跑保留原阈值。

点击模型的“设为默认模型”会保存平台默认值，跨浏览器有效。新建任务选择模型，预选平台默认；提交固定用户看到的模型版本，三种worker共用该任务模型。之后修改默认模型不切换已经创建任务的模型。历史账本保持原币种，新模型价格统一填写CNY。

支持OpenAI Chat Completions/Responses、Azure OpenAI两协议、Microsoft Foundry、Foundry Local HTTP、Anthropic及Foundry/Bedrock/Vertex托管端点、Ollama、Amazon Bedrock、Gemini/Vertex、Mistral，另保留DeepSeek和OpenAI兼容接口。MAF Python不提供.NET清单里的ONNX/Dapr客户端，不把这些列为可运行选项。Foundry Local只连接现成服务，不在Ubuntu容器下载模型。服务使用原生SDK的认证要求不同；实际云端连通性需对应账号资源与授权，本项目离线测试不替代各账号实际认证。

MCP管理支持Streamable HTTP；连接从服务容器发出，宿主机服务地址应使用host.docker.internal。读取工具清单只初始化和列工具，不执行业务工具。Explore可选多个服务及工具白名单，derive/Close保留受限角色权限；MCP提示词加载和采样关闭。

费用提供“固定费率”和“DeepSeek 官方峰谷时段”两种估算方式，后者仅适用于官方端点与已知模型，按请求开始时间使用对应费率。高峰为北京时间周一至周五9–12时、14–18时（中国节假日除外），闲时为高峰的一半；上方录入的费率是高峰还是闲时由复选框声明。当前节假日日历覆盖2026年，其他年份工作日峰时保守使用高峰价，需更新日历。历史任务保留固定模式直到显式校正，不自动换汇。Anthropic与Bedrock的缓存读写单独计入输入总量，缓存写入目前按未命中输入单价估算；如需账单精确对账，应以供应商账单为准。加密key由AGENT_TOKEN_SECRET派生，备份需保留该服务端密钥，直接替换会使旧平台凭据无法解密。平台配置公开接口、Profile快照和事件不含明文凭据。


## 完成前推导复核

只有明确目标范围、直接完成证据充分且无关键未验证事项时，Close才能声明completion_basis=explicit并记录完成理由，从而允许不启动derive直接收尾。其余情况先完成现有方向，静止后由derive复核，再由Close再次裁定。复核产生新Intent会回到探索；无新方向须说明排除理由，不能用空回执冒充通过。图谱/Agent列表将此类derive显示为“完成复核”，目标详情可看明确完成依据。

新事实、意图或争议变化会使旧复核失效；预算、时间、人工停止仍优先于继续探索。关闭“主动并行推导”不关闭必要复核。single参数仍仅限制一个Explore，但必要derive/Close仍参与，历史评估的“无derive”口径不再适用于新版。


## 续跑与费用校正

Explore 应及时把复现脚本、必要输入和依赖逐个作为 Fact 附件登记：`post_fact.evidence` 的 `type`、`path`、`summary` 均必填。只在事实正文、意图或命令中提到路径不算登记；系统不按扩展名或正文路径自动收集。未登记的下载包、缓存、镜像展开内容和扫描临时文件不会保留，也不应为凑归档范围登记整个临时目录。任务结束后，系统将黑板、会话和已登记文件按任务及运行轮次保存到 MinIO，然后销毁该任务的 Ubuntu 容器。旧版全量工作区归档仍可读取和下载；新归档只包含已登记的必要文件以及任务元数据。

任务页终态显示“续跑任务”。填写追加金额（人民币）与分钟数；它们增加原预算，不重置已有消耗。剩余执行资源须足够且归档/容器清理已完成，处理中的复盘消息会暂时阻止续跑。暂停间隔不计入已持续时间。表单可选采用当前 Worker 工具设置；模型、目标和验收条件保留原值。续跑使用新 Ubuntu 容器，只恢复已登记的必要文件；运行依赖、系统安装包及进程需重新建立。旧报告/归档按轮次保留；删除任务才清理该任务的所有轮次存档和会话。

平台不自动重跑已结束任务，也不会因只读复盘消息重开执行。默认不自动修改历史估算：管理接口 `GET /api/tasks/{id}/cost-reconciliation` 预览按官方峰谷规则重算；`POST` 携带 `expected_version` 应用并记录 `cost.reconciled` 审计事件。仅可对终态、用量事件齐全的官方DeepSeek任务校正；原token/事件不变，后续续跑沿用已选择的时段规则。历史调用若缺少请求开始时间，按用量事件时间估算，跨时段边界可能有差异。估算不等于供应商实扣，网络中断丢失响应用量时也无法代替账单。

## 看图与证据阅读

在平台模型选择图片输入能力，在对应Worker工具列表启用view_image。Explore可看`/workspace`图片；derive、Close及结束后的复盘仅可看本任务持久证据。支持PNG/JPEG/WebP、单图10MiB，不下载本地视觉模型。MAF统一图片消息传给所选模型；Bedrock当前适配器及DeepSeek V4 Pro不接受图片，其他模型仍需厂商实际支持。

大证据通过read_evidence的offset/limit分页读取，默认16,000字符、最大32,000；页面提示总长和下一偏移。模型get默认只读指定对象，需关联时传depth=1。完整文件和模型对话历史保持可回溯。

## CTF 团队的上下文与故障收尾

团队模式的上下文阈值以 token 为单位。输入硬预算为 `min(context_threshold, context_window − max_output_tokens) × 0.8`，固定提示和工具 schema 也计入其中。例如窗口 1,000,000、最大输出 393,216 时，阈值 400,000 得到 320,000 输入预算；阈值取 606,784 或整个窗口均得到 485,427，不能同时预留最大输出又使用满窗口输入。平台不自动增大已保存任务的阈值。

模型输入达到硬预算的 90% 时尝试安全裁剪，60% 为理想目标而非必须达到的条件。已确认的纯文本派工可完整保留在稳定恢复前缀；完整 Session 不删除，工具调用和结果仍按 MAF 分组保护。真正无法容纳的新输入仍阻挡，并保存原因、估计值和可得的末次真实单次用量。每成员每轮最多一次自动上下文恢复；耗尽会通知 Lead，停止或重派前先盘点既有记录与产物，显式新指令不重置恢复额度。

耗尽通知和闲置提醒包含有界的阻塞分支、可裁范围、估计输入、硬上限及延期消息 ID。Lead 可用已有 `confirm_messages` 确认仍适用的 queued/deferred 输入；cancelled 消息不能复活，因上下文阻塞保护的原输入也不能仅靠确认重放，需发一条较小的新指令。新指令和成员 stop/resume 不重置额度；显式任务续跑才进入新的 run。

CTF 配置页更新的是 `ctf`。默认新任务取它的最新模板，再叠加所选模型和请求选项，创建不可变的 `ctf-task-settings` 快照；历史任务保持旧版本是正常机制。若运维需同步可复用的任务配置，使用下面的只读预览，复核版本后再带 `--apply` 与两个预期版本发布。工具复用 ProfileStore 的事务及 CAS，保留两个家族各自的模型、工具、价格、资源和其他参数；只有明确指定的目标阈值及模板变化。下列容量数字适用于保存的 1,000,000 窗口、393,216 输出预留，不是所有模型的通用值。显式创建请求仍指定 400,000 时继续尊重该值；想使用模型可用容量可省略阈值，或明确设为 606,784。

```sh
docker exec bbx-ctf-team-mode-blackboard-1 /app/.venv/bin/python \
  -m bbx_blackboard.ctf_profile_publish \
  --task-context-threshold 606784 --reserved-output-tokens 393216
```

已结束任务的旧活动阻塞标记可通过 `bbx_blackboard.ctf_context_cleanup` 预览，再用 `--apply --task-id <UUID>` 清理；不传 task-id 时仅筛选终态 closed 的任务。清理持锁检查执行/复盘回合及成员操作，转存原诊断历史并记录审计事件，不改会话、消息、恢复计数或完成结论。正常保留的空 `{}` 不算残留。两项运维命令均在已配置的 blackboard 环境内运行，不读取 `.env`，错误输出不包含私有 SQL 参数。验证与本地发布记录见 [上下文未关闭项修复报告](tasks/CTF-context-unclosed-fix-report.md)。

最后 checkpoint 未确认时，收尾采用退避；达到八次普通重试或六十秒后，在写者退出及远端 drain 已确认的前提下，标记系统失败收尾。已保存会话、未知费用预留、本地未确认快照和容器保留，清理显示失败，需修复后才可归档与显式续跑。未确认 drain 或数据库不可用时低频等待，不以销毁环境或假定成功来消除故障。

黑板控制连接短暂断开时，回合读取会有界重试，结算保留原回答和结束原因；一次故障不会取消其他成员。`finish_turn` 的写入结果未知时只读回核对，不重建整轮模型/工具。该成员存在未确认结算或保存时暂不领取新回合，其他成员仍可运行。持续错误仍明确升级，4xx、本地协议及参数错误不当成可无限重试的故障。错误记录包含任务、成员、回合、代次与追踪 ID，不含请求体或凭据。

停止操作按真实执行代次排空，另记录实际结算的回合身份；快速恢复成员也不能使旧回执覆盖新回合。envd 已登记但黑板绑定写入未确认时先对账，空黑板绑定不是排空证明。复盘领取丢应答只能重签原回合 token，过期证明不新建孤儿回合；目标复盘结算恢复须本地写者退出且保存/用量/观测已确认，保留原回答与会话，未确认时低频等待。

普通黑板模式也保留启动成功的执行环境与原最终回执证据。最终回执存入原生 Session，按任务轮次、Agent 身份和 derive 轮次补偿；清扫或重启不会用心跳超时结果覆盖已有最终回执。历史 review 用量按原已保存调用对账，不归入新复盘回合。相关故障注入与审查范围见 [回合传输修复](tasks/CTF-turn-transport-fix-report.md) 和 [控制链扩查](tasks/CTF-control-audit-report.md)。

## CTF 团队交流优化补充（2026-10-14）

CTF 的 `update_challenge` 可在 `assign` / `collaborators` 时附 `instructions`（每项为 `recipient_id`、`body`），在同一事务授予分工权限并派工；成功后无需重复 `send_message`。仅更新任务板仍可不附指令。释放题目等重新可调度变化会向 Lead 发短通知，回合结果附实际自动恢复决定。

CTF Worker 配置可选择 `read_turn_result`、`read_saved_tool_result`，Lead 另可选择 `list_deferred_messages`。它们读取已结算派工回执、本成员保存的工具结果或待确认输入元数据，支持分页，不重执行工具或读取队友私聊。原配置与历史任务快照不自动改变；启用后用于之后创建的任务。

观测查找使用迁移 `0015` 的部分索引；CTF checkpoint 成功只回小回执，完整会话及响应丢失读回保持。旧恢复前缀只凭正常完成与交付证明退役一次性输入，不删除原会话，也不释放未知命令或费用。流内明确瞬态码复用原有界恢复；未知、审核或鉴权失败不自动当成瞬态。事故与验证细节见 [团队交流审查报告](tasks/CTF-team-communication-audit-report.md)。

后续性能轮增加迁移 `0016` 的邮箱序号和共享记录索引。工具按当前 turn 的执行/复盘用途单次授权，仍读取固定 Profile 并受原白名单限制。调度使用现有 SSE 的控制事件唤醒及最长两秒补偿扫描，观测不会触发调度风暴；CTF 通知在同一事务提交后才可见。MCP 使用公开 MAF 生命周期在每个 run 内复用连接，目录按任务和权限隔离缓存；每次 build 仍核验配置与凭据，断连不会重发原工具调用。完整历史、原有预算及停止语义保持；这些优化无需改写现有模型或 Worker 配置。

## CTF 题目进展与解题流程（2026-10-14）

题目节点使用单一题名和带图标的状态标签。`已交付` 表示负责人提交了本轮工作，只有工作状态完成且存在可信、非模拟的平台或用户成功结果时才显示 `已解出`；候选文本、模拟通过和任务终态不会自动升级状态。

题目详情分为概览、解题流程和文件。概览显示成员、Agent 登记的题目说明、负责人工作结论和技术进展；创建、分配和纯状态变化位于折叠的派工动态。解题流程由负责人或明确署名的 Lead 整理，包含思路、关键尝试与取舍、真实突破（如有）、结论、未解项和复现入口；记录及附件引用可以回读。旧任务没有结构化流程时继续显示历史共享记录，不自动补写。

新的 `append_record.progress` 用于短进展标题和摘要。正常把题目更新为 `completed` 时，`update_challenge` 或 `record_candidate` 必须在同一次调用附 `solution`；服务在同一事务保存总结记录、候选、证据和工作状态，并校验负责人、题目 revision、执行代次以及同题记录/附件引用。重开题目会清当前总结指针，旧流程保留为上一轮结论。取消、预算耗尽或异常停止沿用原收尾，不因缺少正常交付流程而阻塞。

CTF Profile revision 15 只在 revision 14 的 Lead/teammate 提示词末尾追加题面保真、及时进展和流程交付规则；模型、工具、MCP、费用、上下文、并发和执行配置未变。新建任务采用新版本；历史任务仍使用创建时固定的 Profile。
