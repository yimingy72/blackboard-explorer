状态：内部审查通过，入口修复及离线、隔离对照检查通过，现场恢复单独留证。基线 `601c19bae570c3f4f44bd23bc5d26be2f2e8506b`；原暂存区为空，已有工作改动 102 项（30 已跟踪、72 未跟踪）已独立保留。当前授权包括排查和必要的修复及本地恢复；不重发原保存，不采集或输出真实密钥。

## 1. 现场与根因范围

用户在原生 AgentGateway 添加提供商时看到保存错误。原生存储现有 1 个提供商、0 个模型；已有两个消费者的维护保护同属原请求与原代次。现存原生部署有同请求的滚动注解，服务已同步；有落库与滚动请求证据，但此前响应丢失，不能仅凭提供商存在就断定原提交内容或旧错误的具体阶段。固定版 Provider 集合和单项 PUT 均返回同一种资源响应，原生 Provider API 与现有匹配形状无静态冲突。

现有入口的成功流程为：原生认证 → 两站空闲保护 → 转发唯一一次原生修改 → 在原存储上滚动 → 单次读取运行状态与存储原记录 → 双站精确解锁。一次可恢复的端点错误或同步迟滞就会跳到不确定状态，两个消费者保持锁定。日志不区分这些阶段。隔离环境将用实际固定版 AgentGateway 验证故障点；如果旧请求没有可用历史证据，报告只确认可复现的漏洞，不把它冒充旧请求的精确诊断。

## 2. 修复范围

- 仅改现有原生管理入口，保留原生管理界面、配置单源、两站空闲保护、同一存储与原生资源的匹配、密钥与结构写限制。每次请求仍最多转发一次原生 PUT/DELETE，最多发一次原生部署滚动 PATCH；异常回执不能触发重发。
- 已知成功的原生修改和已确认的同存储滚动之后，在同一有界时间内重试暂时失败的运行状态和原生资源 GET。只在观察到运行同步、并且读回与原生成功响应完全匹配时释放原请求。仍然未知时保留维护保护。记录无密钥的阶段、原因和请求关联 ID，不记任何原生请求、响应、认证值或客户端报文；不增设通用维护平台、自动解锁任务或后台重写。
- 恢复本地原有未知操作是一次限定处置：确认旧入口进程/请求已退出，两个消费者仍是精确原请求与代次且无活动或不确定调用；比对原生 Deployment/PVC、原滚动标记、已同步的原进程及当前原生资源语义摘要。用连续一致的当前配置作为新基准，只对两站释放同一个原请求，核对释放回执和前后摘要。保留用户 Provider 和现有密钥；无原生写、无重新输入、无真实上游请求。若证据不闭合，保留维护保护。此处置不追认历史 UI 保存成功，也不证明提交意图。
- Core 负责入口的产品修复、必要离线测试、任务文档和最终提交。Runtime 负责隔离复现及受控的本地部署与历史处置。独立审查确认实际症状、故障边界、恢复证明及最终差量。

## 3. 验证

1. 对固定版原生 Provider 保存接口提交一次页面同形请求，受控注入重启完成后的暂时读取故障；应仅通过原生 GET 重新确认，前端收到原生成功响应，双站解锁，原生版本只前进一次。负例：永久失败或不一致读回应保持维护保护；失败写入或不确定写入不可重发。
2. 离线检查有界读取重试、记录阶段且无配置值、严格拒绝不一致/读回失败。提交前运行一次 `make check`。不运行真实模型。
3. 已有请求恢复前后核对双站、原生存储、用户资源与本地既有部署；现场只读检查原生 Provider 页面、两个消费者目录及既有权限。记录原请求能否释放、当前资源是否保留和未完成边界；不把模型尚未配置当作平台不可用。
