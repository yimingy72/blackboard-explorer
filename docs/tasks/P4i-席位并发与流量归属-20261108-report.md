基线 `51c798ca021479793c125b37f21227209a550810`。本片用真实 PostgreSQL 验证同一个 Task 的 20 个共享席位，并在新 Task 可选的 `binding-pcap-v1` 上完成逐 binding 的隔离、采集、原始对象归档、授权解析和只读查看。Lead 不占这 20 席。命令审计仍只读。

真实 PostgreSQL 发出 18 个主 Assignment，让两个不同的原父并发借完两席，验证满位即时拒借、领取结果未知的原 helper 保留席位。明确未启动的另一个 helper 有原关闭回执后，ready 主任务优先取得同一席位，新 binding/generation 只发一条 prepare。另一项验证分别覆盖新作用域领取、采集未就绪不能发 SDK、原 ready/permit 后只准入一次、原段摘要/写入确认、授权下载和未知写入拒绝清理。32 是原 epoch 全历史 binding 的恢复 manifest 上限；PG 验证达到 32 时 helper 拒新增，主派工仍可继续并保持单次 prepare。该实证不代表 20 个模型、真实命令或 Pod 同时运行。

新 profile 的每个 `exec_command` 使用当前 binding 的独立 netns、原 veth、IPv4 和已确认就绪的采集器。文件工具不创建网络作用域。冻结的数值 IPv4 TCP 白名单与双向逐包内核 grant 一起限制流量；原授权受 owner、binding/父 binding、子期限及 Task 截止限制。精确原镜像的探针验证了已建立双向连接按时失效、旧授权不重开且另一独立来源保持有效。内核单调窗口另有保守 UTC 截止，使用要求包括可信节点时钟。PCAP 取原 veth 的 SNAT 前观察，每源 classic Ethernet PCAP，snaplen 512 字节，至多 7943 包和 4 MiB，截断或缺口明确保留。它不证明目标收到包或包属于某条命令，也不覆盖 loopback、IPv6、DNS、真实 VPN、TLS 解密和 HA。原共享 `worker-a` 来源保持原协议与显示。
