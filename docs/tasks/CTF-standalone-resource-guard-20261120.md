# 独立 CTF 比赛版：扩容与卡死保护

本文件细化[独立比赛版方案](CTF-standalone-20261120.md)第 5 节。用户已确定初始 10 个同级 Worker，Lead 可以查看资源并创建更多 Worker，同时要求避免扩容过多拖死容器。本轮只给出实现合同，没有修改产品代码、提交或进行故障注入。

## 1. 最小结构

只需要一个本地协调器、两条执行队列和一个轻量监督进程：

- 协调器管理 Worker 人数、工作归属、资源采样和准入预约。
- 模型队列按实际供应商/凭据协调在途请求与退避；工具队列管理本地高消耗命令。两者都可以并行，不绑定为“一个 Worker 占一个 CPU”。
- 监督进程在 Node 宿主之外检查主控心跳并负责受管进程收尾；不参与求解、不调用模型、不新增 Agent。

团队初始记录和目标人数为 10。会话准备和后续模型激活仍走同一准入路径；准备失败的 Worker 显示为未就绪，不伪报 10 人都已经开始求解。没有工作时不为这些会话发起模型回合。

每题 10 人上限、每人 3 条 Intent 持有上限、三个在线题目环境名额分别保留。它们不是全局 Worker 总数上限。自动援助先使用现有空闲成员，团队不足时通知 Lead 决定增员。

## 2. Lead 请求与实际创建

建议对 Lead 暴露两个窄工具，名称可在正式合同中统一：

| 工具 | 最小输入/输出 |
| --- | --- |
| 资源查看 | 返回采样序号和年龄、容器 CPU/内存/磁盘、就绪/忙碌/待命/准备中人数、模型与工具队列、当前准入状态及主要原因 |
| 增员 | 输入 `request_id`、`target_total`、工作理由；返回已就绪人数、准备中人数、目标人数、暂未创建数量和原因 |

用目标人数而不是“再加 N 人”。同一 `request_id` 不同内容为冲突；重复请求同一目标、不同请求同时要求同一目标，都不会重复增加人数。降低目标不自动删除已有 Worker，删除能力不从增员权限推导。

Lead 看到的资源快照不构成创建许可。实际准入如下：

1. 本地采样器每秒读取一次资源。采样超过两秒没有更新时停止新增，保留当前执行；不拿旧的空闲截图继续扩容。
2. **Worker 准备和高消耗工具启动共用同一准入串行区及预约账本。** 模型请求造成的显著内存增长也计入预算。不能让三条通道各自看见同一份剩余内存后同时花掉。
3. 在短串行区内重读最新采样、已有预约、实际已建人数和待准备人数，计算本次可接受数量，先写入预约与准备记录，再离开串行区进行 SDK/进程 I/O。
4. 同时只允许一批 Worker 准备。第一轮可每批 2 人；该批全部就绪或失败、且至少取得一份更新的资源采样后，才判定下一批。批大小是压测参数，不是总人数上限。
5. 失败只回收本批尚未生效的预约并记录原因；已成功准备的成员不重复创建。不得把仍在准备中的成员当作空闲可分配者。
6. 新采样尚未覆盖启动消耗时保留预约，避免进程已启动但监控尚未反映的窗口。长期工具的预计后续增长也要保留；不能一看到 PID 就将全部预约释放。

人数更新、预约与幂等结果落在短 SQLite 事务里；会话准备、外部请求和工具执行不持数据库写锁。取消准备或超时后先确认准备实例结束，再释放其预约。

## 3. 资源预算与暂停/恢复

以容器实际 cgroup 配额为准。预期值为 4 核、6 GiB；没有读取到可靠配额或资源采样时不继续加人。不能使用宿主机的总 CPU 数、总内存或空会话均值来算可开人数。

准入预算包含：当前容器用量、未兑现的启动预约、在途模型请求和工具后续增长、主控保存/退出所需余量。已经体现在采样中的消耗不能长期重复记账；具体预约释放点必须可观测。没有工具峰值样本时，先单独校准该类高消耗工具，再放大其并发，不给未经测量的命令按“零成本”放行。

以下是**首次组合压力测试的起始参数**，不能称为已验证的生产阈值：

| 信号 | 新增准入 | 恢复/后续处理 |
| --- | --- | --- |
| 容器内存达到 80%，或预算不足以覆盖新增动作和余量 | 暂停增员与新高消耗工具；不杀正在正常工作的成员 | 低于 70%、无持续内存压力且连续稳定 10 秒后，每次只恢复一批 |
| 内存继续接近硬限额、出现持续 PSI/分配压力或快速增长 | 暂停额外模型发送；优先保存状态、处理已有回执；定位增长来源 | 先卸载已确认 idle 会话的缓存；仍恶化时取消确实异常增长的受管工具，保留失败记录 |
| Node 事件循环明显恶化并持续，例如连续三次秒级采样延迟超过 500 ms | 暂停扩员，减少新请求与大输出处理 | 延迟恢复到正常区间并持续稳定后恢复；一次尖峰不重启 |
| CPU 达到配额 | 单独此信号不暂停或杀进程 | 结合工具排队、throttling、事件循环及有效吞吐决定是否继续增加重工具 |
| 模型 429/超时集中出现 | 由对应供应商队列统一退避，暂停该路由的新请求 | 遵守 `Retry-After`，错峰逐步恢复；不通过创建新 Worker 绕开拥塞 |
| 磁盘可用空间低于预留 | 暂停增员及新的大文件/大输出作业 | 清理明确可再生的临时数据或完整处理其失败，不删除已引用证据和未决回执 |

内存判断至少同时记录 `memory.current`、`memory.stat` 中的匿名内存/文件缓存/脏页、`memory.events` 与可读的 PSI；可选指标不存在时明确降级。**文件缓存高不等于进程泄漏。** 高位可以使新增暂缓，但不能单凭一次 clean file cache 增大就取消工具或重启。也不能简单从用量中扣掉全部 file cache：脏页和写回中的页不是立即可回收空间。压测时据实际回收行为校准高水位。

恢复使用低于暂停线的阈值和稳定窗口，避免来回增员/收缩。恢复时不一次释放全部积压请求。CPU、内存和模型网络是不同瓶颈，不采用一个“系统繁忙”布尔值决定全部通道。

已加入的忙碌 Worker 不因方向减少或一次高负载被突然删除。idle 会话允许保存同一个 session ID 和完整日志后卸载内存；恢复时仍是原成员和会话，不重置 `has_worked`、模型历史或工作来源。

## 4. 工具、输出与磁盘

Node 宿主只负责协调，数值计算、编译、解压和分析运行在本地子进程。命令使用独立 cwd/env，不修改整个宿主的 `process.chdir` 或 `process.env`。常见 BLAS/OpenMP/JVM 等参数应按工具实际支持情况配置；不能声称一个环境变量能限制所有程序。

执行接缝优先使用已安装 Pi SDK 的 `BashOperations.exec(command, cwd, { onData, signal, timeout, env })` 和 `spawnHook`：在薄 operations 包装中接入准入、调用记录、输出落盘与取消，在 spawnHook 中设置本次命令的 cwd/env。无需重写整套工具，也不再绕回远端 Sandbox。已核对 SDK 本地 backend 会创建 detached process group、跟踪 PID，并在 abort/显式 timeout 时调用进程树清理；但 **timeout 默认未设置**，它也没有本方案要求的持久 PID 恢复账本和全局输出预算。

以当前 SDK 1.5.0 的实际实现为准：`OutputAccumulator` 保留有界显示尾部，超过阈值后将原始输出写入临时文件；`bash.js` 的 `STRUCTURED_OUTPUT_MAX_BYTES = 1024 * 1024` 将程序化 `structuredContent.output` 限在 1 MiB，并在截断时返回完整输出文件路径。类型注释中的“程序化 output 不同于模型展示限制”不能解读为无限缓存。首版复用这些既有能力，不再造全部输出处理，也不预先剥掉原始数据。

仍需补的是全局临时文件/磁盘预算、慢盘背压与输出风暴检测，以及输出文件的任务/工作代次归属。显示尾部和返回值有界，不代表所有会话合计的落盘量或慢盘写入积压已经受控。应以快生产者/慢存储的测试确认原管道和写入队列行为，再在薄执行接缝中暂停新准入、调节生产速率或取消失控作业；不能只将同步 `onData` 回调改成异步就假定调用方会等待。保留 SDK 的原始文件路径与截断信息，最终登记实际保存范围。

每个受管工具保存运行代次、command ID、PID/进程组及启动时间、预期输出目录。进程退出、超时、资源取消和传输未知分别记录。工具输出持续写文件，内存只保留有界展示/模型摘要；管道必须持续排空，不能因停止读取 stdout 把子进程卡住。

按实际挂载点使用 `statvfs` 监测空间，不能用宿主磁盘空间代替赛事可写额度。首轮为状态、回执和清理预留至少 512 MiB，并结合在途作业剩余输出预算判断是否准入。需要验证平台 10 GiB 配额能否从文件系统直接观察；观察不到时以已核实配额和容器内写入记账补充，不能将大宿主盘误认为无限空间。

临时下载、缓存和未引用的中间结果与不可变证据分开目录管理。可以清理已经确认可再生的临时文件；不自动删除引用中的文件、会话和未决提交记录。达到输出预算时明确截断展示或取消相应作业，并记录实际保留范围；不将截断输出冒充完整证据。SQLite WAL 的 checkpoint/回收应在可控时机执行，避免磁盘持续增长且无人管理。

## 5. 主控失联与恢复

watchdog 必须独立于 Node 事件循环。Node 用单调递增计数写入当前运行代次的心跳；正常工具耗时不妨碍主控心跳，模型长期等待也不直接算主控挂死。

首次参数可采用 1 秒心跳、连续 30 秒未推进才进入失联处置。该值明显大于当前合成样本的约 208 ms 最大事件循环延迟，但还需要真实组合负载校准。一次 GC、集中日志写入、CPU 满载或工具暂时没有 stdout，都不满足主控失联条件。

处置顺序固定：

1. 停止新准入，记录失联原因；先向当前宿主发送正常结束请求并给短暂收尾机会。
2. 按受管运行代次、PID 和启动时间确认旧宿主及工具身份，必要时结束对应进程组。不能只按数字 PID 杀进程，更不能使用全容器 `pkill`。
3. 确认旧执行已结束后才启动新宿主，避免两个协调器同时写同一黑板或重复发出工具调用。启动记录与实际 PID 之间的异常窗口必须纳入测试；未确认清理时不得宣称安全释放。
4. 新宿主打开原 SQLite 和会话日志，保留原 attempt、deadline、session ID、候选、工作代次及 `has_worked`。先核对未决提交/命令，再恢复可确认的工作。
5. 重启使用退避；连续故障时停止无意义的快速重启并保留诊断状态。容器启动异常、模型超时或主控重启均不得顺手调用赛事 `finish`。

watchdog 只负责本容器受管执行，不恢复旧平台的分布式租约、外部控制面或多宿主高可用架构。外部赛事重新创建整个容器后能否恢复，取决于其挂载保留合同，不能仅靠本方案承诺。

## 6. 验证与实现边界

已有父代理样本是在隔离 4 核/6 GiB 容器中运行固定 SDK 1.5.0：64 个少量历史会话结束时 RSS 约 139.5 MiB；64 个每人 4 MiB 合成文本的长历史会话，结束时 RSS 约 630.2 MiB、`memory.current` 约 912.1 MiB、追加期事件循环最大约 208 ms。没有模型调用、真实工具或 SQLite 负载；结束快照不是全过程内存峰值。这些数据只用于选择起始实验范围，不能推出真实总人数上限。

实施必须覆盖下列故障场景，全部使用假模型/假赛事，不消耗正式机会：

| 场景 | 必须成立 |
| --- | --- |
| Lead 并发重复请求目标 20 人 | 目标仍为 20，准备中人数计入，不多建成员 |
| 两次动作看到相同内存采样，其中一次已预约工具 | 后一个动作看到预约后的剩余量，不花掉同一份余量 |
| 高水位附近来回抖动 | 一旦暂停，满足低水位和连续稳定窗口才恢复，不反复开停 |
| 文件缓存增长、匿名内存稳定、无实际分配压力 | 不能仅因此杀工具或重启；允许审慎暂停新增并记录原因 |
| CPU 满载但任务有进展、主控健康 | 不判卡死，不自动缩掉活跃团队 |
| 正常长工具/GC 突发/长模型请求 | 主控健康时不重启；工具超时与主控失联独立判断 |
| stdout 持续输出或磁盘将满 | 不将完整输出堆进 Node 内存；为状态回执留空间，截断/取消有明确记录 |
| 准备失败、监控采样停更 | 只回收已确认失败实例的预约，停止新准入，不伪报已创建成员 |
| Node 挂死、PID 被重用、旧工具未退出 | 不误杀其他进程，不启动双写者，清理未知保持未决 |
| 重启时提交回执未知 | 不重置截止时间、不盲目重提、不将异常转成整场 finish |

本次只新增本设计文件；未改变产品默认值，未执行真实资源耗尽或杀进程测试。未知工具可能瞬时分配大量内存，轮询和估算存在反应延迟；没有可用的逐工具内核限制时，本方案只能通过预留、受控启动和处置降低风险，不能保证任意工具永不 OOM。应通过混合负载测出余量和工具级配置，不把软监控包装成硬隔离。

建议父任务将本文件与设计修订一起单独提交，之后再实现准入、队列和监督。当前无需新增用户业务决策；阈值、批大小和时间窗口属于需要验证的工程参数。
