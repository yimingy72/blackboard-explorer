# 独立 CTF 比赛版：资源可见性与 Lead 扩员

本文件补充[独立比赛版方案](CTF-standalone-20261120.md)。按用户最新决定，初始创建 **20 个同级 Worker**，之后由 Lead 查看实际系统占用并决定是否增员。保留原文件名用于已有链接；此前的自动容量保护方案已撤销。

## 1. 决策与职责

- Lead 读取真实资源信息，判断是否需要、能够增加 Worker，并直接调用创建工具。
- 程序执行 Lead 的创建请求，如实返回成功、准备中或失败结果。
- 不设置容量准入、资源预约账本、模型/工具容量队列、内存阈值自动拒绝、强制分批门禁、自动缩容或复杂 watchdog。
- 没有隐藏的自动容量控制；资源读取结果只提供给 Lead 判断，不转换成程序的增员许可。
- 没有工作的 Worker 继续待命，不为待命产生模型轮询。新题优先、同题援助和业务认领规则按主方案执行，不受取消容量排队影响。

初始 20 人是团队起步人数，不是全局上限。每题 10 人、每 Worker 持有 3 条 Intent、最多三个在线题目环境仍是各自独立的既定业务/赛事规则。

## 2. 资源读取

资源工具只读当前容器，返回值包含采样时间、数据来源和不可获取的字段。至少提供：

| 信息 | 内容 |
| --- | --- |
| CPU | 实际容器配额、近期使用量及可读的 throttling 信息 |
| 内存 | 容器限制与当前用量、Node RSS/heap，能读取时附匿名内存和文件缓存 |
| 磁盘 | 当前工作目录所在文件系统的可用空间；赛事可写配额另行标明 |
| 执行情况 | Worker 总数、就绪/忙碌/待命/准备中人数，正在运行的模型请求和工具进程数量 |

不能把宿主机总资源当作容器剩余资源，也不能用空会话均值推断真实可开人数。CPU 满载、文件缓存增长或采样暂不可读，都如实呈现给 Lead；程序不据此自行拒绝扩员、暂停工具或结束 Worker。采样过旧时注明时间，不把旧数值冒充实时信息。

## 3. 创建工具与幂等

建议创建工具使用 `request_id`、`target_total`，可附 Lead 的增员理由。`target_total` 表示希望达到的团队人数，避免重试“再加 N 人”时重复创建。

1. 同一 `request_id` 与相同参数返回原请求的结果或当前实际进度；同一 ID 改变内容返回参数冲突。
2. 按已经存在和正在创建的 Worker 记录计算缺口；并发请求同一目标不会重复创建成员。这是业务去重，不是资源预约或容量限制。
3. 为实际要创建的成员登记稳定 ID，再启动会话；不人为等待资源阈值、固定批次或容量队列。
4. 返回实际已就绪、准备中、失败成员与失败原因，不把目标人数直接报为成功人数。创建过程中遇到 SDK、进程或操作系统错误时正常报告，不伪造成功。
5. 已经成功的成员不会因重试再建一次；失败后需要补足时，Lead 可以再次请求目标人数。低于当前人数的目标不会自动删人。

这里保留必要的参数校验、短事务和幂等记录，避免重复副作用；不设置全局 Worker 数量上限，也不依据资源信息缩小 Lead 的目标请求。

## 4. 正常执行与日志

继续复用 Pi SDK 的本地工具能力。`BashOperations.exec(command, cwd, { onData, signal, timeout, env })` 和 `spawnHook` 可用于调用记录以及本次命令的 cwd/env；不修改整个 Node 宿主的全局 cwd/env，也不重新接回远端 Sandbox。

已核实 SDK 1.5.0 本地 backend 会创建 detached process group、跟踪 PID，并在正常取消或显式 timeout 时清理进程树；timeout 默认未设置。它没有自动提供持久 PID 恢复账本，不能将普通进程跟踪表述为已经完成崩溃恢复。

输出复用 SDK 的有界显示尾部、超限临时文件，以及 1 MiB 的 `structuredContent.output` 上限。保留真实输出路径、退出码、取消/超时和截断信息；记录 Worker、题目和工作代次，不另外建立全局输出容量门禁。

普通错误、单个 Worker 结束一轮或创建失败都不自动调用赛事 `finish`。已确认的暂缓、停止及正常会话结束仍进行对应执行清理，不因取消容量保护而丢弃事实、日志或未决提交结果。

## 5. 验证与边界

后续实现只需针对本合同验证：初始 20 人；资源读数来源与时间准确；重复/并发目标人数不多建；部分创建失败回执真实；没有基于 CPU/内存阈值的隐藏拒绝或容量等待；SDK 正常取消和输出引用仍可用。

本轮仅重写此设计文件，未修改产品代码、提交或进行真实资源耗尽测试。Lead 的判断不等于内核硬内存保护，不能承诺任意工具都不会 OOM。
