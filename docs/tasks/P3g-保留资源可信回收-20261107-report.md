# P3g：保留资源可信回收

## 完成内容

本片把用户明确删除 Task 的原有入口接入可信 Runtime 的原生资源回收循环。普通停止仍保留 Namespace、journal 与 workspace PVC；删除请求在 Task 锁内持久化独立、幂等的 user_delete 意图。未取得部署归属的取消请求保留原有最小删除路径。

执行必须已到 Task 终态，且原 Runner/Sandbox 退出已经确认，才能准备回收。删除政策可代替归档要求，但不冒充归档成功，也不覆盖未决调用、未收口费用、仍运行的 Turn 或进度任务。先回收原生模型凭据及 MCP 路由，随后才允许破坏卷。回收 HTTP 不持有 Task 数据库事务；每次进度提交与紧贴修改的准入都重核全局 Runtime fence、PG 会话身份及原 Task 归属。

原资源账中保存来源、Namespace/PVC/PV 与 policy/binding UID、原 claimRef、Delete 策略及逐项缺失读回。原 UID 不允许替换或丢弃；未知结果继续保账。旧创建配置没有 StorageClass UID/模式快照，因此首版拒绝未绑定 PVC，不能拿当前无 PV 推断历史从未异步创建。Retain PV 在破坏卷前拒绝。

Namespace 回收只支持部署明确冻结并实际验证的单 apiserver。原生 ValidatingAdmissionPolicy 通过 core/v1 Namespace 参数绑定原 UID，封锁该 Namespace 的 CREATE；必须用该策略特定的 dry-run Deny 证明生效后，才完整盘点并逐 UID 删除原对象。外来资源、无法完整发现/读取的 API、身份漂移或 HA 配置均保守停止。Namespace 最后通过 UID precondition 删除，原卷由 Delete provisioner 回收，平台不直接删除 PV。

真实 controller 持续重读同一账，不建立第二套 GC/调度系统。全部资源及封口策略读回消失后持久退休，现有 purge 才释放资源门；已退休无需再次访问旧集群。存储删除读回不等于物理数据擦除。

## 偏差与待决

首版只自动退休已确认单 apiserver、已绑定且 Delete 策略明确的原卷；其他情形保账并显示原因，不声明资源清理成功。原生事件等元数据仅保留归属所需 UID 投影，不落原始事件正文或 Secret 内容。Namespace 准入封口不取消已在途请求；重新完整盘点、原生 UID 条件删除及后续读回仍是必要条件。

P3h 的 Sandbox 工具、平台命令审计与现有界面查看是本轮下一提交的范围，本提交不宣称已实现。
