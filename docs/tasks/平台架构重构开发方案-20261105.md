## 0. 范围、基线与完成标准

### 0.1 用户要求

| 编号 | 必须交付的行为 |
| --- | --- |
| R1 | 用户从“创建任务”输入自由目标、验收条件和材料；普通任务、单题、多题使用同一底层，不把 TSec 规则写死成平台流程 |
| R2 | 平台负责 Task、Agent、Kubernetes 任务资源和 OpenSandbox 接入；Runtime 是内部运行管理模块 |
| R3 | Lead 创建/管理题目；Worker 仅修改当前负责题目里的工作信息，不创建题目；helper 只处理父题目局部目标 |
| R4 | 每题组织 Intent、Fact、证据及多条 Flag；候选写入产生持久事件，Lead 提交并依据真实回执验收 |
| R5 | 全局公告承载网络背景、共同约定与材料；真实环境状态由平台观测，公告不能伪造 readiness |
| R6 | 保留现有 CTF 工具镜像；命令和文件由 OpenSandbox 执行；同任务共享文件，跨任务隔离 |
| R7 | 复用 OpenVPN/代理客户端，Lead 请求准备环境；Worker 直接使用已验证的题目连接 |
| R8 | 保留 Lead、Worker、helper 的流量与归属；显示采集范围、丢失和未知，不把 Task 抓包冒充逐 Agent 抓包 |
| R9 | 可视化查看任务内各 Agent 的所有受控沙箱命令、输出、状态及关联流量；明确子进程审计覆盖边界 |
| R10 | 尽量复用 Pi SDK、pi-subagents、agentgateway、OpenSandbox 和原有事务/界面；不额外引入管理 LLM 或通用工作流引擎 |

## 1. 概念与职责

### 1.1 对象含义

| 对象 | 含义与权威 |
| --- | --- |
| Task | 用户的一次整体任务，持有目标、模式、预算、时限、配置和基础设施 |
| Challenge / WorkItem | Task 内一道题或明确工作项；复用当前题目对象，不再建第二张题库 |
| Assignment | 某 Worker 当前负责某题的分配及 generation；唯一负责人权威 |
| AgentSlot | 可占用的 Worker 身份容量；main/helper/free/draining 总和为 N，Lead 另计 |
| AgentSession | Pi 会话；换独立题建立新会话，与稳定的界面 Agent ID 分开 |
| ChildRun | helper 的父题目、局部目标、席位、会话和宿主绑定 |
| RuntimeLease | Task 的唯一有效运行控制权，包含 owner、epoch、到期时间 |
| EnvironmentBinding | Namespace、Tenant、Sandbox、Pod UID、卷、环境代次及真实就绪状态 |

CTF work_status 保持 pending / in_progress / blocked / completed / cancelled。ready 是材料、环境、owner、清理条件计算出来的派发条件；待模型、预算、用户或验收是 Assignment 的等待原因，不再并行维护另一套题目状态。

### 1.2 部件分工

| 部件 | 负责 | 边界 |
| --- | --- | --- |
| Web / blackboard | 用户入口、黑板、业务授权、数据库事务、配置、验收及事件 | 业务状态只有一份权威 |
| Runtime 控制模块 | Task 租约、派工、席位、模型/工具准入、输入、停止恢复及独立清理 | 留在现有 agent-runtime；不重写 Agent 循环 |
| Task Runner | 承载 Pi Lead/Worker/helper 与插件后台进程 | 不运行题目脚本、不挂求解工作卷 |
| Pi SDK | 会话、模型工具循环、压缩、原生日志、插话与取消 | 不决定题目 owner、预算余额或题目通关 |
| pi-subagents | 子会话创建、消息、状态、结果与取消 | 由平台补齐身份继承、席位、持久化与回收 |
| agentgateway 1.7 standalone | 唯一上游模型 provider 连接/协议适配/凭据、usage 归一化、USD cost 目录与 per-key 预算执行；MCP 路由/策略 | 平台保留可信费用归集、阈值停止和题目授权；不另做一套模型计价/预算执行 |
| OpenSandbox | 生命周期、执行接口、文件、execd、官方 Controller/Ingress | 不理解 BBX Agent、题目、epoch 或 Flag 规则 |

Runtime 在用户启动任务后取得执行权、准备资源、启动 Lead；Lead 发布题目后由 Runtime 原子派给 Worker，之后持续管理等待、完成、补位与清理。它不是另一个管理 Agent，也不要求独立新增服务。

## 2. 部署与调用路径

### 2.1 默认部署

一个运行 Task 对应一个 Namespace、一个 OpenSandbox Tenant、一个有效 Sandbox，以及一个 Runner Pod。每 Task 的 MCP、卷、网络身份和凭据分别绑定。20 个 Worker/helper 不代表 20 个 Pod。

| 部署对象 | 粒度 | 内容 |
| --- | --- | --- |
| blackboard、数据库、对象存储、业务 MCP | 平台共享 | 沿用现有服务 |
| Runtime 控制与 cleaner | 平台共享 | 按 Task 租约管理；Runner 消失仍能清理 |
| agentgateway 1.7 standalone | 首版单活动实例，可用官方 standalone Helm 部署于 K8s | 分开模型和 MCP 入口；唯一配置发布者；不混用 Gateway API 控制面配置模式 |
| OpenSandbox Server、Controller、Ingress | 集群共享 | Server 首版单活；Controller 观察动态 Task Namespace |
| Runner Pod | 每 Task 一个 | Pi、任务专属 Sandbox MCP、可信任务出口组件 |
| Sandbox Pod | 每 Task 一个 | 旧 CTF 工具层＋官方 execd＋固定网络与采集组件；本版不启用官方 Egress |
| journal PVC / workspace PVC | 每 Task 各自独立 | 日志不挂进 Sandbox；工作卷不挂进 Pi Runner |

新任务使用官方 kubernetes + batchsandbox，单副本、非池化。平台创建 Namespace、配额、固定网络策略、Runner 资源及租户映射；SDK 调 Server 创建 Sandbox CR，再由官方 Controller 调度 Pod。不直接操纵 Sandbox Pod 或增加自研 Operator。

TenantProvider 在现有平台服务实现 Task 凭据到 Namespace 的映射。租户不是“一个 Namespace 内换几个 Key”；不同 Task 必须有不同 Namespace。平台、MCP、Sandbox 均不向模型提供集群凭据或全局密钥。

启用官方 Ingress gateway 与 secureAccess，并核验 execd 的访问鉴权；不能把 Server 的租户 Key 当成所有执行端口均已保护。Task MCP 入站仅允许网关/受信管理连接，其出站 Key 不代替 HTTP 入站认证。

SDK 创建采用有限 TTL 并留有界收尾时间，任务 deadline 独立硬停，续期受当前 Task/epoch 控制；首版不采用自动暂停/唤醒或快照代替业务恢复。journal 卷优先采用支持 ReadWriteOncePod 的存储并核验能力，不能只用文件名保证单写者。

### 2.2 四条路径

| 路径 | 链路 |
| --- | --- |
| 模型 | Pi → Runtime 身份/fence 与原请求关联薄层 → agentgateway standalone 原生模型/预算 → 供应商 |
| 沙箱工具 | Pi → pi-mcp → agentgateway → 本 Task Sandbox MCP（官方工具＋窄扩展）→ 官方 SDK/Ingress/execd |
| 黑板/平台业务 | 官方低层 pi-mcp＋最小平台桥 → agentgateway → 严格 Agent OpenAPI 子集候选或官方 Server 薄 host → 原业务处理器 |
| 生命周期与故障清理 | Runtime/cleaner → 官方 SDK/Server 或数据面 → 已绑定 Sandbox |

共享业务 MCP 可由每 Task 逻辑路由展示，但不复制进程。Task/Agent/Assignment 身份来自平台签发和服务端绑定，不由模型选择。生命周期 SDK 通道只做管理、既有执行观测、归档与清理，不成为 Agent 随意执行命令的第二入口。

### 2.3 就绪与配置

分别保存 namespace_ready、runner_ready、sandbox_api_ready、network_ready、capture_ready、audit_ready，附观测时间、环境代次和原因。Pod Running 不等于全部就绪。

工作负载和网络附件先以待机状态健康启动，再由 Lead 请求网络配置；VPN 不作为整个 Sandbox Pod 的 readiness 条件，避免无法创建或无法修复。

Pod UID 改变会使旧进程、网络、采集就绪证据失效。记录新 environment_revision，冻结相关新执行并核对，不把自动补 Pod 当成原进程恢复。

### 2.4 原生复用优先与必要薄适配

用户追加要求 Pi 调用 Sandbox 也统一经 agentgateway，继续优先原生能力，不重复客户端、聚合器、权限目录或执行服务。现连接使用官方 pi-mcp；business_mcp 是官方 MCP Server 的薄 host，不是自研整层协议。先直接复用，明确缺口再薄适配；高层 extension/OpenAPI 不能满足已核边界时保最小桥，不机械删除安全接缝。

| 能力 | 直接复用候选 | 仅在缺口明确后保留的薄适配/门槛 |
| --- | --- | --- |
| Pi MCP 客户端/挂载 | 暂推荐官方低层 pi-mcp＋最小平台桥；高层 createMcpExtension/loadConfig 等连接/目录/命名/content 能力为候选 | 高层忽略 callId/_meta、404 重发会要求更多桥，不能裸替换；只载受信 gateway，禁默认 codemode/stdio/全局文件/本机执行，保确认/absolute permit/关闭 gate |
| MCP 路由/聚合/角色目录 | agentgateway 原生 MCP modes、Virtual MCP、mcpAuthorization 工具/角色/target allowlist、每 target backendAuth | target 条件基于可信 JWT；tools/list 隐藏不等于未初始化 foreign target，须实测握手/调用均隔离，不能只比列表 |
| 共享业务工具 | 官方 OpenAPI→MCP 转换严格 Agent 专用子集，与现薄 host 比较 | 不能全量暴露内部 OpenAPI；不得假定 _meta 透传。须保可信 invocation/header、稳定 request_id、域事务 fence/结果确认及 403/409/422 错误语义；不为 converter 造复杂协议 |
| Sandbox 执行/文件 | 官方 MCP command_run/interrupt/text files，官方 SDK 执行引擎 | background status/log、低 UID files、Task/Assignment/nonce/cgroup 清理只作已核窄补；不重写执行服务，不恢复旁路命令入口 |
| MCP 可观测 | 原生 MCP 日志/OTel | 当前 request_logs 仅 LLM，不能冒称永久 MCP 命令审计；平台命令/官方 execution_id、netns/流量/eBPF 缺口继续独立留证 |

候选资料见 [MCP modes](https://agentgateway.dev/docs/standalone/latest/documentation/mcp/configuration-modes/)、[Virtual MCP](https://agentgateway.dev/docs/standalone/latest/integrations/mcp/servers/virtual/)、[OpenAPI](https://agentgateway.dev/docs/standalone/latest/integrations/mcp/servers/openapi/)和 [mcpAuthorization](https://agentgateway.dev/docs/standalone/latest/documentation/configuration/security/mcp-authz/)。v1.7 OpenAPI 转换的已知限制是 4xx 仍可返回 isError=false 且省 HTTP 状态，5xx 才为 RPC -32603；200 通路成功不足以替换现薄适配。真实 Pi→agentgateway→工具 backend 与一个 OpenAPI 工具对比通过前只记候选，若保不住上述权限/关联/错误/结果语义，保留最小可信 hook 并写明实证缺口。

只读核查还确认：原生 Pi execute 不提供稳定 SDK callId/_meta 注入，session 404 可重试一次 tools/call，progress 会续 server timeout；tool_call 可 await/block，但 tool_result 异常会被吞，不能独占持久屏障；bindExtensions 的后台 connect 非硬 readiness，dispose 不自动发 session_shutdown，须用公开 runner emit 并 await。大于约 20 KiB/二进制结果的 Runner 临时文件不等于 Sandbox 可读，须分页/注册 artifact 或保结果薄层。网关验证 JWT 后默认剥 Authorization，共享 board 必须显式核 backendAuth passthrough；generic `/tools/{operation}` 不会自动变为十四个有独立 schema 的工具。这些是已知缺口与后续 probe 门槛，不为替换而造复杂协议。

### 2.5 Kubernetes 1.34 原生职责

复用官方 OpenSandbox Server→BatchSandbox→Controller，不重写 Sandbox 调度/重建循环。Runner 按任务进程生命周期选择合适原生 workload 并用官方 watch/状态对账；复用 probes、requests/limits、ResourceQuota/LimitRange、Secret/ConfigMap、SA/RBAC/Downward API、Service/DNS/CNI，不新增 Operator/scheduler。真实 G1/P1 probe 是接缝证据，不是产品控制器，不因替代而误删。

OwnerRef 按原生 GC 规则：namespaced owner 不跨 Namespace，cluster-scoped dependent 不引用 namespaced owner；PVC/审计保全不交给无条件级联删除。Job 的 backoff/deadline/TTL 只用于适合的 Job，suspend 会终止 Pod、不是保存进程；RWO 不是单 Pod，RWOP 需实际 CSI 支持。Lease 可做组件 leader 协调，不替代数据库 Task epoch/fencing。K8s/网关不代替同 Pod 各 Assignment 的 nonce/cgroup 清理、netns/流量身份和命令审计，旧进程是否停止仍要证据。官方边界见 [ownerRef](https://v1-34.docs.kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/)、[Job](https://v1-34.docs.kubernetes.io/docs/concepts/workloads/controllers/job/)、[存储访问模式](https://v1-34.docs.kubernetes.io/docs/concepts/storage/persistent-volumes/)与 [Lease](https://v1-34.docs.kubernetes.io/docs/concepts/architecture/leases/)。

## 3. 黑板数据、公告与知识

### 3.1 数据修改范围

优先扩展现有 contracts、schema、投影和事件，不引入另一套图数据库或消息中间件。

| 数据 | 最小字段/调整 | 写入者 |
| --- | --- | --- |
| Challenge | 原题来源/unique_code、题面引用、类别、目标/附件引用、优先级、前置、交付条件、版本 | Lead 发起管理；平台维护 owner/状态 |
| Fact | 原有 statement、证据、推导/争议关系，增加 challenge_id、assignment_ref、原作者/子运行来源 | 当前 Worker；helper 限局部目标；Lead 可追加注释/裁定 |
| Intent | 原有方向、依据、结果关系，增加 challenge_id 与分配来源 | 当前 Worker/helper；CTF 不开放独立 claim |
| Announcement | id、task_id、revision、body、author、environment_revision、published_at、supersedes | Lead 发布不可变版本 |
| FlagCandidate | candidate_id、challenge_id、值引用/受保护值、精确值摘要、作者、assignment、证据、验证轮次 | 当前 Worker；helper 交父 Worker |
| FlagSubmission | submission_id、candidate_id、操作 ID、来源平台、状态、回执引用、分数与正确数 | Lead 发起；可信平台处理器写结果 |

Fact / Intent 的 challenge_id 允许为空以保留普通任务和历史语义；新 CTF 写入必须指定并验证题目。普通任务调度仅消费其原有范围的 Intent，不读取 CTF 的题内方向。跨题引用必须通过本 Task 的获准共享记录；不能用引用绕过读取授权。

普通任务继续按原 Intent holder 校验 resolves；CTF 题内 Intent 不独立认领，关闭权限改由当前有效 Assignment 判断：主 Worker 可关闭本题方向，helper 仅可关闭其 ChildRun 登记的局部方向。换人后由新负责人承接未结方向，保留原作者与历史；旧 generation/epoch 不得继续关闭。Intent 关闭不推进题目 completed。

Fact 是带证据的声明，不因命名为 Fact 就自动变成正确结论。复用现有 disputes/resolves 与修正事件，保留作者和历史，不直接覆盖他人的证据。子 Agent 产物被父引用时保留原作者。

### 3.2 公告及上下文

公告用于任务背景、VPN/代理用法、共享材料、协作约定；凭据只保留受控引用，不放密码、Token 或私钥。

系统单独返回实际 network_status、observed_at、environment_revision 和检查结果。Lead 写“已连接”不会改变真实网络状态。公告引用的环境版本过期时界面提示，依赖当前网络的派工按实际状态判断。

新 Worker 启动获得最新公告、原题、材料、已有尝试和当前 Assignment；运行中以确认游标接收公告增量。网络失效由系统事件更新状态；不靠给所有 Agent 反复发送整段公告维持同步。

普通进度合并给 Lead；候选 Flag、全局前置失效、明确求助、题目/任务结束即时进入持久待办。通知丢失由事件/数据库状态补齐，通知重复不能重复开展工作。

### 3.3 写入与 API 合同

所有写入包含 request_id、expected_revision；服务端取可信 task/agent/role/assignment/generation/epoch。相同 ID 和参数读取原结果；同 ID 换参数拒绝；停止和撤权优先于旧配置快照。

授权失败返回明确越权；版本/代次冲突要求刷新；未知外部副作用不作为普通可重试错误。REST 与 MCP 共用同一个处理器和事务，不维护两份校验。

## 4. Lead / Worker / helper 工具与权限

本节是 CTF 协作 Profile；普通任务的 Explore/Derive/Close 与成果整理继续使用原领域权限和调度，仅复用新会话、执行、审计与预算底座。

| 能力 | Lead | Worker | helper |
| --- | --- | --- | --- |
| 读 Task/公告/共享知识 | 本 Task 全局 | 当前题目及获准共享信息 | 父题目必要范围 |
| 建题/改题干、范围、优先级 | 允许 | 禁止 | 禁止 |
| 追加方向、Fact、尝试、求助 | 允许，保留原作者 | 当前 Assignment | 当前局部目标 |
| 候选 Flag | 处理/转交，保留发现者 | 当前题目登记 | 回父 Worker |
| 提交/查询验收/平台靶场管理 | 允许受控业务工具 | 禁止 | 禁止 |
| 公告与环境配置请求 | 允许 | 求助 | 求助 |
| 命令/文件 | 准备、材料、诊断和规定验收 | 求解 | 局部目标 |
| Worker 调整/题目交接 | 发起意图 | 禁止 | 禁止 |
| subagent 委派/消息/取消 | 不作为日常解题工具 | 本题单层委派 | 禁止递归 |
| Sandbox create/kill/renew/list、集群操作 | 不开放 | 不开放 | 不开放 |

Lead 不亲自解题，也不逐条审批普通命令。Lead 的环境工具只发布已支持配置，集群权限与网络特权由可信组件持有。

创建题目只允许 Lead；Worker 可以在本题创建 Fact/Intent/候选记录，这不等于创建题目。发现新题时 Worker 报告材料，Lead 批量登记。删除旧 discover 自动建题分支，不以插件或来源模板绕过该规则。

平台管理 owner 和席位；Lead 的换人请求触发旧执行收尾后再交接。Worker 不能通过更新题目把自己改成另一题负责人，也不能写 accepted、真实得分或自行通关。

工具清单来自发布后的角色配置。网关过滤 tools/list 并检查 tools/call；业务服务仍检查题目范围。原生 Pi 本机 bash/read/write/edit 默认关闭，Skills 和子插件不能恢复本机执行。

## 5. 派工与子 Agent

1. 创建 Task 即预建 N 个空闲席位；空闲身份不调用模型。
2. Lead 尽早获取有效材料并批量登记题目；有一道满足前置就可开工，不等待整场计划完成。
3. 派工事务依次检查停止/租约、材料/环境、无有效 owner、旧执行清理、席位；原子绑定 Assignment 并写唤醒 outbox。
4. 先按 Lead 优先级，再按同级等待时间，最后匹配空闲成员最近题型；没有同题型立即派其他题，不抢占正常求解。
5. 题目完成并清理后事件触发补位；定时看门狗只补漏，不能靠 LLM 轮询容量。
6. 没有可执行工作时显示材料、环境、外部名额或预算原因；不强行把 20 人塞进 3 道无法独立拆分的题。

Worker 只提交子目标、输入引用和预期产物。平台从父有效快照继承模型、推理强度、获准工具/Skills、题目目录和 Sandbox；签发独立子身份，权限取父有效范围与 helper 上限的交集。

主任务和 helper 借位共用原子席位入口，先覆盖独立 ready 工作，再借余量。18 main + 2 helper 已满 20，Lead 另计。满位立即返回，父 Worker 继续求解，禁止全体父 Worker 占位等待子位。

helper 默认新上下文，自动注入必要题目事实，不复制全部父对话。产物约定放在本题 .subagents/child_id 下，但目录不是同任务安全边界。

父普通回合结束不取消子任务；父分配取消、换题、整题完成或 Task 停止才级联收尾。迟到结果保存到原 ChildRun/Assignment，不投给下一题、不唤醒已停止父会话。

pi-subagents 的前台/后台确认与取消接缝必须先通过 G3。前台通过不能冒充后台通过；后台未过时明确关闭异步能力，不引入未受控替代实现。

## 6. Flag 验收闭环

1. Worker 提交候选值、证据和当前 Assignment；验证题目归属与材料引用。
2. 同事务写候选、事件和 Lead 持久待办。事件携带 ID 和摘要，不广播明文 Flag。
3. 同 Task、题目、验证轮次、精确候选值去重；不自动 trim/改写有意义字符，不跨题去重。
4. Lead 从待办审核并发起提交，生成稳定 submission_id。平台保存外部请求前记录和真实回执。
5. accepted 推进正确数；rejected 通知原 Worker；duplicate 查询/关联既有正确结果，不重复加分；unknown 先核对，不当作错误答案。
6. 部分 Flag 正确继续求解；全部条件满足才由可信处理器推进 completed。单个候选不自动停止 Worker。
7. 通关/放弃后按任务规则关闭外部靶场，确认释放后再补下一题；完成说明和资源清理状态分别展示。

外部平台没有结果查询或幂等能力时，响应丢失不能保证 exactly-once。保留 unknown，由 Lead/用户依据证据处理，不通过换请求 ID 掩盖未知。

TSec 的三个靶场名额与 Worker 席位分开：启动中、启动结果未知、关闭待确认都占名额。总分按每题最新累计得分求和；不能反复累加累计值。普通任务无 Flag 时按原验收规则处理。

单题附件或没有外部提交接口的任务，由 Lead 对用户验收条件和证据发起评审，保存 verifier_type 与依据；不得伪造外部平台 accepted、分数或正确数。总 Flag 数未知时明确未知，不以已发现数量自动充当总数。

## 7. 旧镜像、OpenSandbox 与执行身份

### 7.1 镜像复用

以现有 services/envd/Dockerfile.kali 的 CTF 工具层为基础制作迁移镜像。保留语言、调试器、逆向/密码/取证工具、OpenVPN、tcpdump/tshark 等；保留原普通任务镜像选择能力，不强制所有任务使用 Kali。

调整旧 envd 启动入口，使用官方注入的 execd/bootstrap。OpenSandbox Server、Controller、MCP 不装进工具镜像。集群所有节点必须能拉取固定工具镜像；kali-mini:latest 是本地标签，不能直接当跨节点分发合同。

镜像、架构、工具清单、execd、采集版本分别锁定。已运行 Docker 容器不被原地“接管”；新后端使用新实例，历史环境按旧生命周期结束。

### 7.2 最小执行接入

保留任务专属官方 MCP 的连接与工具基础，在固定版本上增加一个有测试的小范围扩展：

- 受控命令工具绑定平台 command_id / invocation / Agent / Assignment / epoch；复用官方 SDK 命令执行、输出与中断。
- 可信启动器按固定网络身份进入命名空间，随后降到任务共同低权限 UID/GID，去除网络管理/身份切换等能力，再执行用户命令。
- 所有文件工具通过官方 files_with_identity 绑定同一任务低权限身份；owner/group 参数不能提升到控制身份。共享工作区正常读写，不建立逐题文件 ACL。
- 原始未绑定身份的 command_run 和以 root 访问文件的工具不同时对 Agent 开放。工具目录明确发布版本与差异，不能靠提示词选择“正确的那个入口”。
- 状态和增量日志按需发布薄 MCP 工具，内部调用 sandbox.commands.get_command_status(execution_id) 与 sandbox.commands.get_background_command_logs(execution_id, cursor)；图片/二进制使用官方字节文件接口。平台工具名不冒充官方 MCP 已有能力，不恢复另一套通用文件/进程服务。

执行身份来自可信调用上下文；模型不能指定 UID、netns、环境代次或采集凭据。使用官方 SDK 的原生 argv 接口启动固定程序，用户命令保持为独立数据参数，禁止插值进特权 shell 前缀。启动器完成 setns/降权后 exec 替换为实际命令，不能自己退出留下脱管后台 shell；核对官方 execution_id、根 PID/进程组、退出码和中断的一致性。

原生 argv 不会自动清空 execd 的继承环境。特权阶段固定绝对程序路径、可信工作目录和环境，不接受模型指定 envs、PATH、动态加载器或 shell 初始化变量；EXECD_ENVS 和启动器依赖位于受保护控制区。启动器使用固定可信构建，不设置供普通用户提权的 setuid/file capabilities。进入绑定 netns 后关闭无关继承文件描述符、清空管理环境、降共同 UID/GID 与能力，再按白名单重建求解环境，只下传工具运行、任务目录、本命令代理/CA等必要变量，不继承 execd/MCP/VPN 管理凭据。最后 exec 真实命令并保留执行关联。

启动器/控制配置只读，凭据不在共享工作卷；支持 files_with_identity 失败时不得回落 root。官方 Linux 文件身份接口通过独立低权限文件 worker 执行，能力不满足会拒绝；工具 owner/group 固定共同身份，mode 不允许 setuid/setgid 等特殊位。共享工作目录正常权限变化属于协作问题，不升级为逐题 ACL。

命令先保存准入与审计记录，再派发；拿到官方 execution_id 后立即绑定。响应丢失保留 unknown；同一 invocation 不能重新生成一次执行。

### 7.3 能力与文件边界

同 Task 共享文件与共同低权限身份。题目目录、子目录、明确写者用于协作，不承诺阻止同任务 Agent 相互干扰。

逐 Agent 网络身份用于采集归属，不等于每 Agent 一个 Sandbox。网络身份包含 Assignment/generation，旧执行未清理前不能复用给新题。

保留旧 netns 机制需要可信进程具备 setns/网络管理能力；这不是只添加一个 SDK uid 参数就能实现。主容器/可信进程所需 SYS_ADMIN、NET_ADMIN 和子进程能力下降必须在最终 Pod 与 G1 中核验。只把创建/采集移到 sidecar 仍不能自动免除主侧 setns 权限。首版接受可信 execd/启动器所需的明确能力例外，不给主容器笼统 privileged；Solver 执行前去除 SYS_ADMIN、NET_ADMIN、SETUID、SETGID 等管理能力并设置 no-new-privs。NET_RAW 按工具需求明确配置并验证。

平台控制区和会话卷不向求解身份提供写权限。官方低权限文件 API承担操作系统身份约束，不以字符串路径校验解决符号链接竞态。

## 8. VPN、代理与任务出口

### 8.1 默认线路与取舍

默认沿用两个 Task Pod、一个外部 VPN 会话：可信出口位于 Runner 侧；Sandbox 经固定内部三层隧道使用该出口。成熟 OpenVPN/WireGuard/DNS/代理软件负责协议；平台仅发布配置、观察状态和停止。

选择这一位置的理由：Lead 的可信平台请求与 Worker 求解流量都需要同一 VPN；TSec 可能使用明文 HTTP Token，提交凭据不能进入所有 Worker 共享的网络和抓包文件。把 OpenVPN 只装进 Solver 不能自动解决 Runner 提交路径。

如果后续要改为 Solver 内终止 VPN，必须先交付可信提交凭据/网络边界的具体替代方案；不作为第一版并行实现选项。第一版不增加第二个 VPN 登录会话。

### 8.2 通道与策略

| 通道 | 路径和限制 |
| --- | --- |
| Worker / helper / Lead 的 Sandbox 命令 | 对应网络身份 → 任务出口 → VPN/获准公网；采集在加密前 |
| Lead 题库/提交等可信业务请求 | 平台客户端 → 本 Task 认证代理 → 同一 VPN；请求/回执单独审计并脱敏 |
| 模型/MCP/Server/Ingress | 原集群控制通道；VPN 不能改写这些默认路由 |

Cilium 在 Pod 外阻止跨 Task、节点和集群管理面的访问；任务出口解封装后再次过滤目的地址和 Runner 服务。允许任务所需私网靶场，不简单封禁全部 RFC1918。

还必须覆盖未离开 Pod 的路径：Sandbox 根网络空间按实际 Agent veth 入口过滤 INPUT/FORWARD，禁止访问 execd、初始化、采集控制与其他管理端口，只放行任务内层 DNS 和受限采集代理。控制侧另允许官方 Ingress、Runtime/MCP 及必要探针。不能指望 Cilium 或远端 task-network 看见这段本地流量。验证直接 Pod IP、网关 IP、IPv6、loopback 映射及通过允许代理转发均不能绕过；代理检查实际目标和重定向，不能成为控制端口旁路。Agent 不获得执行端点 Token 或原始端点管理工具，execd 令牌为空的兼容放行不能进入新环境。

本版默认不启用官方 Egress sidecar，不传 OpenSandbox 创建请求的 networkPolicy；平台的 Kubernetes/Cilium 网络策略始终存在。原因是官方 Egress 规则位于 OUTPUT，而 Agent 嵌套 netns 出网经过根网络空间的 FORWARD，不能声称自动受它过滤。直接使用已需要的 task-link/task-network FORWARD 和内层目的过滤，减少重复 DNS/路由/mark 管理；不同时开发第二个 Egress 模式。

Task DNS 复用成熟 dnsmasq/转发器：Agent netns → 任务内层 DNS → 可信出口按任务选择 VPN/公网 DNS；Runner 自身控制 DNS 独立。固定 shardPatches 只加入受信网络/采集组件及必要能力/只读配置；不再向不存在的 egress 容器补 env，也不允许任务上传任意 Pod patch。

DNS、路由冲突、MTU、IPv6、TCP/UDP/ICMP、回连监听及代理绕过都进入 G1；HTTP CONNECT 不能当作完整三层 VPN。回连端口按已发布能力开放，不用 HTTP Ingress 假装支持所有协议。

### 8.3 Lead 的环境请求

环境工具只需 configure / status / disconnect 等少量业务动作；输入是协议、配置引用、目标范围、DNS/必要路由和预检要求，平台返回操作 ID、实际版本及状态。

平台预先配置 TUN、能力、Secret 和可信启动方式。Lead 不上传任意 Pod patch，也不以 root 任意执行配置脚本。仅“客户端已安装”不代表连接已准备。

配置变更先冻结受影响命令和新旧业务连接，核对执行后应用，再做可信预检；通过后发布新环境版本并恢复。控制端口在 VPN 断线时仍可达。网络组件在运行许可失效时停止 Solver 转发。

TSec 预检严格按原任务规则，从真实求解路径检查指定地址；首次失败立即停止，不换地址或静默重试后继续。其他任务的连接方式由任务和已发布能力决定，不强制 VPN。

## 9. 流量采集与归属

### 9.1 默认保留的机制

复用旧 per-Agent netns/独立地址和每命令代理身份，以最小接缝接到 OpenSandbox。任务内仍共享文件；Agent ID、题目分配和网络身份之间保存不可混用的映射。

| 来源 | 可靠归属 | 不能据此推断 |
| --- | --- | --- |
| 模型/MCP 调用观测 | Task、Agent、调用 ID | 全部远端网络包 |
| Lead 可信平台客户端 | Lead、题目、submission/operation ID | Solver 抓包已包含该请求 |
| 命令 HTTP(S) 代理 | Agent、command_id、请求回执 | 绕过代理的所有协议正文 |
| Agent 网络接口抓包 | Agent、网络代次、时间/连接 | 同 Agent 并发命令中的精确 command_id |
| 进程/套接字观测 | 有证据时关联命令与连接 | 缺事件时靠目标 IP 猜测归属 |

逐 Agent 是默认交付目标；逐命令网络归属只有代理身份或进程/套接字证据充分时填充。代理身份还应与实际 netns/veth 来源绑定，不能只相信任意客户端填写的 Header。共享代理保留 forwarded_for 与实际执行进程；连接池若跨身份复用，则按身份分池或将原始包关联降为共享代理级。无法确认则归到任务系统/unknown，不强塞给最近执行命令的 Agent。

### 9.2 覆盖、保全与容量

Lead、Worker、helper 的沙箱命令全部经过相同身份接入；平台管理请求另标 system，不能把维护流量计到 Lead。Sandbox 的原始抓包位于 VPN 加密前；可信提交侧使用脱敏逻辑请求记录，默认不把含凭据的原始 PCAP 下放共享工作区。

继续复用 traffic manifest、sealed chunk、上传确认、对象存储、TrafficDrawer/PacketInspector 和下载。采集数据在可信控制目录/独立卷，Agent 文件工具没有修改权。归档先确认对象可读再清理本地片段。

HTTPS 明文仅覆盖支持代理/证书或可取得密钥的流量；证书固定、QUIC、非 HTTP、原始报文分别标能力。PCAP 可能包含目标敏感数据，下载沿用任务访问权限；鉴权头和平台凭据不进入普通索引、公告或日志。

任务有显式采集字节/时长/保留策略，满额、事件丢失或组件重启显示 partial 及时间范围。执行身份准入失败不能无归属启动命令；采集运行中降级是否暂停求解，按任务冻结的 required/best_effort 策略，缺省沿用当前配置而不静默放宽旧任务。

## 10. 命令审计与可视化

### 10.1 两层审计

必须区分：平台接收的命令、execd 的执行状态/输出，以及命令衍生的系统进程事件。一次 shell 命令可能包含管道、脚本、后台进程和 shell 内建动作，不能把一条工具日志描述为所有子进程审计。

基础交付必须覆盖所有经受控工具发出的 Agent 沙箱命令；额外进程审计复用官方 execd-ebpf，在同一阶段做独立接缝验证后接入。未接审计的 PTY、code/Jupyter、其他命令入口不开放给 Agent，避免出现未登记的第二条执行路径。

固定 1.2.0 的真实边界已核对：

- SDK 有命令状态、后台增量输出，官方 MCP 没有独立对应工具。后台日志游标以服务端字节偏移为准，不能按 SDK 注释当行号；前台与后台合并输出的差异如实展示。
- 镜像源码包含普通 execd 与 execd-ebpf，但 Server/K8s 的默认安装仅复制普通 execd，未自动选择变体。只部署官方镜像不等于开启进程审计。
- eBPF exec 事件只有 PID/PPID/comm/有限长度 filename 等，没有完整 argv、Agent ID 或 command_id；TCP connect 事件不是 UDP/全连接审计。shell 内建和解释器内部语句不产生独立 exec 事件。
- BPF/BTF、cgroup v2、内核能力、部分挂钩失败与轮转/丢失需验证；不能给 Worker BPF 管理权限，不能因未收到事件推断没有子进程。

因此“平台下发命令完整登记”是强制能力；“进程观察 disabled/active/degraded/unsupported”是独立状态。未启用与环境不支持分别展示。采集器记录轮转位置、读取失败和已知缺口；上游没有可靠丢失计数时显示完整性未知，不能以零事件或零计数宣称无遗漏。进程观察不可用时保留基础命令审计，不能把内部语句或不可观测后台行为标为完整。

### 10.2 命令记录合同

复用 ToolInvocation/现有 execution 记录扩展 CommandExecution 投影，不创建第二套可写执行状态机。

| 分组 | 字段 |
| --- | --- |
| 身份 | command_id、invocation_id、task/run、agent_id、role、parent_agent_id、challenge_id、assignment/generation、epoch |
| 环境 | sandbox_id、Pod UID、environment_revision、network_identity、tool/version |
| 输入 | 原命令的受保护引用、脱敏展示、cwd、前后台、声明超时、输入材料引用 |
| 执行 | 官方 execution_id、可确认 PID/启动时间、开始/结束、exit_code/signal、取消请求与确认 |
| 输出 | stdout/stderr 分块引用、游标、字节数、截断/丢失范围、完整输出保留状态 |
| 关联 | 进程事件、流量记录、产物、Fact/Intent、候选 Flag |

状态由调用账本和执行证据派生：queued / admitted / dispatched / running / exited / cancelled_confirmed / unknown；拒绝未派发单列。非零退出是已知执行结果，不等于传输未知。父 shell 退出和全部后代清理分别展示。

ProcessEvent 是附加观察投影：保存上游实际字段、采集源/代次、原始文件位置和健康；Agent/command 关联可以为空，并标 exact/unknown。关联需 launcher 的 PID/启动时间、Pod UID、PID namespace/NSpid 等证据，防止 PID 复用误配；不能补造 argv/退出码或按时间邻近自动认领。

命令入库必须早于派发。平台 command_id 稳定，ExecutionHandlers.on_init 返回 execd execution_id 后立即绑定；ID 迟到或缺失时不能把命令从列表移除。后台命令通过官方 SDK 的状态/日志接口和启动器证据更新；任务/Agent 停止继续核对原 ID。官方进程内状态与有期限日志不能作为永久审计库，必须按游标及时分块归档。

### 10.3 界面与操作

任务工作台增加“命令”视图，Agent、题目详情可带筛选进入同一视图；不新增全局基础设施控制台。

- 筛选：Agent/角色/helper、题目、状态、前后台、时间、退出码、关键词；默认按任务版本与稳定游标分页。
- 列表：发起者、题目、命令摘要、cwd、开始时间、耗时、状态、输出/流量入口。
- 详情：原请求与脱敏规则、stdout/stderr、执行状态时间线、可确认的进程树、相关流量和产物；显示环境代次、缺失或截断。
- 用户/Lead 可按权限取消任务内命令；Worker 仅取消自己命令，helper 由父通过子任务取消。取消受理不直接显示已停止。
- 无“一键重放未知命令”。若以后允许重新执行，必须是新的明确操作、当前权限和新审计记录；本期不提供自动重跑按钮。
- 更新复用 TaskEvent；日志按字节/片段游标拉取，不把所有输出塞进 SSE、全局快照或浏览器内存。

默认展示脱敏信息，不收集完整环境变量或平台密钥。原始命令/输出可能包含任务材料，受任务权限和保留策略控制；记录实际脱敏/截断状态，不承诺任意字符串中所有秘密都能自动识别。

## 11. Pi 会话、输入、模型与配置

### 11.1 会话内容与确认

Pi SessionManager 是唯一会话内容权威；平台保存 session 归属、active leaf、confirmed_seq/hash、业务回执和输入状态。日志在 Runner 专属持久卷，对象存储保存确认备份与归档；不为每个 token 复制完整历史。

一会话只有一个有效写入者。同步 append 不自动等于 fsync；必须验证所选存储的持久化和确认边界。普通 subscribe 回调不能作为可等待的硬屏障。

工具前确认必要日志与准入记录；工具结果先持久保存再交 Pi 写入日志并确认。已发送工具结果未知不重放。日志有结果而 ACK 丢失时按原 ID/游标核对，不重复添加。

模型前也必须确认当前 journal、输入及业务回执。主会话通过公开 session.agent.streamFunction 组合包装，确认完成后调用原函数；确认失败返回 SDK 可消费的 error/aborted 终态流且上游请求数为 0，不直接 throw/reject 留下悬挂流。固定 Pi 版本的默认压缩复用该 streamFunction；主回合和自动/手动压缩都必须验证受限网关身份。包装函数不会继承 ModelRuntime 的私有 auth 标记，不通过 deep import 或复制私有标记维持认证；使用公开接缝完成身份绑定。Runtime 薄层是最终 live fence 拒绝点，包装器与入口共用 call/attempt 和一次派发关联；它不持 provider key、不解 SSE、不二次 token 计价。首版关闭 SDK cache warmer 和其他未接调用身份的后台模型路径；可能吞掉异常的提示 hook 不能承担唯一硬屏障。子会话同等语义由 G3 验证，不能以普通 subscribe 代替。

人工消息先入持久收件箱，确认进入日志后才显示已应用。普通 steer 在安全边界注入；停止并改计划先收尾旧执行。终态复盘另开只读用途会话，不恢复求解权限或自动重跑任务。

Runner poll 当前每秒重复短 DB 事务，后续单独小改优先复用 SSEDispatcher.subscribe 与 Repository.notify 的现 Task 通知，不新增总线。先登记订阅再读权威命令表；成功提交后通知（同事务 pg_notify 只在提交生效），通知只是唤醒，不作为命令/ACK 或推进 command_seq 的依据。读取/核验使用短事务，等待期间不持 DB 连接；按短许可续期边界及断连/漏通知有界回读，listener 未 ready 必须有有界回退、不能阻塞续租。先补此最小接缝，不重写控制循环。

### 11.2 模型准入与费用

本节以 2026-11-06 用户授权的费用阈值方案覆盖旧默认严格预留：目标是累计费用达到阈值后持久暂停/终止新工作，允许已在途调用继续产生费用及超额，不宣称每请求预留或异常重启后的绝对零损失。legacy CNY 计价、历史估算与原角色额度保持原合同；新 V1 不按 Worker 复制总预算。

agentgateway 1.7 standalone 是唯一上游 provider 连接、协议适配、provider 凭据、usage 归一化、USD cost 目录与原生 APIKey DB 预算执行者。可用官方 standalone Helm 在 K8s 单活部署，不能与 Gateway API 控制面配置混淆。Runtime 薄层只核当前 Task/binding/epoch/permit、确认日志、原请求字节与 call/attempt 一次派发关联；Task 原生模型 budget key 仅在可信 Runtime/网关侧，Runner 沿 binding/epoch 短 token，不接触该 key 或 provider key。

每 Task 一个稳定共享 key，使用不设置 window 的累计 USD 预算；Lead、Worker、helper、主回合、自动/手动压缩和 summary 等同 Task 模型用途共享，控制服务/Pod/epoch 或席位变化不重置累计。原生在响应结束后记费，跨阈请求仍完成，之后的请求可返回 budget_exceeded；平台同时拉取可信 budget status 补充阈值触发，不能等下一次 429 才停止派工。预算拒绝须有原生状态/日志来源证明，不能把一般 provider/rate-limit 429 或仅相同响应 body 当 Task 预算耗尽。Native 规则与 Admin API 见 [per-key 预算](https://agentgateway.dev/docs/standalone/latest/documentation/llm/cost-controls/budget-limits/per-key/)。

平台以稳定 accounting_source_id＋native_log_id 去重；前者是逻辑部署/持久 DB 命名空间，不是 PodUID、进程启动 UUID 或 Runtime epoch。原 attempt/Task key 用于关联与冲突校验，不能变更关联后把同一日志再计一次。费用不靠 Prom 累计或未核 webhook，budget status 快照不与明细相加；缺行/usage/cost/catalog 待核，已知零须完整证据，已确认费用/暂停不回退。Cost 的 best-effort 估算边界见 [Model costs](https://agentgateway.dev/docs/standalone/latest/documentation/llm/cost-controls/costs/)，不冒称供应商账单。

原生 USD 原值、来源和 catalog/部署版本保留。现平台 CNY 不能隐式 1:1：新 V1 需显式配置并冻结 USD/CNY 汇率、来源、时点、精度/舍入规则，将 CNY 阈值一次换算为原生 USD 阈值；展示保留 USD 与按该冻结汇率换算的 CNY。缺汇率不静默启动 CNY 预算，也不声称 CNY 保障；本任务不猜实时汇率。

达到阈值后沿现 stop/hold 控制持久停止新派工与新模型准入，停止、清理、费用对账仍可执行；暂停/恢复、显式追加阈值及多 Agent 公平控制由 P4 闭合，不增加第二 Agent 循环。首版单活；不能把快照恢复值当未落盘费用为 0。本轮固定 1.7.0 已证共享 key 两请求各 0.003 USD、合计 0.006 跨 0.005 阈值完成，后续 budget_exceeded 429 且 fake provider 零调用，另一 Task 不受影响。缺 usage/断流/普通 429 可 cost=0、error=NULL 而 token 全 NULL，缺 catalog 则 usage 齐但 cost=NULL，均待核。Native search/get 能取 stable log id/attrs，opaque cursor 按 completed_at/id 分页，不能用 started_at 水位漏掉晚完成；分页仍不证明所有未完成 attempt 已落行。SIGKILL 实测 counter 0.006 回退 0.003，等待 5.2 秒落库后重启保持 0.006，持久日志可按原 id 恢复；平台已确认费用/暂停不随 counter 回退。详细锁定版本、局部证据与多副本等未过门槛见 [本次调整报告](P3c-Agentgateway费用阈值调整-20261106-report.md)。

已发送断流保持执行/费用各自 unknown；本地连接断开不证明上游停止。不自动跨模型 fallback，不叠加 Pi/provider/gateway 多层重试；每次真实发送保留独立 attempt 和原生日志关联。任务/provider/platform 并发与费用阈值分别治理，完整公平队列仍为 P4/G5 后续，不能用一个已过预算例子宣称全闸门完成。

### 11.3 配置管理

配置按管理员部署能力、角色 Profile、任务选择、有效快照四层解析；服务端返回最终值与来源。模型、Skills、MCP、环境版本由 Task 固定。提示词保留既有“保存后在下一次模型调用前生效”的行为：以管理员已发布版本替换单份系统指令，记录该次调用版本，不重放既有工具、不因提示词变更扩权。父/子角色分别加载当前获准版本；紧急停用实时优先。

平台是网关唯一配置发布者，记录 desired/applied revision、内容摘要和 last-good；核对活动路由/策略后放行。发布失败暂停受影响新调用，验证回滚，不仅凭写文件成功显示已生效。

模型目录/路由只保一个受信可编辑来源，平台选型/角色引用、SDK snapshot、缓存均派生，不再独立 provider 发现或三处双写。动态原生资源采用 native hybrid＋DB（standalone Helm 的 database 模式），file-owned 基础资源不与同名 API 资源竞争。优先从原生 `/v1/models` 派生 context/max tokens/modalities/capabilities；缺字段省略，不补造能力。旧平台编辑入口迁成同一来源的受控发布/引用，旧存储停止写入后退出，见 [模型目录](https://agentgateway.dev/docs/standalone/latest/documentation/llm/api-types/models/)和 [配置存储](https://agentgateway.dev/docs/standalone/latest/documentation/setup/storage/)。Task 动态 key 须显式 lifetime/no window＋Block，不照抄工具的 30d/Audit 默认；创建 ACK 丢失按同 key/hash/name 读回，不能另发额度，产品接缝仍待验证。

business_manifest、MUTATIONS、schemas 与 REST 参数只从共享 DTO/必要的小元数据派生，保持领域验证一份；不为去重复造通用 registry/DSL。此项和 poll 通知复用分别列后续小改，本轮仅明确范围。

共享 MCP 与专业 MCP 必须声明实际执行位置、网络和工作区能力。继承 MCP 配置不意味着外部工具自动走本 Task VPN。CTF 工具优先通过已装工具镜像执行。

## 12. 停止、恢复与数据保全

### 12.1 停止顺序

1. 持久写停止范围，撤销该范围的认领、借位、模型、工具和提交新准入。
2. 全任务停止时冻结 Solver 新旧业务流量；仅保留规则允许的可信查询/关闭通道。
3. 并行取消 Pi、helper 宿主和已知远端命令；cleaner 不依赖 Lead 存活或剩余模型预算。
4. 核对会话、进程树/执行、采集封存、文件写入及已发生用量；无法确认的部分保持 unknown。
5. 上传必要证据、日志、命令和流量清单，确认可读；再回收 Sandbox、网络、Runner、卷和 Namespace。

局部成员故障只在能证明影响范围时局部隔离；无法证明后台进程归属则冻结共享 Task，不靠题目目录推断其他成员安全。仅费用待核而执行已清理，可以按原席位合同回收；费用待核记录与阈值 hold 保留，不补 0 或回退已确认累计。

### 12.2 接管与恢复

新控制者 CAS 取得新 epoch 后先处于 frozen：列出旧 Assignment/child、命令、模型、提交、创建操作和 Pod UID；使旧执行无法再取得许可；核对清理后恢复确认日志、输入与当前环境。

旧 Runner、MCP、网络或 detached 子进程可能跨控制服务重启存活，禁止沿用“旧 Python 协程已死”假设。强删 Kubernetes 对象或查询 404 不证明分区节点上的进程已经终止。

模型/工具/创建/提交响应丢失分别对账；没有证据不重发。创建使用可信 create_op_id 元数据查证；一次 list 为空不能证明原 create 未进行。

恢复 journal 用新的 epoch 工作副本及 CAS 引用；旧 Runner 释放卷之前不启动第二个写入者。工作卷保留用于故障保全；不把 Pod 重建当成命令内存恢复。

### 12.3 归档与保留

当前登记证据、附件、会话、命令、流量和回执是必须保全对象。延续已有按登记材料归档语义，不默认打包所有下载缓存；临时工作区保留用于故障恢复和诊断，按任务明确期限回收。

workspace PVC 默认不随 Sandbox 自动删除；journal 独立。正常结束确认归档后再删卷；归档失败保留明确的 claim 和 cleanup_pending。存储类 reclaimPolicy 和底层回收实际状态可查，删除 PVC 不冒充数据已擦除。

续跑新一轮与故障恢复分开：新一轮按照既有合同恢复已登记产物；恢复原运行先核对其所有未决副作用。历史、费用和验收回执不随代码退役而删除。
