# 任务 M0 · 工程基座

依据：`docs/design/黑板系统开发方案.md` 第 1 节（仓库结构）、第 4 节 M0、第 9 节（配置）；`docs/design/黑板系统实现架构.md` 第 3 节（数据模型）；`docs/design/黑板式探索架构设计.md` 第 3、8、9 节。

先阅读根目录 `AGENTS.md`。在 `main` 上切出分支 `m0` 开发。

## 目标

建立一个可以持续开发的空骨架：依赖管理、基础设施容器、统一的检查命令、共享数据模型、配置加载和默认 Agent 配置。**不实现任何业务接口、数据库迁移、前端或执行环境**，这些属于后续里程碑。

## 任务

### 0.1 仓库骨架

- 按开发方案第 1 节建立目录。本里程碑只需要以下 Python 包有真实内容，其余目录放一个简短的 `README.md` 说明用途即可：
  - `packages/contracts`（包名 `bbx_contracts`）
  - `services/blackboard`（包名 `bbx_blackboard`）
  - `services/agent-runtime`（包名 `bbx_runtime`）
  - `services/envd`（包名 `bbx_envd`）
- 根目录 `pyproject.toml` 作为 uv workspace，包含以上四个成员；四个服务包各自依赖 `bbx_contracts`。
- 每个服务包目前只需：包结构、一个 `settings.py`（见 0.5）、一个最小测试。
- `.python-version` 设为 3.12；如果 uv 无法获取 3.12 解释器，改用本机 3.13 并在报告中说明。
- ruff、pyright（standard）、pytest 配置放在根 `pyproject.toml`。
- `.pre-commit-config.yaml`：ruff format、ruff check（pyright 太慢，不放进 pre-commit，只在 `make check` 中跑）。
- `.gitignore`：Python、Node、`.env`、`.venv`、缓存、`*.log`、本地数据目录。
- `web/` 只放 `README.md`（前端在 M1-W 搭建）。

### 0.2 基础设施容器

`docker-compose.yml`：

- `postgres`：镜像 `pgvector/pgvector:pg16`；数据卷；healthcheck；主机端口 `127.0.0.1:55432`（避免与本机已有服务冲突）。
- `minio`：镜像 `minio/minio`；数据卷；healthcheck；主机端口 `127.0.0.1:59000`（API）与 `127.0.0.1:59001`（控制台）。
- `minio-init`：一次性容器（`minio/mc`），等 minio 健康后创建 bucket `blackboard`，幂等。
- 定义网络 `internal` 与 `exec`（`exec` 为 `internal: true`），本里程碑只有 postgres 与 minio 接入 `internal`。
- `blackboard`、`agent-runtime`、`egress-proxy` 在后续里程碑加入；本里程碑不要写占位服务。
- 连接参数全部来自 `.env`（compose 的变量替换），`.env.example` 给出本地开发可用的默认占位值。

### 0.3 统一命令

`Makefile`：

| 目标 | 作用 |
|---|---|
| `make up` / `make down` | 启动 / 停止基础设施容器（`down` 不删数据卷；另提供 `make clean-volumes` 删除数据卷） |
| `make fmt` | ruff format + ruff check --fix |
| `make lint` | ruff format --check + ruff check |
| `make typecheck` | pyright |
| `make test` | pytest（全部 Python 包） |
| `make check` | lint + typecheck + test；不访问网络、不需要 Docker 运行 |
| `make schemas` | 导出 contracts 的 JSON Schema 到 `packages/contracts/schemas/` |

### 0.4 共享数据模型 `bbx_contracts`

用 pydantic v2 定义跨服务共享的数据结构，字段名、枚举值与设计文档一致（设计文档中的中文说明写进字段 `description`）。

至少包括：

- 枚举：FactKind、FactStatus、EvidenceType、IntentStatus、IntentResult、AcceptanceStatus、Verdict（met/unmet）、TaskStatus、AgentTaskType（explore/derive/close）、CloseMode（judge/final）、AgentStatus、EndReason、EventType（实现架构 3.3 的全部事件类型）
- 对象：Evidence、Fact、Intent、IntentNote、AcceptanceItem、AcceptanceItemState、VerdictItem、Usage（cache_hit_tokens、cache_miss_tokens、output_tokens、reasoning_tokens、cost）、Budget（max_concurrent_agents、max_cost、max_minutes）、Params（设计文档第 9 节全部参数及初值）、TaskSpec（goal、domain_context、acceptance、budget、params 覆盖、agent_profile、egress_allowlist）、AgentRun、Event
- 回执：ExploreReceipt、DeriveReceipt、RefusalReceipt，以及解析用的判别联合类型
- 写入请求：PostFactRequest、PostIntentRequest（含 claim）、ReleaseRequest、SubmitCloseRequest
- AgentProfile：models（按任务类型：provider、model、base_url、reasoning_effort、price）、params、prompts（模板文件路径）、exec_image、exec_resources、privileged_allowlist

边界：contracts 只做**结构与单字段校验**（必填、枚举、长度、数值范围）和少量同一对象内的一致性校验（例如 `resolves` 非空时 `result` 必填、Intent 的五个必要字段非空）。跨对象的规则（引用是否存在、是否 holder、争议状态计算等）属于 M1 的黑板领域层，这里不实现。

测试：每个模型至少覆盖一个合法样例与一个非法样例；回执联合类型能正确区分三种回执；JSON Schema 导出成功。

### 0.5 配置与日志

- 每个服务一个 `Settings`（pydantic-settings），从环境变量读取开发方案第 9 节列出的、与该服务相关的变量；密钥字段用 `SecretStr`。
- `.env.example`：列出全部变量，只放占位符（例如 `DEEPSEEK_API_KEY=replace-me`）。
- 结构化日志：一个小的共享辅助函数（放在 contracts 或单独模块均可，保持简单），输出 JSON 行，包含时间、级别、服务名、消息与额外字段。
- `OTEL_ENABLED` 开关（默认 false），本里程碑只读取，不接入。

### 0.6 默认 Agent 配置

`profiles/default/`：

- `models.yaml`：explore / derive / close 均为 provider `deepseek`、model `deepseek-flash`、base_url `https://api.deepseek.com`、reasoning_effort `high`；价格表字段（currency、cache_hit_per_m、cache_miss_per_m、output_per_m、off_peak）**留空（null）并注释"按 DeepSeek 官方价格页填写"**，不要猜测价格。
- `params.yaml`：设计文档第 9 节全部参数的初值。
- `prompts/`：放 `explore.md.j2`、`derive.md.j2`、`close.md.j2` 三个文件，本里程碑只写一行注释说明将在 M2 填入设计文档 8.1–8.3 的提示词。
- 一个加载函数：读取 profile 目录并用 `AgentProfile` 校验；测试加载 `profiles/default` 成功，并能识别出价格表未填写（给出明确的提示，而不是报错崩溃）。

## 完成标准（请实际运行并在报告中给出结果）

1. `uv sync` 成功。
2. `make check` 全绿。
3. `make schemas` 生成 JSON Schema 文件。
4. `docker compose config` 通过校验。
5. 如果沙箱允许访问 Docker：`make up` 后 postgres 与 minio 均为 healthy，bucket `blackboard` 存在；然后 `make down`。如果不允许，在报告中写明，并给出用户需要执行的验证命令。
6. 分支 `m0` 上有若干逻辑清晰的提交；工作区干净。

## 不要做

- 数据库迁移、任何 HTTP 接口、SSE、MinIO 读写逻辑（M1）
- 前端脚手架（M1-W）
- envd、执行环境镜像、Docker SDK 调用（M2）
- 调用任何真实模型 API
