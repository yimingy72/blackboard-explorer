# Responses 网关工具续传失败修复

2026-10-19，本地任务 `d3c25dac-8557-4261-af18-56bab7a9b23d`。工作树 `/Users/yym/bbx-wt/platform-performance-audit`，分支 `fix/progress-curator-response`；保留此前未提交改动。

## 确认原因

任务模型为 `openai_responses / workbuddy-ai/deepseek-v4.1-flash`。第一次模型请求及两个 execute_command 均成功，随后请求在1ms内抛出 ChatClientInvalidRequestException；重新激活后12ms内再次失败，最终因“种子无法起步”终止。

从持久 Session 取出完整的推理/调用/结果组，在不发HTTP请求的情况下复现：MAF 1.19.0 / OpenAI adapter 1.14.4 的无状态 Responses 校验需要可续传的加密 reasoning，而网关只给出451字符明文、没有 encrypted_content。两次失败都不是模型地址、认证、网络、目标描述或实际工具执行错误。

## 实现

- 复用 MAF 公开 annotate_message_groups 和 GROUP_ANNOTATION_KEY，在请求副本上按原子组处理。仅将完整配对、明文且无法原生续传的推理/工具组转换为确定性的已执行工具观察，保留调用ID、名字、参数、完整结果及原助手正文。
- 图片和富结果保留为原生 Content，不转为base64文本；记录原组/消息来源。持久 Session 与原始推理不变，不清空历史、不重放工具、不伪造加密数据、不启用服务端存储，也不切换API协议。
- 合法加密组不改写；缺失、重复、孤立、混合加密及不支持的hosted工具组仍交由MAF拒绝。带有效 reasoning ID 的空字符串、空值和纯空白片段同样支持完整工具组投影。该机制恢复可见执行依据，不声称恢复提供方内部推理状态。
- 模型连接新增 auto/native/tool_observations 三种策略，界面使用目录驱动的Select。默认auto对官方OpenAI与Azure保留原生模式，自定义Responses网关在需要时使用工具观察。模式值保存前校验，运行时拒绝非法值。
- 普通、CTF、复盘和整理共用客户端，兼容不依赖特定任务、题目、模型名或靶机套路。日志仅记录组数和消息数。

## 补充：空白推理片段与黑板增量

初版发布后恢复原任务，运行约53分钟，产生29个Fact、22个Intent，随后再次失败。agent-7、19、20的错误均为6–11ms内抛出的本地请求校验异常，没有上游HTTP状态或request_id，不能据此认定为模型内容审核或网络问题。

离线检查三份失败会话发现：最后的工具组调用和结果完整，但网关 reasoning 只有一个空格。旧投影要求可见的非空推理文本，导致完整工具组被跳过。现仅要求有效reasoning ID、完整唯一配对的工具证据；推理文本是否为空不再决定能否转换。缺ID及未完成组仍保持MAF校验。

独立代码复核还发现工具结果的 `result` 与 `items` 可能不同步，投影会漏掉运行时追加的黑板更新。已在共享 `append_board_update` 同步二者，图片、文本和结束标记均保留；投影同时兼容旧checkpoint中的不同步数据。加密原生和明文网关路径都覆盖，不重复黑板增量、不丢图片。

客户端明确标记本地失败阶段 `request_validation`，普通黑板及CTF错误提示显示“本地模型请求组装失败”，避免将尚未发送的请求误标为模型服务拒绝。诊断仍仅保留固定类别与安全计数。

用户随后明确要求“无需继续跑，修好即可”。停止请求返回任务已经failed；当前没有运行中或交接中的Agent，不再恢复任务、不追加预算、不再调用真实模型。
