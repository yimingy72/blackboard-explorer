# 独立 CTF 比赛版：方案与开发准备

任务编号：`CTF-standalone-20261120`。状态：主代理与用户指定子代理共同讨论形成的设计稿；本轮不表示独立程序已经实现或部署。

用户已确认：继续准备独立比赛版；删除“所有题目必须死磕”的策略。此前 Lead/同级 Worker、首次分配后续自选、援助、题内 Fact/Intent、实时 steer 和跨题会话复用继续保留。

用户后续要求最大限度利用容器、尽可能多开启 Worker，并明确选择：发现可并行、未认领的独立方向时，调度器自动增加援助，仍遵守每题总计 10 人。该决定覆盖此前“困难题凑齐两人后只能等待 Worker 主动申请”的限制。

最新人数与权限决定：初始创建 10 个 Worker；Lead 可以读取真实系统占用，并请求创建更多同级 Worker。新增成员仍属于同一个 Worker 池，不恢复 helper 子层级。Lead 获得增员权限，原有“Lead 不得创建 Worker”的限制在独立版中撤销；没有顺带授予删除成员或直接任意发消息权限。用户同时明确要求避免增员过多导致卡死，因此增员必须由本地代码做实际资源准入。

## 1. 交付目标

交付一个可独立打包的比赛镜像，在赛事提供的容器里直接启动求解程序。首版没有 Web 管理站，不依赖本平台的 PostgreSQL、MinIO、Kubernetes、OpenSandbox、模型代理或账号服务。现有完整平台继续保留，不通过先删除原项目代码来实现精简。

推荐一个 Node.js 主进程承载 Lead 和多个 Worker 的 Pi SDK 会话，SQLite 保存业务状态，工作目录保存会话、日志和证据。求解命令是该容器内的子进程。多个 Worker 不对应多个 Docker 容器，也不要求每人启动独立 Node 进程。

选择此方案是为了减少部署依赖和进程通信；尚未实测其速度或内存收益。不为统一语言重写全仓库，只迁移本次确实使用的规则与工具。Python 保留为解题工具环境，不再承担一个平台服务。

## 2. 保留与剥离

| 范围 | 首版处理 |
| --- | --- |
| Pi 会话与模型工具循环 | 直接使用固定版本的 `createAgentSession`、`SessionManager`、自定义工具和 steer；正常换题复用会话 |
| 协作核心 | 移植已验证的领取、主援、难度、核验、计时、Fact/Intent 语义，并以原有场景作为回归依据 |
| 持久化 | SQLite 事务与一个本地写入者；提交后通知会话，重启读取未完成状态；不需要远程租约/投影凭据/每次工具的跨服务许可 |
| 证据与日志 | 本地不可变文件快照、哈希、JSONL 会话与工具记录；保留作者、题目、工作代次、模型和工具关联 |
| 命令执行 | 使用 Pi 工具接口或薄包装直接管理本地命令和文件；保留输出、退出、超时及子进程收尾，不依赖特权 cgroup 挂载 |
| 模型接入 | 按官方托管配置访问允许的供应商；保留实际用量、超时、退避与异常恢复，不带模型管理页面和平台费用结算服务 |
| 赛事接入 | 一个薄适配器负责目录、启动、提交、关闭、状态和整场结束；不再让模型通过通用 HTTP 自行猜协议 |
| 不进入比赛包 | 普通黑板模式、Web、账号/RBAC、平台发布中心、Kubernetes 控制器、OpenSandbox 服务、VPN、抓包、旧 helper、旧平台历史迁移 |

当前 `native_worker_pool.py`、`collaboration_board.py`、`collaboration_review.py` 和 `worker_board_updates.py` 混合了业务逻辑与 PG/HTTP 依赖。纯协作文件约 180 行不代表全部核心；Fact/Intent 校验、候选核验、调用归属和迟到结果还在其他模块，必须按行为完整迁移。

Pi SDK 本身已支持本地工具和自定义工具。新入口不伪造一个 `HttpPlatform` 去兼容所有旧协议，而是直接连接本地状态与 SDK；不整体复制旧 Runner 的租约、远程 journal confirm、模型许可和 helper 宿主。

## 3. 取消死磕后的最小闭环

Lead 可通过题目黑板决定暂缓或恢复未完成题目。Worker 可提出暂缓建议并记录事实、已尝试方向、阻塞及建议；Worker 不直接修改自己或别人的状态。首版仍由 Lead 统一决定题目顺序，不新增调度模型或强制定时换题规则。

题目阶段使用 `pending / solving / reviewing / deferred / completed`；执行收尾是独立的运行事实，不用再给业务增加一套复杂阶段。成员状态由协调器维护。暂缓规则为：

1. 保存原因与进展，停止为旧工作发起新的求解动作；实际结束旧模型/工具执行并收尾子进程后，逐个释放成员。
2. 需要释放在线环境时，调用官方关闭接口；确认已关闭才释放环境名额。关闭结果未知继续占位并核实，不能因此开出第四个在线环境。
3. `deferred` 不立即回到可领取集合。Lead 根据分值、剩余时间、阻塞变化及已有成果显式恢复后，才进入排队。避免暂缓后马上被同一 Worker 再次领取。
4. 事实、意图、脚本、候选和会话历史保留；已释放成员不再占住旧 Intent。记录原认领与尝试，恢复时允许重新认领，不伪造方向已成功或整题已完成。
5. 环境重开可能改变地址和 flag。每次环境有独立代次；旧证据保留其来源，新的工具使用新地址，旧候选不能未经核实直接当作当前答案。
6. 有提交结果未核实时先对账，不因为暂缓直接关环境、丢弃回执或把 unknown 当错误答案。
7. 所有剩余题都被暂缓时，协调器向 Lead 提供可恢复列表；“没有当前可领取任务”不等于完成，也不等待一个永远不会出现的新题事件。

不设置“做满 N 分钟必须放弃”。累计解题 30 分钟仍沿用已确认的两分支：无实际援助时自动开放/保持至少一个名额；已有实际援助时只提醒主责研判。累计排除 pending、reviewing、deferred，恢复后续算；它不是换题或失败阈值。赛事四小时截止时间始终连续，不因暂缓或进程恢复延长。首次分配标记不会因暂缓或恢复重置；重新空闲的已工作 Worker 继续自主领取。

普通待核验仍用已确认的 steer，不加模型 ACK。明确暂缓导致的执行撤销与收尾是另一种生命周期操作；消息已插入不等于实际执行已结束。

## 4. 核验与得分

Lead 选择候选和证据并授权提交，提供一个完整的“提交并处理回执”工具。程序按真实回执记账，避免成功后再叫模型判断一次同一个成功布尔值。

- 明确接受：保存回执和依据，按本届单 flag 合同更新题目完成，通知团队并在执行实际结束后释放。赛事自动释放解出的题目环境，不再额外重复关闭。由 Lead 发起的提交操作承担验收授权，不把提交权限给 Worker。
- 明确拒绝：保存返回原因 Fact，通知原团队读取反馈继续；只陈述赛事实际返回的信息，不编造技术根因。Lead 仍可补充分析。
- 结果未知：保持待核实，按官方状态/幂等合同对账，不当作拒绝、不重算得分、不盲目重放提交。

进度以 `correct_flag_count`、`is_completed` 及提交的 `correct` 等真实字段为准，不能用 `awarded > 0` 判断通过。`points/total_score` 是题目分值，`awarded` 是本次接受得分，`cumulative_score` 是整次 attempt 总分；不得当作单题累计再求和。驳回或 testing 回执中的 0 不覆盖此前已确认的总分。`409 duplicate` 不重试加分，使用题目列表核对完成状态。

整场结束只能基于已核实的赛事终态、时间截止或明确的结束决策。单个 Worker 正常结束一轮、短时 API 失败、全部暂缓或一次提交失败都不触发整场结束。禁止在主程序 `finally` 或一般异常分支无条件调用赛事 `finish`。

## 5. 赛事约束与资源

已核对[正式规则](https://alidocs.dingtalk.com/i/nodes/oP0MALyR8k7rRMpRtMNl6D2383bzYmDO)和[正式公告](https://hanqing.chaitin.net/topic/3720)：4 核/6 GiB/10 GiB，在线题目环境最多 3 个，离线题不占额度，每队一次、每次最长 4 小时；总分优先，同分比有效耗时。赛前仍可能更新。

环境名额、Worker 会话数量、模型在途请求和重型本地工具并发分别管理。初始 10 个 Worker 是起步数量，不是全局上限。不能把三个题目环境误写成三个 Worker 上限；Lead 根据可推进工作和真实资源请求增员，本地代码决定当下能实际创建多少。沿用每题最多 10 人、每人最多 3 条 Intent、困难初始主援各一人；简单/中等单人起步，存在独立方向时同样可自动增援。

依赖与工具在构建时安装，启动不下载模型目录或工具。遵守赛事实际模型出口、注入参数和代理/证书合同；不恢复本平台的 VPN、抓包和逐任务网络检验。

日志与工具输出落盘并管理体积；重型任务按可用资源执行，避免单工具占满整个容器。SDK 重试和外层调度不能形成重复重试放大。状态可在同一保留工作目录内恢复；容器被重建后是否保留目录，以赛事合同为准。

### 5.1 更多有效 Worker

1. Worker 是轻量记录与长期 Pi 会话；启动准备 10 个，只有获得工作才激活模型，空闲不轮询。优先复用现有空闲会话，确有有效工作超出当前团队能力时向 Lead 提供资源与工作缺口；由 Lead 请求增员。正常跨题保持会话和工具上下文，不为每个 Intent 创建 Agent。
2. 新题优先援助。先让本题真正可开始另一方向的现有成员工作；仍有独立方向可并行时，自动增加目标援助人数、通知全局空闲 Worker，最多达到每题 10 人。援助目标自动增长不等于调度器绕过 Lead 不断创建新 Worker。
3. Intent 的 3 条持有上限不是 3 个同时执行槽，不能按 `ceil(Intent数/3)` 估算所需人数，也不能因忙碌 Worker 尚未拿满 3 条就阻止其他人并行。
4. 在提出 Intent 的同一次写入中，允许原 Worker 标注可并行及必要依赖。协调器核对依赖就绪、已有认领及在途结果，不凭文字不同认定独立性，也不增加一个管理模型来审核。多个相同请求不重复增加人数。
5. 没有有用方向时保留待命记录，不为增加人数制造模型调用。新增人数以实际工作吞吐和可推进方向为依据，不把所有题一律填满 10 人。

### 5.2 最小资源调度

一个本地调度器管理模型请求队列和本地工具队列，不引入通用分布式调度系统。

- 模型请求：按实际 provider/凭据共享在途计数与退避。逐步增加并发，观察完成吞吐、延迟、429/超时和 Retry-After；限流时减少新请求并错开重试，恢复后再扩。进程不因单个 provider 暂时失败退出。
- 本地工具：网络等待、短读写与 CPU/大内存任务分别观察；控制的是同时运行的资源消耗，待执行工具排队不等于关闭 Worker。读取容器实际 CPU quota/内存用量，不按宿主 CPU 总数盲开线程。
- 线程：避免每个 Python/数值工具都自动开满所有 CPU。按当时可分配 CPU 为常见线程库传入合适配置；资源空闲时允许单个任务使用更多份额，不固定让每个任务永远单线程。
- 主控响应：Lead 的提交、回执核对、释放环境和状态更新及时执行；空闲份额可给求解使用，不为主控永久闲置固定 CPU。
- 内存：同时考虑 Node 会话、模型请求序列化、子进程和文件缓存。新增工作保留由实测峰值确定的余量；出现压力先停止扩容和新重型工具，不抛弃现有上下文或让 OOM 成为调度方式。
- 状态与 I/O：SQLite 短事务，文件/模型/工具 I/O 不占写锁。工具完整输出写文件，进入模型的内容以必要摘要和引用为主；避免向所有 Worker 复制大文件或整份黑板。
- 提示词：共享稳定的公共前缀，工具说明按任务需要提供，增量同步事实。SDK compaction 会额外调用模型，不能当作免费、即时的内存回收。

SDK 1.5.0 的 SessionManager 将完整历史保存在 `fileEntries/byId`，在 `message_end` 同步追加持久消息，不是每个 token 都写盘；压缩改变模型上下文但不删除全部历史内存，压缩请求也必须进入统一模型队列。cache warming 关闭。多会话下需测量事件循环延迟和长历史成本。首版优先减少冗余日志/巨型工具结果，不未经测量就 fork SDK 或增加多个 Node 宿主。

共享只读工具 schema 和模型目录，各会话的历史、输入队列、活动工具与工作目录仍独立。不得通过全局 `process.chdir` 或逐 Worker 修改 `process.env` 设置上下文，命令使用自己的 cwd/env。Pi 默认可并行执行同一响应中的多个工具，而旧平台明确使用 sequential；首版保留顺序语义，以多个 Worker 实现并行，后续仅对已验证互不依赖的调用另行优化，不把默认差异当作扩容收益。

### 5.3 验收指标

使用隔离的 4 核/6 GiB 容器，在相同假模型响应、同一组任务/工具负载下逐级增加 Worker，记录有效任务吞吐、模型等待、工具排队、CPU throttling、容器内存峰值、事件循环延迟、磁盘增长和失败率。模型延迟高、CPU 未满不等于程序浪费性能；更多 Worker 若使完成吞吐下降则不是优化。

先分别测 1/8/16/32/64 个持久 Pi 会话的准备与合成历史开销，证明低开销会话承载；随后必须测真正执行工具和模型流式响应的组合负载。前者不能作为完整比赛版支持 64 个重型 Worker 的证明，也不能用来预报真实比赛成功率。

### 5.4 防止扩容把容器拖死

实际准入顺序、初始工程参数和故障验收详见[扩容与卡死保护](CTF-standalone-resource-guard-20261120.md)。Worker、模型内存与工具启动共用同一份资源预约账本，防止几条通道同时花掉同一份空闲资源；不能只在创建 Worker 时检查内存。

Lead 获得资源快照和增员工具，但快照只是信息；实际创建时由本地协调器重新检查资源，不能信任模型口述“资源够用”。增员以目标团队人数表达，重复请求幂等；只允许一批准备中的增员，分批落地并观察实际增量，不一次并行准备大量会话。资源不足时返回当前人数、暂未创建数量和原因，不把排队记录冒充已启动 Worker。

资源监控是轻量本地代码，不额外调用模型；黑板仍由事件触发。监控容器内存/压力、Node heap 与事件循环、受管子进程、CPU throttling、文件系统余量和模型失败/等待。CPU 满载本身不视为卡死；健康的高负载应继续工作。

| 状态 | 处理 |
| --- | --- |
| 正常 | 有独立工作、模型吞吐和内存余量时接受 Lead 增员；实际准备完成才计为可用 |
| 出现压力 | 立即停止扩员及新高消耗工具启动；已有工作继续，模型/工具请求排队；先回收确认 idle 会话的内存缓存，保留同一 session ID 和日志 |
| 持续恶化 | 停止启动额外模型请求，保留提交/回执等必要处理；识别异常增长或无进展的受管工具，先保存记录，再取消对应执行并报告，不清空整个黑板 |
| 资源恢复 | 经过持续稳定观察再恢复准入；恢复线低于暂停线，避免反复扩容/收缩；不立即释放全部积压请求 |
| 宿主失去响应 | 独立于 Node 事件循环的轻量 watchdog 根据连续失联判断；确认旧宿主及受管执行结束后才恢复，保留截止时间与未决回执，不自动调用 finish |

容量预算同时为新会话的后续上下文增长、在途模型请求、工具峰值和主控收尾保留空间，不能使用空会话的平均 RSS 直接除出一个人数上限。首轮压测可从容器内存 80% 暂停新增、降至 70% 且稳定后恢复的工程参数起步，再用实际峰值和可回收文件缓存调整；这些不是杀掉已有 Worker 的阈值。紧急处理还必须结合实际内存压力及增长来源，不能单凭一次文件缓存升高就误杀任务。

watchdog 不按一次 GC、一次大日志写入或正常长工具执行判死。主控心跳与工具进度分别记录；初始采用秒级心跳和连续数十秒无主控响应的判断窗口，最终由故障注入测量校准。PID 需结合进程启动时间/运行代次核对，避免误杀复用 PID。重启有退避，恢复先核实未决提交/命令，不重新执行全部历史副作用。该小型监督进程是运行保障，不是新增 Agent，也不恢复分布式租约/高可用系统。

### 5.5 工具清单与 Worker 提示词

实际镜像核对、补齐优先级及提示词模板见[工具补齐与 Worker 提示词](CTF-standalone-tooling-20261120.md)。已实测现有镜像的 Pwn/逆向/数学等核心能力，但 nmap/sqlmap、部分 Python 库、音频二维码工具和通用字典仍有缺口；新镜像须补齐并重新验收，不能宣称当前已全部安装。

镜像构建时生成实际工具 manifest，记录类别、可执行路径或 Python/Ruby 环境、版本、离线烟测结果及必要用法入口。构建后以正式 Worker 的 UID/PATH 执行烟测；仅写进 Dockerfile 或能找到文件不算已可用。

Worker 系统提示词包含精简分类清单、解释器/虚拟环境的准确路径、共享目录和查询完整 manifest 的方法；任务需要时再读取对应工具用法。已安装但依赖/符号/字典缺失的能力必须注明，避免模型盲用；不向每个模型回合重复塞入完整工具手册。Lead 同样可以读取清单和资源占用。

参考群内的 [Des-CTF-Knowledge](https://github.com/Dest1ny-Sec/Des-CTF-Knowledge) 的工具说明与脚本依赖确定通用工具缺口，来源包括 `CTF常用脚本及工具/SCRIPTS-INDEX.md`、`工具使用/` 和音频/图片工具索引。只据此整理工具需求与通用使用说明，不将整包历年题目答案作为默认比赛材料；来源中的 Windows GUI 工具优先寻找适合无界面 Linux 的实际替代。

## 6. 官方接入核实

已完整读取[官方夺旗猫接入文档](https://cyber-arena.chaitin.cn/manual?tab=participant)及[普通手册](https://cyber-arena.chaitin.cn/manual)。只读取文档，没有发起真实 attempt。

平台注入 `/challenge/cyber_arena_help.md`、同内容 `CYBER_ARENA_HELP_MARKDOWN` 和 `ARENA_SOLVER_TOKEN`，不注入 prompt，也不从 transcript 自动提交答案。程序需读取当前 attempt 的帮助和身份，自行启动 Lead；不能等待平台主动发送聊天输入。

帮助中的 `ARENA_SOLVER_BASE_URL` 与 `BENCHMARK_BASE_URL` 指同一 per-attempt 接入地址；不要缓存旧 attempt 的地址或 token。请求使用 `BENCHMARK_TOKEN` Header，或官方接受的 Bearer。不能假定模板里每个字段都另外以独立环境变量注入。日志不记录 token。

以下路径相对于实际接入地址，属于正式求解 HTTP 接口，不是账户 `/v1` API，不提供求解 MCP：

| 动作 | 已确认接口与语义 |
| --- | --- |
| 列题/核对进度 | `GET /openapi/v1/challenges`；读取实际分值、进度和 container 字段，不发明 `/status` |
| 开始题目 | `POST /openapi/v1/challenges/start?unique_code=...`；离线题也必须 start，pending 时可重试 |
| 提交 | `POST /openapi/v1/challenges/submit`，body 为 `unique_code`、`flag` |
| 关闭环境 | `POST /openapi/v1/challenges/close?unique_code=...`；accepted 会自动释放，rejected 不关闭环境 |
| 题面与附件 | `GET /openapi/v1/challenges/files?unique_code=...`；沿返回的真实 path 获取，不猜附件拼写 |
| 结束整场 | `POST /openapi/v1/challenges/finish`；明确完成/结束才调用，不放进通用 finally |
| 当前帮助 | `GET /openapi/v1/challenges/help`；使用本次 attempt 文档 |

`409 environment_limit` 的 `detail.challenges` 给出占用者；`409 challenge_not_started` 先 start；`409 duplicate` 对账不反复提交；`409 invalid_state` 按真实 message 区分结束和名额问题；`503 resource_unavailable` 短时退避或调度其他可用工作。`404 task_not_found` 是身份缺失/无效，不能当作没有题目；`404 challenge_not_found` 不继续操作该题。模板中的题数和分数不是本次真实题目数据，不硬编码。

仍需在发布前核实：镜像架构、正式入口命令、额外模型配置变量与代理 CA、工作目录挂载/重建保留规则。两份手册未明确这些内容，不猜常见 `OPENAI_*` 或证书变量名。它们不阻塞本地核心和模拟合同开发，但未核实前不宣称可直接参赛。

## 7. 最小实施顺序

| 阶段 | 交付 | 完成依据 |
| --- | --- | --- |
| S0 | 官方接入合同、最小目录清单与设计修订 | 参数来自原文；原有死磕条款已被覆盖；不提前宣称可参赛 |
| S1 | 本地黑板和调度核心 | 首次分配/后续自选、援助、Intent、核验、暂缓恢复、版本和幂等用假执行验证 |
| S2 | Pi 会话和本地工具 | 真实 SDK 加假 provider 验证稳态会话、steer、命令输出、进程收尾、重试和异常恢复 |

| S4 | 资源与提交前验收 | 4 核/6 GiB 下逐级增加 Worker，测有效吞吐、内存/事件循环/磁盘与 CPU throttling，覆盖模型限流、API 失败、工具超时和退出 |

暂定比赛包位于 `services/ctf-standalone/`，只携带需要的 SDK、代码、配置和预装工具。跨服务共享结构仍遵守仓库 `packages/contracts` 规则；独立版的内部存储不增加第二套通用平台合同。

## 8. 必须保住的验收

1. 不启动原平台，单容器能完成假赛事的取题、领取、求解、提交、释放和结束。
2. 新题优先援助、主责唯一、每人一题、10 人/3 Intent、所有状态由协调器更新。
3. Fact/Intent 校验、作者与 holder、文件版本、同题同步和失败核验事实完整；不只测试队列能取出题。
4. 两题复用同一 Worker 会话；旧通知、旧候选和旧工具结果不污染新工作或新环境。
   同一旧/空闲上下文的模型响应即使先成功领取新题，其后工具也不能借用新的工作身份；消费领取结果后的下一次模型请求才采用新 Assignment。
5. 任一同题成员可提交候选；Lead 授权提交；重复/未知回执不会重复计分或误判错误。
6. 待核验 steer 不要求额外模型 ACK；暂缓必须完成旧执行收尾才释放成员。
7. 三个在线名额已满、关闭 unknown、全 deferred、恢复后环境地址变化均有可推进的明确路径。
8. Agent 回合结束、模型 429/超时、API 503 和普通异常不会提前结束整场运行；退出清理不自动调用赛事 finish。
9. 状态、候选、调用日志在同一工作目录的进程重启后可回读；未决副作用先对账，不把恢复当作重跑全部命令。
10. 包含运行记录和复现方法，不以假模型通过推断真实比赛成功率或性能提升。
11. 独立方向自动增援不要求现有 Worker 拿满 3 条 Intent，仍遵守新题优先、每题 10 人及依赖就绪；同一事件重放不超招。
12. 模型队列与工具队列独立，网络等待期间仍可推进其他任务；扩容不会把 429 放大为重试风暴，不因追求 Worker 数量提前 OOM。
13. 初始 10 个 Worker；Lead 增员的重复、并发、过期资源快照和部分准备失败不会多建成员。压力下拒绝/延后新增，恢复时逐步放行。
14. 以受控内存增长、线程超卖、磁盘增长和宿主无响应注入验证保护；普通长工具与正常 GC 不误触发整场停止；没有 watchdog 重启风暴。
15. 最终镜像中的实际工具烟测与 manifest 一致，Worker 提示词引用正确环境；清单不包含仅在构建机存在的工具。

## 9. 协作结论

主代理与 `standalone_ctf_partner` 已就单 Node 宿主、直接 Pi SDK、本地 SQLite、保留核心业务验证、Lead 单次授权提交、暂缓后的真实释放与不误结束比赛达成一致。后续按用户允许并行的要求，由 `resource_guard_design` 与 `tool_manifest_design` 分别完善资源保护和工具/提示词，主代理复核官方合同、SDK 输出实现与实测证据后汇总。官方接入核对结果见第 6 节。初始 10 人、Lead 增员、自动援助和性能保护已纳入第 5 节；不以 CPU 100% 或空载会话数代替有效吞吐。

本轮只完成设计与准备；原平台的冻结任务、运行中会话、数据和线上部署不变。下一阶段按上表实施，不将一个骨架或某个工具跑通称为完整比赛版。
