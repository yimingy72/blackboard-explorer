## 1. 审核结论

三路第二轮审核已通过按 P0/P1 开始实施，保留“平台业务控制＋Pi SDK＋agentgateway＋OpenSandbox/Kubernetes”的整体方向。审核前旧稿不能直接用于全面替换：题目级 Intent/Fact、Lead-only 建题、共享公告、多 Flag 事件验收，以及可归属流量和完整命令登记尚未实现；旧恢复/WIP 与新进程边界也有冲突。新方案已收敛这些合同，后续仍须实际接缝验证，不能直接发布完整能力。

本轮收敛了实际默认路线：

1. Runtime 继续是现有平台内部运行模块；题目、配置、预算和事件仍由现有数据库/业务服务管理。
2. 一个共享业务 MCP 按可信调用身份授权；每 Task 单独的 Sandbox MCP 绑定租户；不按题目或 Worker 部署服务。
3. 保留旧 CTF 工具镜像、同 Task 共同低权限文件/命令身份和共享工作卷；保留每个工作分配的网络身份用于流量归属。
4. 官方 MCP 增加命令身份与低权限文件的窄扩展，执行/文件仍调用官方 SDK。原始未绑定身份入口关闭。
5. VPN/可信提交位于 Runner 侧，只有一个外部 VPN；Solver 经内部隧道使用出口。默认不启用官方 Egress，因为其 OUTPUT 规则不自动约束嵌套 netns 的 FORWARD 流量；Cilium 与可信出口负责实际网络约束。
6. 所有受控 Agent 命令先登记，再执行；基础命令审计和可选进程观察分层显示，不把 eBPF 等同全部子命令/网络审计。

## 5. 方案取舍与未验证项

- 保留网络身份而不恢复逐题文件硬隔离；共同UID不承诺防御同任务Agent主动冒用、信号干扰或共享服务代发。归属优先使用实际网络入口与可信执行映射。
- 禁止root文件工具旁路，复用上游低权限文件worker，避免自建容易出错的符号链接路径ACL。
- 不启用官方Egress是本次根据实际FORWARD路径作出的平台选型，不表示该组件普遍无效；先做一种能覆盖当前要求的出口方案。
- 保留可信VPN出口的代价是内部隧道和固定网络组件；收益是单VPN和可信Lead提交通道。协议用成熟软件，平台只负责配置/状态/停止。
- 强制命令账本与可选eBPF观察分层。eBPF缺少完整argv、Agent身份、UDP等信息，不能满足“捕获所有解释器内部命令”的绝对承诺。
- Pi/子插件、权限下降、原生argv、文件身份、K8s网络与采集的最终组合尚未联调。P1先做有限接缝验证，再进入批量替换；这不是让用户替开发者判断底层接口。
