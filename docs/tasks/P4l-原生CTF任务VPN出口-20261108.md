# P4l：原生 CTF 任务 VPN 出口

已审实施方案，基线 `202258c`。按[平台架构方案](平台架构重构开发方案-20261105.md) R7 / §8，在 Runner 侧可信出口终止一个外部 VPN，Sandbox 经固定内层 L3 链路使用。当前只发布经过验证的数字 IPv4 TCP 求解流量，模型/业务 MCP/平台控制继续走原路径；命令记录只读，不做审查或处置。旧直连任务和 P4k 共享附件不更改。

1. **发布与凭据**：管理员显式发布 `openvpn-ipv4-tcp-v1`，冻结一个命名配置、固定数字 IPv4 TCP 求解目的及外层端点、预检目标、可信出口镜像与已验 TUN 能力。外层沿现 OpenVPN 2.7.8 传统 TUN（禁 DCO），内层为每 Task 独立、验证身份的 WireGuard 链路。工具和浏览器只提交安全能力 ID；外部凭据只由可信配置引用且只挂出口容器，不进 Node、Sandbox、附件、共享卷、提示词、日志或公开证据。由受信程序构造有界选项，禁止输入任意 `.ovpn`、脚本、路由/DNS 或 Pod patch；拒绝任意推送改变控制路由。首版每个部署只开放一个 PG 凭据槽位，证书重发、密钥轮换或发布版本变化不能绕过该占用；请求/启动/断开结果未知继续占位。普通断开仍保留凭据占用，直至原全部容器正退出。
2. **Lead 业务工具**：现可信 Business MCP 只对冻结启用任务的原 Lead 发布 `vpn_configure/status/disconnect`。模型与业务控制必须在 VPN down 时可启动。配置只收已发布 ID，按原 invocation 一次保存操作及已受理结果，不把 ACK 写成 ready。Runtime/出口在锁外按原 operation 一次执行，旧响应或换控制器只读对账原身份。status 返回安全阶段、原操作 ID 和当前可用动作；disconnect 绑定原操作。每 resource generation 只允许一次连接，同调用幂等；确认断开或身份变化后不重新开启该代，不提供伪重连。新代仅在受控恢复全部旧 CID 正退出后允许显式 configure；不自动登录。
3. **双层转发门**：可信独立出口容器绑定原 Task、Runner/Sandbox Pod UIDs/IP、原出口 CID、原控制 scope 和连接身份。只有该容器获实际 TUN 设备和必要网络能力；Task Pod 无新增对外控制 listener，出口向 BB 持专用原 scope 短许可。Sandbox 用固定可信系统预检通过原内层 WG 和外 VPN 到原数字目标，预检不授 Agent 通用权限或作 Agent 归属。预检与原实际 TUN/进程身份均有证且新鲜才开放 solver。去掉 VPN 任务的旧目标直连许可；Sandbox 根按精确 WG 口及原源约束，Runner 出口按原 WG→TUN 和返回方向约束，独立短内核出口 lease 与原 P4i per-binding grant 同时满足。只有 `exec_command` 及实际 solver 转发受 VPN 状态门控；文件工具与原命令结果仍可读。停、暂停、断开或失权撤 Solver 转发。仅原主动暂停正封存旧 binding/source/cgroup 后，可凭同 pause ID 和新短许可在未断开的原外层连接上启用新 binding/source；旧流不复用。未预告许可失效终止原代转发。模型/MCP/Server/Ingress 的现控制路由和 DNS 不因 VPN 变动。
4. **停止、恢复和采集**：不凭 404、HTTP 超时或脚本返回推断原进程已退出。停及退役按原 Runner、Host、出口三 CID 与原 Sandbox CID 全部正退出；此前不释放原共享凭据占用。原跨代恢复保存旧证明和原 P4k 工作卷附件历史；只允许新代在原全部正退出后显式配置。继续沿 P4i 抓 VPN 加密前的已知 Agent veth、封存及 MinIO/Linux 读取，不声称无证命令归属。断开/停止保持独立控制通道。
5. **必要验证**：一组 PG 场景覆盖冻结、原 Lead 和工具原回执、凭据并发互斥、未知占位、未就绪拒绝/原正退出释放；隔离集群验收一条完整的本地实际 VPN Task（失败的原 Task 留证并独立停止，不重放配置）：脚本模型 Lead 在 down 能控制，原操作配置→可信固定预检→实际数字 TCP 命令与原抓包→断开禁止旧/新目标流但控制仍可用→所有原容器正停止。设备以实测 scoped TUN 设备授权、内 WG 能力为前置。DNS、solver UDP/ICMP、回连、IPv6、任意外部路由、真实 TSec 来源/预检/提交及实际 VPN 凭据不在本片；只证明实际验过的能力。
6. **工作边界**：合同/BB 负责发布及状态、授权与已存原回执；Runtime/可信出口/启动器负责实际接口、租约和物理生命周期；现 Web 只说明冻结能力及断开限制，不加任意配置界面。沿干净候选运行必要测试及 `make check`，多 Agent 独审 exact 差量后本地提交。原 38 tracked、72 untracked 及四交付镜像保留；不读 `.env`，不改正式设计或 AGENTS，不启用用户现部署、不推送、不调用真实模型/VPN/靶场。

## 管理员配置与节点前置

沿 P4j 管理员发布文件显式加顶层 `vpn_profile: openvpn-ipv4-tcp-v1`。在完整 `runtime_resource_config` 中填写同一 `vpn.profile`、已发布 `id/label`、新 `sandbox_image` 与 `egress_image` 的不可变引用、只读原凭据 `namespace/name/uid/cert_sha256`、原 `peer.ipv4/port/server_name`、可信固定 `tun_ipv4` 和已验的 `tun_resource`；仅在本地集群隔离 peer 需要时填写 `peer_namespace`。保留现冻结 `traffic_targets`，VPN Task 不据此装直连 CNP。新 VPN Sandbox 镜像与原直连 capture 镜像明确区分。

管理员只在真实验收后更新私有验收 JSON 的 `vpn_profile`、`vpn_sandbox_image`、`vpn_egress_image`、`vpn_host_image` 和 `vpn_roundtrip_and_disconnect: true`，重算原文件摘要。VPN 客户端只在固定可信出口挂载原 Secret 的证书、CA 和私钥；证书字节摘要与不可变源 UID 必须与已冻结配置匹配。已验证的 TUN 设备资源按设备插件仅分配给该出口，Runner/Host/Solver 不获原设备。没有该节点能力、验收或真实连接正证时不发布求解转发。

OpenVPN 只使用固定参数及窄的服务端推送选项。[官方手册](https://openvpn.net/community-docs/community-articles/openvpn-2-7-manual/) 区分路由和接口配置；固定 [2.7.8 实现](https://github.com/OpenVPN/openvpn/blob/v2.7.8/src/openvpn/options.c#L8118-L8161) 的 `protocol-flags` 仅参与协议协商，其他非白名单推送仍忽略。本片不接受来源用户上传的任意配置，也不从 peer 取得控制路由/DNS。
