# P2b 公告与多 Flag：实施约束

2026-11-06 · 承接知识切片 401d7cf · 本轮仍不部署、不调用真实模型或靶场。

## 1. 业务版本与迁移窗口

- 只有受信 create_task 调用可在**同一创建事务**冻结 `business_contract=challenge-board-v1` 和角色工具 manifest。普通创建 body/模型不接收内部合同；不提供旧 Task 事后切换入口，缺字段继续 legacy。
- V1 的新业务只走 `/ctf/knowledge/`，发布工具没有旧入口；API 边界拒绝通过旧 tools/业务写路由绕过，旧 Task 权限与 automatic WIP 保持。
- legacy supervisor 对安全 TaskView 投影中的 V1 前置跳过，环境创建前再次校验。服务器旧 start/claim/recover/fail_start/review 准入也拒绝 V1；不能凭调用者传一个支持字符串放行。
- V1 真实 Runner 的支持、资源 readiness、binding/lease 核验由 P3 接同一门禁。接入前 V1 不会被旧模型执行器消费；控制停止、归档清理与旧历史读取保持可用。

## 2. 公告与候选

公告为 Task 级不可变版本，只有当前 fenced Lead 可发布，使用 request_id 和公告 revision。环境版本只引用平台观测，正文和请求参数不能设置 network/readiness。

候选只由当前负责人登记，helper 等待可信 ChildRun。原值受保护，公共 DTO、事件和 Lead 待办只有 ID、精确摘要与证据。明确授权的值详情允许 Task 用户、Lead、仍获准的作者；后端先鉴权再解密。原值不 trim/规范化。

verification round 从可信 Task 轮次、题目 scope_revision 和已登记平台目标引用派生，不取题面/说明文字，不接受模型填写 round。候选在 Task/题目/轮次/精确值范围去重，候选、事件、稳定 Lead 消息同事务；保存候选不完成题目。

## 3. 提交、停止与可信回执

submission_id/operation_id 由服务端稳定生成，同候选已有未决 operation 时不同 request_id 也不能再次派发。平台 call_id 保留原 Text 格式并关联；P3 复用同一业务记录，不另建远程执行权威。

Lead 只发起提交，模型不传 accepted/score。内部派发先持久登记，再只授予一次发送许可；重复、unknown 不再次授予许可。真实回执须匹配 operation/candidate/source/请求摘要与已登记 call_id，并由可信适配器留下可验证凭据；未支持或不能验证的来源只返回 unsupported/unknown。

可信捕获先按已登记调用绑定原样保存回包，包括 HTML、截断/坏 JSON 和空响应；规范结果解析在签封/验收阶段，失败保留 unknown 和原始 capture，不签 accepted。V1 的旧 challenge/record 事件同样按当前题目范围过滤，缺归属 linked 不公开；越界事件保留空游标，公告事件仍可全局读取。

迟到真实回执保存于原记录，停止后不唤醒 Lead、不恢复 Task、不释放未清理席位，不把 cancelled 工作改完成。停止事件取消尚未派发的提交；派发与停止竞争由同一 Task 锁裁定。

accepted 的部分正确继续，duplicate 不自行加分；得分按可信累计值的最新记录解释，总数未知不自动通关。只有当前目标版本下可信完整验收可推进题目完成。

## 4. 本轮范围

0022 仅追加 announcements、flag_candidates、flag_submissions 三表。沿用现有事件、Task 锁、身份与消息事务；新增聚焦公告/Flag 处理器，HTTP/未来共享 MCP 共用。任务归档和删除补齐新数据，不改 P1/P3 独占目录、schema/runner.py 或真实部署。

必要 PostgreSQL 场景集中验证公告权限/版本/网络边界、候选去重/保护/通知事务、多 Flag 与可信回执、停止派发竞争/迟到回执；不做字段测试矩阵。真实来源集成和新 Runner 发布由后续接缝分别验证，本轮不将假服务证明写成真实靶场验收。
